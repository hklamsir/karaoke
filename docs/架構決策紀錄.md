## ADR-001 · `-l yue` 內部重映射為 `language_hints=['zh']`

**狀態**：✅ 已接受（2026-10-29）

**背景**
原規格書假設 `-l yue` 可以指定粵語識別。實測發現這個假設不僅錯，而且**反效果最嚴重**。

**決策**
`--language yue` **不會**把 `yue` 傳給百煉。程式內部統一重映射為 `language_hints=['zh']`，並在 log 明確印出：
```
[warn] 已將 --language=yue 重映射為 language_hints=['zh']（見 ADR-001：yue 會觸發粵語→普通話轉寫）
```
其餘語言碼（`zh` / `en` / `ja` …）原值直傳。

**理由（實測）**
同一段粵語音源（ground truth：`我哋今晚一齊去食飯啦，你唔好唔記得帶埋個銀包。`）：

| `language_hints` | 輸出 | 粵語口語字 | 粒度 |
|---|---|---|---|
| 不傳（auto） | `我们今晚一起去吃饭啦，你不要不记得带个钱包。` | ❌ 全蒸發 | 詞級 |
| **`['zh']`** | **`我哋今晚一齐去食饭啦，你唔好唔记得带埋个银包。`** | ✅ **全保留** | ✅ **18/21 字級** |
| **`['yue']`** | `我们今晚一起去吃饭啦，你不要不记得带上个钱包。` | ❌ **全蒸發** | 詞級 |

`yue` 在這個 API 的實際語義是「**識別粵語，但輸出規範普通話書面語**」，等同於要求模型做方言轉寫。
另外：官方 `language_hints` 語言碼清單亦**根本沒有 `yue`**（只有 `zh en ja ko vi th id ms tl hi ar fr de es pt ru it nl sv da fi no el pl cs hu ro bg hr sk`）。

**被駁回的選項**
- **粵語自動改用 `fun-asr`**（官方唯一明文支援粵語）— 實測 fun-asr 確實正確輸出粵語（19/21 字級），但沒有 `usage` 字段、`confidence` 尺度不同，要雙軌處理。列為後備 model，不做自動切換：**自動切換會令 `--model` 參數失去決定性，對教學場景是災難**。
- **argparse 層面拒絕 `yue`** — 對香港用戶最不友善，它們不會理解為何「粵語不給選擇粵語」。

**後果**
- 代價：`--language` 的語義不再是「原值轉發」，code 必須有 mapping table。
- 好處：用戶打 `-l yue` 得到正確的粵語歌詞，而並非一堆普通話。

## ADR-002 · 不傳 `enable_words` 與 `enable_itn`

**狀態**：✅ 已接受（2026-10-29）

**背景**
原規格書要求「必須開啟 `enable_words=True`」與「`enable_itn=False` 避免數字被轉阿拉伯數字」。兩者**都不存在於本 model**。

**決策**
提交轉寫任務時**只傳** `model` / `file_urls` / `language_hints`（視情況）。其餘參數一律不傳。

**理由（實測）**
- 官方文件中 `enable_words` **只屬於 `qwen3-asr-flash-filetrans`**。本 model（`Qwen-Audio-3.x-ASR-Flash-Filetrans`）的時間戳是「**永久開啟、不可關閉**」，而 word-level **本來就自帶**。
- `enable_itn` 只存在於 `qwen3-asr-flash` 的 **OpenAI 兼容模式** `asr_options`。
- 實測：傳 `enable_words=True` / `enable_itn=False` **沒有報錯亦沒有可觀測差異**（both 200 OK，`words[]` 照樣有）。
- 不傳的好處是**減少對未文件化參數的依賴**：這些參數今日被靜默忽略，明日可能變成 `400 InvalidParameter`。

**後果**
- 數字歌詞如何呈現由模型決定，我們控制不到（原規格書想解決的問題仍然存在，但**無解**，並非我們不做）。
- code 更簡單、更抗 API 變動。

## ADR-003 · 本地音頻上傳走 `Files.upload → Files.get()` 預簽名 URL

**狀態**：✅ 已接受（2026-10-29）

**背景**
Filetrans 模型不收本地路徑，必須先上傳。原規格書建議用 `oss://` + `X-DashScope-OssResourceResolve` header。

**決策**
主路線：
```python
up   = dashscope.Files.upload(file_path=wav, purpose="assistants")
fid  = up.output["uploaded_files"][0]["file_id"]
url  = dashscope.Files.get(file_id=fid).output["url"]   # 預簽名 https URL
if url.startswith("http://"):
    url = url.replace("http://", "https://", 1)
```
後備路線（`Files.get()` 失敗時）：`OssUtils.upload()` + `Transcription.async_call(..., headers={"X-DashScope-OssResourceResolve": "enable"})`。

**理由（實測）**
四種做法全部試過：

| 做法 | 結果 |
|---|---|
| `file://C:\...` 直塞 `file_urls` | ❌ `DECODE_ERROR` |
| 裸絕對路徑 | ❌ `REQUEST_INVALID_FILE_URL_VALUE` |
| `oss://...`（**沒有** header） | ❌ `REQUEST_INVALID_FILE_URL_VALUE`（13.8s 後 FAILED） |
| `oss://...` + `OssResourceResolve` header | ✅ SUCCEEDED |
| **`Files.get()` 預簽名 https URL** | ✅ **SUCCEEDED（無需額外 header）** |

⚠️ **陷阱**：`dashscope.Files.upload()` 返 200 但僅給一個 `file_id`，**並非**可以直接餵給 ASR 的 URL；必須再 `Files.get()` 拎 `url` 字段。
⚠️ 預簽名 URL 有 `Expires` 參數（實測約 7 日有效），必須「上傳即提交」，不要 cache。

**後果**
- 主路線不依賴任何未公開的 header，SDK 升級更穩。
- 需要兩次 API call（upload + get）而非一次。

## ADR-004 · 永久禁用 `paraformer-v2`（假時間軸）

**狀態**：✅ 已接受（2026-10-29）

**背景**
為了搵「粒度最幼」的 model，測了成個 model 清單。`paraformer-v2` 表面數據**最好**，實際上是最差的選擇。這條決定特別記低，因為**下一個人好大機會會再選擇它**。

**決策**
不准用 `paraformer-v2`（或任何 paraformer 變體）黎產生卡拉OK 時間軸。code 層面加 assertion log。

**理由（實測）**
粵語測試音源（21 個有效字）：

| 指標 | `paraformer-v2` | (`qwen-audio-3.1 + zh` 對照) |
|---|---|---|
| WordSlot 數 | **21（看似完美 100%）** | 18（86%） |
| 每個 duration | `244, 245, 245, 245, 244, 245, …` | `120, 240, 280, 320, 200, 120, 200, 280, …` |
| **duration 唯一值數量** | **2** | **7** |
| word 間 gap | **全部 0** | 有非零值 |
| 起始時間 | **0 ms**（實際語音 280 ms 先開始） | 280 ms |
| `confidence` 字段 | **沒有** | 有 |

→ 是**均勻線性插值**，並非聲學對齊。仍衰的是它**沒有句子內部停頓**：實測 ground truth 兩句之間有明顯停頓，paraformer 當沒有到。

**後果**
用它做出來的卡拉OK 會是**機械等速掃過**，完全不跟歌手節奏，而且因為沒有 gap，字幕永遠不會在停頓位停低。

## ADR-005 · ASS 時間戳統一格式為 `H:MM:SS.cc`，並集中於單一 helper

**狀態**：✅ 已接受（2026-10-29）

**背景**
開發期間踩過一次：時間戳寫成 `M:SS:cc`（如 `0:00:28`），ffmpeg 沒有報錯退出，僅在 verbose log 印了兩行 `Bad timestamp`，然後**輸出一條完全沒有字幕、而且 md5 同輸入完全一樣的 mp4**。

**決策**
- 全專案只准有一個 `ms_to_ass_time()` helper，格式 `"{h:d}:{m:02d}:{s:02d}.{cs:02d}"`（例：`0:00:00.28`）。
- 分鐘與秒**必須兩位數**，毫秒位必須用小數點分隔。
- ms → cs 的換算（`max(1, round(ms/10))`）亦只准有一個 helper。

**理由**
1. ASS 規範硬性要求 `H:MM:SS.cc`。寫 `0:00:28` 時 libass 會解讀成「28 秒」，導致 event 時間錯位。
2. **失敗模式極度隱蔽**：ffmpeg exit code 0、輸出檔案存在、size 正常，僅沒有字幕。肉眼驗收先會發現，自動化測試不 check frame content 就過了。

**後果**
- 所有時間運算集中在兩個 function，改算法僅改一處。
- **要求**：任何改動這兩個 helper 的 PR，必須附「抽 frame 目視驗證」的證據（对比 `_probe/burn test dir/frame_C_*.png`）。

## ADR-006 · ffmpeg 燒錄：切 cwd + 相對路徑 + `original_size`

**狀態**：✅ 已接受（2026-10-29）

**背景**
原規格書已預警 `ass=` filter 的路徑跳脫問題。實測確認存在，而且爆法好具體。

**決策**
1. **永遠不要**把路徑直接寫入 `-vf ass=<path>`。改為：設 `subprocess.run(..., cwd=<ass 檔案所在目錄>)`，filter 只寫 `ass=<檔名>`；輸入影片用 `os.path.relpath()` 轉相對路徑。
2. ffmpeg 命令**必須**帶 `original_size=WxH`；同時 ASS 檔的 `PlayResX/PlayResY` 由 **ffprobe 讀取原片**填入，不准寫死。

**理由（實測）**
```
$ ffmpeg -vf "ass=C:\Users\pslam\...\burn test dir\karaoke.ass"
[Parsed_ass_0] Unable to parse "original_size" option value
               "UserspslamDocumentsAgents_workspaceskaraoke_probeburn test dirkaraoke.ass"
               as image size
→ rc = 4294967274
```
Windows 路徑的 `C:` 冒號被 ffmpeg 當成 **filter option 分隔符**，路徑被切成兩段。目錄裡面的**空格**進一步惡化。
切 cwd + 相對檔名 → 立即成功。

`original_size` 的必要性：libass 需要知道原片尺寸，才可以用正確比例擺放字幕；不加會在輸出 canvas 與輸入尺寸不一致時走位。

**後果**
- `subprocess` call 必須帶 `cwd=`，而且 input path 要 `relpath` — 這個約束要寫在 function docstring。
- 需要先跑一次 `ffprobe` 拎解像度（多一次 subprocess call，可接受）。

## ADR-007 · 歌詞校正必有「字數鎖」，且思考模式必須 ON

**狀態**：⚠️ **已被 ADR-012 取代**（2026-10-29）——歌詞校正整體由 CLI 移除。
本 ADR 保留作歷史紀錄，其實測結論（思考模式是字數鎖必要條件）仍然有效，
若日後要重新引入校正功能，請先讀本 ADR 再讀 ADR-011 / ADR-012。

**背景**
用戶要求加入 LLM 歌詞校正（用百煉 `qwen3.8-27b`）。風險是：LLM 改寫歌詞後**字數改變**，會令所有 CharSlot 的時間軸失去對應關係。

**決策**
1. **字數鎖是鐵律**：校正後每行字數必須 `==` 校正前。**由程式驗證，並非靠 prompt 保證**。
2. **驗證失敗 → 棄用校正結果，原地退回 ASR 原文**，並 warn log。（寧願歌詞有錯字，都不可令時間軸錯位。）
3. **思考模式必須保持 ON**。`enable_thinking=False` 在本專案是**[禁用]**。
4. 預設 model = **`qwen3.8-flash`**；`qwen3.8-27b` 保留為 `--correction-model` 進階選項。
5. 以**批量**（每行 `N|原文（X字）`）發送，行號對齊輸出。

**理由（實測，同一份 6 行測試歌詞）**

| model | thinking | 用時 | 字數鎖 |
|---|---|---|---|
| `qwen3.8-27b` | ON | 134.6 s（22.4 s/行） | ✅ 6/6 |
| `qwen3.8-27b` | OFF | 2.9 s（0.5 s/行） | ❌ **5/6** |
| **`qwen3.8-flash`** | **ON** | **51.9 s（8.6 s/行）** | ✅ **6/6** |
| `qwen3.8-flash` | OFF | 2.5 s（0.4 s/行） | ❌ **5/6** |

→ **思考模式是守住字數鎖的必要條件**。關思考快 ~60 倍，但會數錯字數（實測把「其实我好想你知道我一直都在这里等你」改成少了字）。

校正質素實測結果（正確）：
`我们→我哋` / `已经→已經` / `光竟→光景` / `不要说话→唔好講嘢` / `在这里→喺呢度` / `天塌下来→天塌落嚟`

**被駁回的選項**
- **不鎖字數、校正後重新分配時間軸** — 本末倒置：重新分配就是重新引入估算誤差，抵消了 ASR 時間軸的價值。
- **用 `fun-asr` 的 `confidence` 做門檻代替 LLM** — confidence 只能話你低信心，不會話你應該改成甚麼字。

**後果**
- 一首 40 句的歌，校正階段約需 `40 × 8.6s ÷ 併發數`。**必須做並行分批**（ADR-007 後續：預設 batch=6 / workers=4），並顯示進度。
- 這個是全 pipeline 最慢的一步，要有 `--no-correction` 開關給用戶跳過。

## ADR-008 · 處理管線次序：OpenCC 押後到最後一步

**狀態**：✅ 已接受（2026-10-29）

**背景**
直覺做法是「ASR 一出就跑 OpenCC 轉繁體」。實測發現如此做會被後面的步驟破壞。

**決策**
固定次序，不准調亂：
```
ASR → 字數鎖校正（LLM）→ 拆字（WordSlot→CharSlot）→ OpenCC s2hk → 斷句 → 生成 ASS
```
理由分層：
1. **校正必須在拆字之前** — 字數鎖是以「行」為單位；拆完字再改就無從保證字數對應。
2. **OpenCC 必須在 LLM 之後** — LLM 輸出**繁簡混雜**，實測：`我哋遊過當晚漆黑嘅海港`（前半繁、後半簡）。OpenCC 做最後一道**正規化閘門**，保證落地前全部是港式繁體。
3. **`config` 固還是 `s2hk`**，不用 `s2twp`（差異：`裏vs裡`、`説vs說`、`着vs著`），亦**不用 `t2hk`**（實測 `t2hk` 對本專案輸入反而輸出簡體，行為反直覺）。

**理由（額外）**
- OpenCC `s2hk` 在 53 個測試詞上 **0 個長度變化**（如 `里面→裏面`、`干什么→幹什麼`），**不會破壞字數鎖**，所以放最後安全。
- ⚠️ 但注意：字數鎖的驗證必須**在 OpenCC 之前**用「同一個基準」做（LLM in vs LLM out），不可跨 OpenCC 比較。

**後果**
- OpenCC 只跑一次（對最終 CharSlot），效能最好。
- 若日後加新的文字變換步驟，必須插入這條 chain 的正確位置並更新本 ADR。

## ADR-009 · 輸出規格固定：mp4 / libx264 crf18 medium / `-c:a copy`

**狀態**：✅ 已接受（2026-10-29）

**背景**
目標用戶是香港社福界同工（課堂環境、設備參差）。輸出規格要「一定播到」。

**決策**
- 輸出容器**一律 `.mp4`**，檔名 `<原檔名>_karaoke.mp4`（即使輸入是 `.mkv` / `.mov`）。
- 視頻：`-c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p`。
- 音頻：**`-c:a copy`**（原規格書要求保留原聲軌 + 加速）。**若失敗則降級** `-c:a aac -b:a 192k` 並 warn。
- 解析度、幀率**跟原片**（不縮不放）。

**理由（實測）**
- `-vf ass=` **必然導致 video re-encode**，`-c:a copy` 只對音頻有效 — 所以「保持原片畫質」實際上是「以 crf18 接近無損重編」，要講清楚。
- crf 18 / preset medium 是「接近無損 + 可接受編碼時間」的平衡點，對 4-12 小時課程的示範 MV 長度（3-5 分鐘）綽綽有餘。
- 遇到 mkv 常見的非 mp4 相容音頻編碼（eg. 某些 PCM / Vorbis），`-c:a copy` 會失敗 → 必須有降級路徑。

**被駁回的選項**
- **保留原容器**（mkv 出 mkv）— 社福界設備參差，mkv 並非部部播到。
- **NVENC 硬體加速** — 用戶機器不一定有 N 卡，要寫 fallback，複雜度換不到確定性收益。日後可加做 `--hwaccel` 可選 flag。

**後果**
- 實現上要根據 ffprobe 結果決定音頻 codec，不可無條件 copy。

## ADR-010 · 重依賴一律「懶安裝 + 友善提示」

**狀態**：✅ 已接受（2026-10-29）

**背景**
`--separate-vocals` 需要 AI 人聲分離（`audio-separator` / `demucs`），這些會拖入 `torch` / `onnxruntime`，體積以 GB 計。而本工具的用戶是課堂環境的社福界同工。

**決策**
- `audio-separator` **不入** `requirements.txt`。
- 基礎 `requirements.txt` 只放：`dashscope`、`requests`、`python-dotenv`、`opencc-python-reimplemented`、`openai`。
- 用到 `--separate-vocals` 時先 `importlib.util.find_spec("audio_separator")` 檢查；沒有裝就**印出具體安裝指令**並乾淨退出：
  ```
  [error] 未偵測到 audio-separator。請先執行：
          pip install audio-separator
      （人聲分離會額外安裝 onnxruntime，約需 500MB～2GB 磁碟空間）
      （不用人聲分離可改用 --separate-vocals 以外的預設模式）
  ```
- 同理適用於未來任何重依賴。

**理由**
一般 `--separate-vocals` 是**可選強化**：背景音樂強烈時先用。基礎用戶（八成以上）裝不到 GB 級依賴。
另外實測已知：`qwen-audio-3.1 + language_hints=['zh']` 在**沒有人聲分離**的情況下，對純人聲 TTS 的粵語識別已達 21/21 全中 —— 人聲分離並非常必需。

**被駁回的選項**
- **直接寫入 `requirements.txt`** — 對課堂環境是災難。
- **改成 `extras_require`（`pip install -e .[vocals]`）** — 標準做法，但要改成完整 package 結構（`pyproject.toml`），放棄「單一 `main.py` 拎去就用」的簡單交付，同課程教材的定位不夾。

**後果**
- 「懶依賴」的錯誤訊息必須寫清楚安裝指令同磁碟空間，否則用戶會卡死。

## ADR-011 · 歌詞校正改為「保留原文語體」，禁止書面語⇄口語互相改寫

**狀態**：✅ 已接受並實作（2026-10-29，真實 MV 端到端實測後修訂 ADR-007）

**背景**
ADR-007 定落的校正 prompt 第 4 條是「輸出繁體中文，用香港粵語口語字（的、它、不、們、了、是、在、諗、看）」。
初版在 edge-tts 朗讀語料上測試表現良好（`我们→我哋`、`光竟→光景`），但**該份測試語料全部是粵語口語**。真實 MV 一上場就出事。

**測試條件（首次真實歌唱場景）**
- 素材：林家謙《普渡眾生》（電影《破．地獄》主題曲）MV，1920×1080 / AV1 / 60fps / AAC / 180 秒
- Ground truth 歌詞：239 字（取自百度百科、Shazam、官方 MV 描述三方交叉驗證）
- ⚠️ **關鍵：呢首歌的原詞是標準書面語**（`輪迴塵間的人`、`徘徊來生的往生`），**並非**粵語口語

**決策**
1. 校正 prompt 第 4 條改為：**只修正語音識別造成的同音／近音錯字；原文是書面語定口語，必須原樣保留**，
   並逐項列明禁止的轉換（`的↛嘅` `不↛唔` `這↛呢` `來↛嚟` `給↛畀` `了↛咗` `還↛仲`）。
2. ASR 片尾的**單字雜訊殘句直接丟棄**（實測吐出過 `"用。"`）。

**理由（實測，同一份 ASR 結果、同一 model、只換 prompt）**

| 策略 | 相似度 | 正確字數 | Δ vs 不校正 | 用時 |
|---|---|---|---|---|
| 不校正（基準） | 89.54% | 214/239 | — | — |
| V1 強制口語化（ADR-007 初版） | 80.75% | 193/239 | **−21 字** | 126 s |
| **V2 保留語體（本 ADR）** | **90.38%** | **216/239** | **+2 字** | 340 s |

→ LLM **無從判斷**一首歌是書面語定口語，強制改寫必然錯一半。
第二次完整重跑（ASR 每次結果略有不同）V2 只改了 3 處：修好 `循回→輪迴`，但整壞兩處 `迴→回`，**淨收益 −1 字**。

**同時落實的驗證結論**
- **ADR-001 在真實歌唱場景成立** ✅：  `language_hints=['zh']` 對有伴奏、有唱腔的真 MV 出到 **89.7% 相似度**，
  而且原詞的書面語格式保留完整（`輪迴塵間的人`、`徘徊來生的往生` 全部踢中）。
  初版用 edge-tts 朗讀語料得出的結論沒有被推翻。
- **`PrimaryColour` = 「唱過」的高亮色** 已經**目視雙重確認** ✅（抽 frame 實拍：6.0s 時前 5 字黃色、其後白色；100s 時約 15 字黃、6 字白）。
  名詞表 C 組的語義定義正確，不需要調轉。

**Observed：ASR 與 LLM 兩者都是非確定性的**
兩次完整重跑同一段 MV：ASR 產生 13 句 vs 12 句、字數 239 vs 238、逗號位置亦有差異；
同一 prompt 的校正結果亦有明顯差異。**同一輸入可以出不同質素的字幕**，呢點要寫落 README 風險章節。

**尚未定案（等使用者拍板）**
V2 雖然消滅了災難模式，但**在呢首書面語歌上淨收益只是 −1 ~ +2 字，卻要等多 2～7.5 分鐘**。
口語比重高或咬字含糊的歌可能更有價值，但**未實測**。
→ 待決：校正維持「預設開啟」定改為「`--correct` 手動開啟」。

## ADR-012 · timings.json 做 canonical；CLI 拆 generate / render / burn；移除 LLM 校正

**狀態**：✅ 已接受並實作（2026-10-29）

**背景**
smoke test 之後使用者進一步釐清產品定位，兩點根本變化：
1. **範圍收窄**：本工具只處理**粵語、國語、英語的書面語歌**。
2. **會加字幕編輯 UI**：讓使用者自己精準對齊每個詞的時間戳。
3. 既然有 UI 可以人手改錯字 → **LLM 歌詞校正變成負 ROI**（ADR-011 實測淨收益 −1 ~ +2 字，卻要等 2~7.5 分鐘）。

呢三點令原本「一條龍 ASR→ass→mp4」的單一命令變得不合用。

**決策**

1. **`*_timings.json` 是 canonical interchange format**；`.ass` 降級為**由 json 渲染出來的衍生物**。
2. **CLI 拆三個 subcommand**：
   ```
   generate   影片 → ASR → timings.json + ass      （**預設不出影片**）
   render     timings.json → ass                   （毋須重跑 ASR）
   burn       影片 + ass → mp4                     （僅使用 ass）
   ```
3. **`generate` 預設不再出 mp4**，要影片請另外行 `burn`。
4. **徹底移除 LLM 歌詞校正**（code 清走，`openai` 亦移出 requirements.txt）。錯字交給 UI 人手改。
5. **`burn` 僅食 `.ass`**，永遠不會隱含 render，避免靜默洗走人手 / UI 的改動。
6. **OpenCC 只在偵測到中日韓字元時先跑**（使用者提出會做英語歌）。
7. **斷句改在 WordGroup 邊界切**，不再切穿一個詞。
8. **`burn` 由 `.ass` 自己讀 `PlayResX/PlayResY`**，令 burn 無需依賴 timings.json 都行得通。

**timings.json schema（v1）**

```jsonc
{
  "schema_version": 1,
  "source": { "video": "...", "model": "...", "language_hints": ["zh"], ... },
  "style":  { "play_res_x": 1920, "font_name": "...", "primary_color": "#FFFF00", ... },
  "lines": [{
    "start_ms": 3950, "end_ms": 8890, "text": "輪迴塵間的人，揮之不能",
    "words": [{
      "text": "輪迴", "begin_ms": 3950, "end_ms": 4670,
      "estimated": true,                       // ← 詞內逐字邊界是按比例平分估出來
      "chars": [ { "text": "輪", "begin_ms": 3950, "end_ms": 4310 }, ... ]
    }]
  }]
}
```

- **兩層結構 `words[] → chars[]`**：保留 API 原本的詞邊界，UI 可以給用戶拖成個詞、亦可展開逐字微調。
- **`estimated` flag 是本 schema 最重要的字段**：實測呢首 MV 有 **40% 的詞 / 57% 的字**的逐字時間軸是程式估出來。
  沒有這個 flag，UI 用家無從知道邊些要人手校。
- `style` 內嵌 → render self-contained，改樣式無需重跑 ASR。
- 每行的 `start_ms/end_ms` **存絕對值**，`render` 直接用、**不重新推算**（避免 UI 改動同輸出對不上）。

**理由（實測，2026-10-29 林家謙《普渡眾生》MV）**

| 項目 | 舊一條龍 | 新 generate |
|---|---|---|
| 執行時間 | 7m45s ~ 9m24s | **11 秒** |
| 產出 | ass + mp4 | **json + ass**（沒有 mp4） |
| API 花費 | ASR + LLM 校正 | 僅 ASR |

驗證結果：
- `render` 同一份 json 行兩次 → **byte-identical**（沒有 round-trip 漂移）✅
- `render` 不會改動輸入 json（除非加 `--sync-style`）✅
- `render --primary-color "#00FFFF" --font-size 64` → ASS `&H00FFFF00` / fontsize 64，覆寫生效 ✅
- `burn` 由 `.ass` 讀到 `PlayResX/Y = 1920x1080`，出 57.33MB mp4、保留 AAC 44.1kHz 立體聲原音軌 ✅
- 目視：7.0s 時前 8 字黃色（已唱）、後 3 字白色，底部居中 + 黑色描邊 ✅

**被駁回的選項**
- **`.ass` 繼續做 canonical** — UI 要自行處理 `\kf` 累加值的相對時間運算，而且 `estimated` 資訊在 ass 裡面**永久消失**。
- **`burn` 自動由 json render** — 會令「人手改過的 ass」被靜默覆寫，屬災難級 silent clobber。
- **保留 LLM 校正做 suggestions 清單** — 使用者最終決定：既然 UI 可以直接改錯字，範圍又僅書面語歌，校正沒有存在價值。
- **加 preview 功能（抽單格 / 短片）** — 使用者否決，直接 burn 全片。

**後果**
- `.ass` 檔案頭有註明「改時間請改 json 再 render」，但**沒有技術上強制**；UI 要引導用戶不要直接改 ass。
- `schema_version` 已加；日後加字段要 bump 版本並更新本 ADR。
- `timings.json` 若被人手改壞（例如顏色寫 `null`），`render` 有兜底預設值 + 清晰錯誤提示（實測撞過）。

## ADR-013 · 標點優先斷行 + 歌詞去標點（2026-10-29）

**決策**

1. **斷行改為「標點優先」**：全部句讀符號（`，。！？；：、…` ＋英文對照）都是斷行點；
   ASR `sentence` 邊界當「隱含句末標點」（防 ASR 漏標點）。
   `max_chars=18` 同 `gap>800ms` **降級做安全網**，淨在「分句本身超長」時在 WordGroup 邊界兜底。
2. **歌詞顯示剝走標點**（預設），統一規則：**行尾標點 → 剝走；行中標點 → 變半形空格 + `{\k<gap_cs>}` 停頓**。
   `--keep-punctuation` 可以還原 v1 行為（byte-identical 已實測）。
3. **短句定向合併**：雙條件（字數 ≤3 **且** 自身時長 <1500ms，`--min-clause-chars` / `--min-clause-ms`）
   先算「太短」；句末（hard）收尾 → **向後併**（黐返上一行尾）、句讀（soft）收尾 → **向前併**（帶住下一句）；
   合併會令行超 `max_chars` 就放棄、照出短行。
4. **資料結構**：`punctuation` 由 `CharSlot.text` 尾搬去獨立的 `WordGroup.punctuation` 字段，
   `CharSlot` 從此**永遠純字**；`WordGroup` 加 `sentence_end` flag；`LyricLine` 加 `break_reason`
   （`punctuation` / `sentence` / `max_chars` / `gap`）。
5. **timings.json bump `schema_version=2`**：`words[]` 加 `punctuation`、`lines[]` 加 `break_reason`、
   `lines[].text` 改為顯示用文字；v1 舊檔**自動相容**（讀入時將黐在 text 尾的標點拆返出來，只 warn 不 fail；
   英文句號 `.` 刻意不剝，避免動到 `Mr.` 呢類縮寫）。

**理由（實測，2026-10-29 林家謙《普渡眾生》MV，23 行 / 169 詞 / 32 個標點）**

| 證據 | 數字 |
|---|---|
| 舊 `max_chars` 切法錯位 | 4 處（`…分叉的走`／`馬路，…`、`…偏偏起`／`了一次…`、`…世塵`／`傷感。`、跨 sentence 砌行 `…遺憾中，`／`普渡的眾生`），仍製造 2 字殘行 `不能。`／`傷感。` |
| 純按標點分句 | 32 個分句、**最長 13 字、最短 4 字**，全部 < 18 → 兜底完全無需觸發 |
| ASR sentence 邊界 | 15 句裡面 14 句本身以 `。`／`？` 收尾（同標點斷點高度重疊） |
| 標點不影響時間軸 | `punctuation` 在 ASR **沒有獨立 begin/end**，剝不剝都無需改任何 `\kf` / `hold_ms` |
| v1 相容驗證（probe16） | 169 詞標點全數拆返出來、CharSlot 時間軸 **0 drift**；`--keep-punctuation` render 出來 Dialogue **byte-identical** |
| 新斷句驗證 | 32 行全部 ≤18 字、顯示文字 0 標點、4 個錯位全數修復、`break_reason` 全部 `punctuation`（兜底零觸發） |

**被駁回的選項**

- **`max_chars` 做主、標點只是建議** —— 實測標點分句天然就 fit（最長 13 字），而 `max_chars` 才是錯位切法的元兇。
- **僅句末符號（。！？）斷行** —— 會放棄好多好斷點，出 13 字以上長行。
- **短句一律向前合併** —— 句末短樂句（如 `好冇。`）會讓人拉了入下一句，聽感割裂；分方向才語義正確。
- **Stage 6 直接掉了標點** —— timings.json 永久失去標點資訊，日後 UI 想還原／顯示都無法返轉頭。
- **保持 v1 格式加冗餘字段** —— `text` 會有歧義（含不含標點？），寫入讀取容易重複剝。

**後果**

- **ASR 標點擺錯位會照錯位斷行**（實測有 `揮之不能徘徊，` 呢類）—— 固有風險，algorithm 層減不到；
  靠 `break_reason` 記錄 + 日後字幕編輯 UI 人手改（同 ADR-011/012 方向一致）。
- `WordGroup.text` 語義改變（不再含標點）；`LyricLine.text` 是純字，**顯示一律行 `display_text()`**。
- 渲染時插空格 + `\k` 要將 `prev_end` 更新為下一詞 `begin_ms`，否則會重複插 `\k`、停頓雙倍（probe16 已驗證）。
- 短句合併後行中可能有多於一個空格（連鎖合併），屬預期行為。
- 驗證腳本：`_probe/probe16_punct_split.py`（25 項全 PASS）。

**修訂（2026-10-29 同日，實測《每當變幻時》後）**

1. **短句門檻放寬**：`min_clause_chars` 3 → **5**、`min_clause_ms` 1500 → **2500**——
   舊門檻太保守，4-5 字快句照出會太散（《每當變幻時》28 行 → 24 行）。
2. **合併上限獨立**：新增 `MERGE_MAX_CHARS = 16`（`--merge-max-chars`）——
   合併是為了消滅短行，並非為了砌長行，所以同兜底的 `max_chars=18` 分開；
   合併後超 16 字就放棄、短行照出。
3. **`_kind()` 標點優先過 `sentence_end`**：word 自帶標點才決定 hard/soft，
   `sentence_end` 僅「沒有標點」時的 fallback（B2「隱含」的原意）。
4. 驗證：probe16 加 (c2)/(g1)/(g2) 三個 case，**28 項全 PASS**；
   實測《每當變幻時》24 行全部 ≤16 字、無標點、無異常短行。
5. 已知殘留：ASR 在 `逝去了的` 後面放 `。`（hard）→ 按規則向後併落
   `韶華去 四季暗中追隨` 尾，同樂句不夾 —— 屬 R1 標點擺錯位固有風險。

## ADR-016 · 預覽／時間軸分界改「像素制」，波形高度改「目標值 + 夾高」（2026-11-02）

### 狀態
✅ 已採納（最終定案：sidebar 160px／左欄 386px（歌詞樹 5 欄 370px）／品牌兩行 15px／
預覽 +80px → 波形 192px、字塊 33px）

### 背景
1. **比例制**下 `_preview_ratio = 0.55` 只保證「大約」，任何視窗高度變化都會令 +100px 走位；
   用戶要求的是**實數**（預覽加、時間軸減），比例制做不到。
2. **物理衝突**：1920×1009 視窗下右欄高 899px。時間軸畫布高 = 窗格 − 52px（標題＋zoombar）。
   「波形 128→192（+50%）＋字塊 22→33（+50%）」要
   `20(刻度)+192+4+33+16(概覽) = 265px` 畫布高 → 對應時間軸窗格 317px（= −80px）。
   所以 **預覽 +80 / 時間軸 −80** 先可以同時滿足「波形 +50% ＋ 字塊 +50%」；
   一開始試 +100 只做到波形 172px（+34%），差 20px 擠不落。

### 決策
- `editor._preview_h` 改**像素制**：首次量度 = `int(右欄高 × 0.55) + PREVIEW_EXTRA_H(80)`，
  之後拖曳直接改像素；夾 `[120, 右欄高 − MIN_TIMELINE_H(200)]`（等價於舊有 30%–75% 保護）。
- `timeline.WAVE_H = 192` 是**目標值**，`_wave_h_for()` 夾成
  `min(192, 畫布高 − 刻度 − 概覽 − 4 − 一條 LANE_H)`：「先保證有一行字幕塊，剩落的全給波形」。
  317px 窗格下剛好食到 192px（不再縮水）；若用戶日後拖矮時間軸，波形會自動讓位而不會蓋住字塊。
- 字塊 `LANE_H 22→33`、`BLOCK_GAP 6` → 方塊高 18→27（+50%）。
- 字塊 lane 下限由 2 改 1：時間軸變矮之後強行留 2 行只會浪費；行與行本身不重疊，
  first-fit 實際上永遠用第 1 行（同改動前觀感一致）。
- 圖例由獨立一行搬上 `_tl_box` 的 LabelFrame 標題，回收 ~20px 垂直空間給波形。
- sidebar 總寬 200 → **160px**（`SIDEBAR_MIN_W` 160→140，仍可拖曳）。
- 品牌方塊 `Karaoke AI Subtitler` **分兩行**（`Karaoke` / `AI Subtitler`），11pt（≈15px @96dpi）；
  一行要 146px，160px 欄減 padx/內距只剩 134px，一定爆格。窗口標題同步改 `Karaoke AI Subtitler`。
- 左欄 260 → **386px**：歌詞樹 5 欄總寬鎖 **370px**（32+174+66+66+32），
  加 scrollbar 8 + LabelFrame 邊框/內距 8 = 386，五欄一欄都不裁。
  逐字微調「詞」欄 64→140。

### 影響
- `ui/theme.py`（`SIDEBAR_W`）、`ui/app.py`（標題、品牌 Label、`SIDEBAR_MIN_W`）、
  `ui/pages/editor.py`（`LEFT_W`／`PREVIEW_EXTRA_H`／`MIN_TIMELINE_H`／`_clamp_preview_h`／圖例位置）、
  `ui/widgets/timeline.py`（`WAVE_H`/`LANE_H`/`BLOCK_GAP`/`MIN_WAVE_H`、`_wave_h_for`、`_lanes_y_top`）、
  `ui/widgets/lyric_tree.py`（5 欄寬度合共 370）。

### 驗證
`_probe/probe_layout.py` 幾何 dump（`_smoke/layout_before|after2|v3.json`）＋截圖目視：

## ADR-017 · 導航字級要經 ttk style；顏色色塊改 grid + 雙重上色（2026-11-02）

### 狀態
✅ 已採納（用戶需求：sidebar 160→140px、導航按鈕字級 +2、色塊顏色要同選取一致）

### 背景
1. **ttk::button 沒有 `-font` option**（不似 tk.Button）：`ttkb.Button(..., font=...)` 直接
   拋 `_tkinter.TclError: unknown option "-font"`。字級一定要經 `ttk.Style().configure(style, font=...)`。
   但 `bootstyle="primary"/"secondary"` 每次切頁都會改寫 widget 的 `style`，
   想「只在導航按鈕加大字」就不可只設一次。
2. **色塊不跟選取色**（用戶附截圖回報）：原本用 `pack` 排「色塊 + hex 輸入框」，
   視窗一窄，pack 會先壓細第一個子元件 → 色塊縮到看不到（或只剩一兩 px），
   而 hex 輸入框照樣顯示新色 → 用戶見到「色塊同選擇的色不一致」。
   另外舊 code 只寫 `canvas["bg"]`，而且只 catch `ValueError` ——
   Tk 對 `#0000F` 呢類 5 位 hex 會拋 `TclError`，令色塊靜靜停留在舊色。

### 決策
- 導航按鈕改自訂 style：`Nav.TButton`（未選中）／`NavActive.TButton`（當前頁），
  兩者 `font=(ui_font, 11)`（主題預設 9pt +2），顏色用專案色票
  （`BG_HOVER` / `ACCENT`），切頁時切 style 而不再切 `bootstyle`。
- 色塊 cell 由 `pack` 改 `grid`（label 跨兩欄、色塊 column 0、輸入框 column 1），
  子元件不會再被擠到消失。
- 新增 `_set_swatch(key, color)`：**Canvas 背景 + 填滿的 rectangle item** 雙重上色；
  `color=None`（輸入未合法）就保留舊色並把邊框轉紅，不會出現「輸入新色、色塊舊色」。
- 新增 `_normalise_hex()`（regex `^#?[0-9a-fA-F]{6}$`）：接受沒有 `#`、大小寫混寫；
  輸入框失焦／Enter 時寫返 `#RRGGBB`，所以文字同色塊一定對得上。
- sidebar 總寬 160 → **140px**（`SIDEBAR_MIN_W` 140→120）。

### 影響
- `ui/theme.py`（`SIDEBAR_W`）、`ui/app.py`（`_nav_styles`、`NAV_FONT_SIZE`、切頁改用 style）、
  `ui/pages/home.py`（`_HEX_RE`／`_normalise_hex`／`_set_swatch`／`_normalise_entry`／色塊 grid 化）。

### 驗證
`_probe` 實機截圖：sidebar 140、品牌兩行、4 顆導航 11pt 無裁切、當前頁藍底深字；
主頁色塊 #00FFFF / #FF8800 / #000000 與輸入完全一致；
`#1234`（未打完）→ 保留舊色 + 紅框；`FF8800`（沒有 `#`）→ 認得並上色。
`tests/test_editor_core.py` 26 checks PASS。

## ADR-018 · UI 轉淺色主題；設定頁改 grid；說明頁書面語化（2026-11-02）

### 狀態
✅ 已採納（用戶需求：litera 配色不美觀 → 要白底黑字；設定頁字細又縮中間；說明頁字級不一致、內容要書面語、CLI 說明不足；undo/redo 要 hint；平移 slider 拆走）

### 背景
1. **原本 UI 全部寫死深色**：`bootstyle="dark"` 73 處 + `theme.py` 深色票（#16161d 等）+
   Canvas 內硬編碼 hex（波形 #2a3a52、字塊 #3b4a63、概覽 #101016…）。
   所以設定頁一選擇 `litera` 就變成「白底殼 + 深色面板」的拼貼感 —— 用戶回報的「不美觀」正是此。
2. **設定頁排版**：一行行 `pack` 加固定窄欄（`anchor="n"`），1920 螢幕下縮成中間一條、
   字只有 9pt。
3. **ttkbootstrap trap**：`light.TFrame` / `light.TLabelframe` 這類 **variant style 是「第一個
   用該 bootstyle 的 widget 建立時」才創建**。啟動時 configure 它們，之後 ttkbootstrap 會用
   自己的預設值覆寫 → 邊框/底色「套了等於沒套」（實測：卡片邊框完全消失）。

### 決策
- `theme.py` 全盤改淺色票：白底（#FFFFFF）、面板 #F6F7F9、邊框 #D3D8E0、文字 #16181D、
  accent #1F6FEB；**新增 Canvas token**（`CANVAS_BG`/`WAVE_FILL`/`BLOCK_*`/`GAP_*`/
  `OVERVIEW_*`/`CODE_FG`），widget 內不再寫死 hex。
- 影片預覽區用 `VIDEO_BG`（#0E0E12）**刻意保持深色**：影片本來就是黑框，白底反而突兀。
- 全 UI `bootstyle="dark"` → `"light"`；`theme.py` 亦一併 configure `dark.*` variant，
  避免殘留舊樣式。
- **`apply_ttkbootstrap_theme()` 於 `_build_pages()` 之後再呼叫一次**（idempotent）：

## ADR-020 · 燒錄音源可換成自備純音樂 MV；AI 去人聲否決（2026-11-02）

✅ 已採納（推翻同日較早的「內建 AI 去人聲」方案；該版 commit `da2fba5` 已 revert）

### 否決依據（保留，避免重蹈）
| 項目 | fast（UVR-MDX-NET-Inst_HQ_3） | quality（BS-Roformer ep317） |
|---|---|---|
| 25 秒音訊分離 | 26–32 s（1.1–1.3× 實時） | 495.5 s（19.8× 實時） |

2. **改為「燒錄音源可換」**：`burn` 的 `-i` 或 UI 對話框可以指向用戶自備的純音樂 MV，
   畫面與音軌都取自該檔，字幕燒在它上面。**CLI 零改動**（`burn -i` 本來就食任何影片）。
3. **燒錄前預警，但不自動修**：

## ADR-021 · 交付打包：VERSION 單一真源 + 鎖定依賴 + allowlist 出包（2026-11-02）

### 背景

## ADR-022 · 版本護欄：打包／推送前檢查 VERSION 有無跟住 code 升（2026-11-02）

### 狀態
✅ 已採納

### 背景
ADR-021 定下「`VERSION` 是版本號唯一真源」，但真源是**人手改**的。同日實測撞板：
另一個對話改好快捷鍵並 commit（`3ea0fa1`），**沒有升 VERSION**；若直接打包就會出
「zip 叫 1.0.0、內容已變、程式自報 1.0.0」——同事回報問題時，你問「跑邊版」他答
1.0.0，你分不清是修之前定修之後。

### 決策
1. **邏輯獨立成 `tools/version_guard.py`**（只讀 git，不改任何檔），兩處共用：
   - `tools/build_release.py`：打包前必跑
   - `tools/hooks/pre-push`：推送前跑（靠 `core.hooksPath=tools/hooks`）
2. **只用 git 事實判斷**：基線 = 最後一次改動 `VERSION` 的 commit；基線之後若有
   commit 改過**非文件**檔案 → 警告。
   **不用** mtime／「隔多久」／commit 數 —— clone、換機、補 commit 都會誤報。
3. **預設只警告**：`--strict` 才 `exit 1`；hook 預設 `exit 0`（要硬擋自行改一行）。
   理由：docs-only 改動、hotfix 試跑不應該被鎖死；真正漏升版時，人眼見到警告就會停手。
4. **忽略清單**：`docs/`、任何 `*.md`、`VERSION`、`.gitignore`、`.gitattributes`。
   `requirements.lock.txt` **不忽略** —— 它會改變同事端的安裝結果，屬交付內容變更。
5. **非 git 環境靜靜跳過**（同事手上的 zip 沒有 `.git`），不應該噴錯阻住流程。

### 踩到的坑（值得記）
- **`git diff --name-only` 會把非 ASCII 路徑輸出成 C 式轉義**（`"docs/\346\236..."`，
  連引號），令 `startswith("docs/")` 失效。本專案 `docs/` 全部中文檔名，沒有處理就會
  誤報「改過程式碼」。修法：`git -c core.quotePath=false`，比對前再 `strip('"')` 保險。
  （由 `tests/test_version_guard.py` 第 6 個 case 抓到，並非靠肉眼。）
- **hook 不能帶 CRLF**：本機 `core.autocrlf=true`，下次 checkout 會把
  `tools/hooks/pre-push` 轉成 CRLF，`sh` 會爆 `$'\r': command not found`。
  → `.gitattributes` 加 `tools/hooks/* text eol=lf`。

### 影響
新增 `tools/version_guard.py`、`tools/hooks/pre-push`、`tests/test_version_guard.py`；
修改 `tools/build_release.py`（匯入 + 打包前檢查 + `--strict`）、`.gitattributes`、`DEPLOY.md`；
本機 git 設定 `core.hooksPath=tools/hooks`（屬本地設定，不入 repo）。

### 驗證
- `tests/test_version_guard.py`：**8 checks ALL PASS** —— 基線通過／未升版只警告／
  `--strict` 擋下／升版後通過／只改 md 不算／只改 `docs/` 不算／改 lock 算／非 git 跳過。
  每個 case 開獨立臨時 repo，不污染本專案。
- 本專案實跑：`[version] OK：VERSION 1.0.1 對應最新 commit`。
- hook 實跑：`sh tools/hooks/pre-push` → rc=0；`git ls-files --eol` 確認 `i/lf w/lf`、
  索引 mode `100755`。
- **真實 push 已驗證（2026-11-02）**：首次推送 `origin/main` 到
  `github.com/hklamsir/karaoke` 時，git 輸出的第一行就是
  `[version] OK：VERSION 1.0.2 對應最新 commit` —— 證明 hook 經 `core.hooksPath`
  正常掛上並執行（原本標記「未實測」，現已補上實證）。
- 附帶學到（值得記）：**fine-grained PAT 的 `permissions` 欄位會誤導** ——
  `GET /repos/{owner}/{repo}` 回 `"push": true` 只代表**帳號**對該 repo 有權，
  不代表 **token** 有 Contents 寫入權。public repo 更甚：匿名都讀得到，`GET` 成功
  完全不能夠當作有權限。
  診斷法：`POST /repos/{owner}/{repo}/git/blobs` 建一個 dangling blob（不會產生
  commit、不改內容）——403 `Resource not accessible by personal access token`
  即證明 token 範圍不足；空 repo 會回 409（代表已過授權層，只是沒有 HEAD 可依附）。

### 修訂（2026-11-03 · v1.0.3）：警告只列真正動過 code 的 commit

**症狀**：只改 `requirements-ui.txt` 一個註解，push 時警告卻寫「之後有 **9 個** commit
改過程式碼」，並列出 8 個純文件 commit（README、ADR）。

**成因**：判定用 `code_changes_since()`（已過濾 docs／`*.md`／`VERSION`），但列印時用的
是 `commits_since()`（基線後**全部** commit），兩者沒有共用同一層過濾。屬訊息層缺陷，
不會誤擋，但會讓使用者漸漸無視警告 —— 護欄一被無視就等於失效。

**修法**：新增 `commits_with_code_changes()`，以
`git log --format=%x01%h%x09%s --name-only <baseline>..HEAD` 一次取回每個 commit 的
改動檔案，逐個套用同一套 `_is_ignored()`，只有含非文件檔的 commit 才列出。
用 `%x01`（SOH）作分隔符 —— git 路徑不可能含此字元，比用空行切更可靠。
`check_version_bump()` 的計數與清單一律改用 filtered 結果。

**已知取捨**：合併 commit 在 `--name-only` 下不帶檔案清單，因此不會被列出；它帶入的
改動已由被合併的個別 commit 反映，實務上不影響判斷。

**驗證**：`tests/test_version_guard.py` 由 8 → **13 checks ALL PASS**，新增 5 條回歸
（混合 commit 只列 1 個、列出正確對象、計數用 filtered 數量、不列純文件 commit、
仍列出真正動 code 的 commit）。本專案實跑由「9 個」修正為「1 個」。

## ADR-024 · 錯誤改用例外階層（KaraokeError 家族）；CLI 退出碼不變（2026-11-03）

### 狀態
✅ 已採納（v1.0.4 之後；與 v1.0.5 一併出包）

### 背景
v1.0.4 之前，所有可預期錯誤都由管線函式直接 `sys.exit(N)`（共 17 處）。三個問題：

1. **與 CLI 綁死**：`main.py` 的函式同時是「可被 UI import 的 API 層」，但 `sys.exit`
   會直接結束進程；UI 只能靠 `except SystemExit` 接，拿到的是 `exc.code` 一個整數，
   完全不知發生甚麼事。
2. **無法分辨**：收到 3 不知是「抽音失敗」定「人聲標準化失敗」；收到 2 不知是
   「缺 ffmpeg」定「缺 API key」。
3. **測試只能斷言 `SystemExit`**：對「錯誤類型」零保證 —— 重構時把 code 由 3 改成 4
   都不會紅（審查報告 §2.9）。

### 決策
新增例外階層，每個 `code` 與舊 `sys.exit(N)` 逐一對應：

| 類別 | code | 觸發點 |
|---|---|---|
| `KaraokeError` | 1 | 基底；亦用於無法歸類者（`code=` 覆寫） |
| `UsageError` | 2 | 缺 API key、禁用 model、輸入／字幕／timings 不存在、壞色碼 |
| └ `ToolMissingError` | 2 | 缺 ffmpeg / ffprobe / audio-separator |
| `AudioExtractionError` | 3 | 抽音、人聲分離、人聲標準化失敗 |
| `AsrError` | 4 | 提交／輪詢／逾時／subtask 全失敗 |
| └ `NoSubtitlesError` | 4 | 沒有 `transcripts`、斷句後零行 |
| `BurnError` | 5 | ffmpeg 燒錄失敗 |

三個取捨（都是刻意，並非順手）：

1. **`UsageError` 是最初契約之外多加的一層**。code 2 有 6 個觸發點，全部屬「用戶改
   設定即可解決」；若用裸 `KaraokeError(code=2)`，callers 無法分辨「用法錯」與
   「未歸類錯誤」，等於白做一層階層。`ToolMissingError` 掛在它下面 —— 同屬 code 2，
   但訊息要教安裝方法，所以獨立成子類。
2. **`NoSubtitlesError` 繼承 `AsrError`，不直掛基底**。兩者成因同屬「ASR 沒有給到可用
   內容」，呼叫方可以只 catch 父類一次過處理，減少分支。
3. **例外訊息只放短句**。詳細 stderr / JSON 仍然由 `LOGGER.error()` 輸出。訊息會
   直接顯示在 UI 對話框，塞 2500 字 stderr 會爆窗；`tests/test_error_taxonomy.py`
   有斷言鎖住「單行、≤120 字」。

轉換層：`main()` 加 `except KaraokeError → return exc.code`。因為每個拋出點仍然先
`LOGGER.error()`，**CLI 的輸出與 v1.0.4 之前逐字相同**，只是不再 `sys.exit`。
UI 兩個呼叫端（`home.py`、`editor.py`）保留 `except SystemExit` 作為第三方套件的
保險，但自家錯誤已改由 `except Exception` 分支顯示可讀訊息 ——
由「exit code 3，詳見 log」變成「ffmpeg 抽音失敗（rc=1），詳見 log」。

### 影響
- `Raises` 由 `SystemExit` 改為上述類別：`generate_timings()`、`burn_video()`、
  `burn_subtitles()`、`find_ffmpeg()`、`find_ffprobe()`、`extract_temp_audio()`、
  `separate_vocals()`、`submit_and_wait_transcription()`、`parse_asr_result()`、
  `resolve_api_key()`，以及 `cmd_burn` / `cmd_render` 的前置檢查。
- **CLI 退出碼完全不變**（2/3/4/5），CI 腳本與同事的 `.bat` 無需改動。
- **UI 錯誤訊息變短且具體**（行為改善，非破壞性變更）。
- `_probe/probe*.py` 若直接呼叫這些函式，失敗時會出 traceback 而不再靜靜 exit ——
  屬本機開發腳本，可接受（未改）。

### 驗證
- `pytest tests -q` → **91 passed / 13 xfailed**（重構前：66 passed / 17 xfailed）
- 4 條契約測試由 `XFAIL` 轉 `XPASS`（strict 機制逼使拆標記，已拆）：
  `AudioExtractionError`、`ToolMissingError`、`NoSubtitlesError` ×2
- 新增 21 條測試鎖住：7 個 `code`、6 條繼承關係、「全部是 `Exception` 並非
  `SystemExit`」、`code=` 覆寫、4 條 CLI 退出碼端到端、1 條訊息長度
- 實機 CLI（獨立進程，非 in-process）：`generate` / `burn` / `render` 缺檔 → exit 2；
  `render` 正常 → exit 0

## ADR-025 · 修復審查報告全部 P0/P1：取消、原子寫入、跨磁碟、UI 防呆、長片記憶體（2026-11-03）

### 背景

`docs/代碼審查報告.html` §11 列出 9 項 P0/P1。其中 3 項已於前一輪處理完（§2.2 測試基建、
§2.7 escape 跳脫、§2.9 `KaraokeError` 家族）。本 ADR 收剩下的 6 項，連同 §9.2 遺留的
兩個契約（9.2-1 全靜音、9.2-12 重複提交）。

6 項的共同點：**失敗時畫面沒有反應**，用戶無從排查 —— 燒錄跨碟直接 traceback、
輪詢鏈默默疊加、Tk callback 內的 `ValueError` 只去 stderr、取消只能殺程式、
長片 OOM、中斷後半截 JSON。所以修法都圍繞「失敗要麼講清楚，要麼不會發生」。

### 決策

#### 1. 取消機制（§2.3 P1 / 9.2-11）

- `TaskCancelled` **刻意不繼承 `KaraokeError`**。若繼承，`main()` 的
  `except KaraokeError → return exc.code` 會把「用戶主動取消」變成非零退出碼，
  即「我不想等」= 「程式出錯」。取消不是錯誤。
- `GenerateOptions.cancel_event` 用 `field(default_factory=threading.Event)`，
  不用 class-level `threading.Event()`。後者會令**所有** options 共用同一個
  Event：取消一次之後，之後每次 generate 一開波就立即被取消（`test_cancel_event_is_per_instance`。
- 檢查點放在：ASR 輪詢**每一圈的最頂**（不是尾部 —— `fetch` 本身可能慢幾秒）、
  各階段之間（抽音／人聲分離／上傳／斷句）、以及**寫檔之前**（避免只寫出 ass
  沒有 json 的半完成產出）。
- 燒錄由 `subprocess.run` 改為 `Popen` + poll 迴圈 + `terminate()`（5 秒不死就 `kill()`）。
  `stderr` 導向**臨時檔**而並非 `PIPE`：poll 期間沒有人讀 pipe，寫滿 64KB 緩衝就會
  死鎖 —— 變成「取消都取消不到」。
- 取消後刪除半截輸出 mp4。刪不到（被播放器鎖住）只記錄警告，**照拋
  `TaskCancelled`**，不可讓 `OSError` 蓋掉取消語義。
- UI 用**獨立**「✖ 取消」按鈕，不用「已經 disabled 的開始按鈕」兼職。誤按代價太大
  （中止一個已經跑了幾分鐘的 ASR 任務），而且 disabled 按鈕本來就收不到點擊。
- `ThumbCache.cancelled` 由死代碼接線：換片時把上一條 `_thumbs_task` 設
  `True`。為此 `PreviewPane` 新增 `_thumbs_task`（`_thumbs` 只在完成後才賦值，
  捕捉不到「正在跑」那個）。

#### 2. 單飛閘（9.2-12）

`main.SingleFlight`：`Lock.acquire(blocking=False)` 保證原子性，取代
`home.py` 的 `_running` 布林旗標。布林旗標是 check-then-act，兩條 thread 同時
讀到 `False` 就會一同過關（TOCTOU），而「重複提交」正是併發問題。

`__exit__` 無條件 `release()`；重複 `release()` 拋 `RuntimeError`（同
`threading.Lock` 一致）—— 靜默成功會令閘門在仍有任務時被放開，防護失效且無徵狀。
`locked` 屬性只供顯示，不參與判斷（Lock 無法原子查詢狀態）。

#### 3. 原子寫入（§2.8 P1）

`main.atomic_write_bytes / text / json`：同目錄 `.tmp` → `os.replace`。
覆寫前留 `.bak`（沿用 UI 既有約定：覆寫後才發現有問題時仍有上一版可救）。

- `ui/models.atomic_write_json` 改為**委派**（延遲 `import main`）。以前 UI 有 `.bak`、
  CLI 完全沒有，兩份實作已經開始分叉。
- 為何不新開 `io_utils.py`：`build_release.py` 的 `TOP_FILES` 是白名單，新增根目錄
  模組若漏加，交付包會 `ModuleNotFoundError`（上一輪 `tests/fixtures/*.json`
  就是同類事故）。等到 PR-2 拆 `karaoke/` package 時再搬去 `karaoke/io.py`。
- 沒有循環 import：`main` 不 import `ui`；`ui.models` 是延遲 import，module 載入時
  不會拉入 CLI。

#### 4. 跨磁碟區 `relpath`（§2.1 P0）

`_rel_or_abs()`：`os.path.relpath` 拋 `ValueError` 時退回 `os.path.abspath`。
只用在 `-i` 與**輸出檔參數**；`-vf ass=<檔名>` 仍然用「`cwd` + 純檔名」（ADR-006），
因為只有 filter 內容才怕 `C:` 的冒號。

`MV 放 D:/、字幕輸出 C:/` 是常見配置，以前直接 traceback —— 屬「特定但常見」。

#### 5. UI 兩個 P0（§2.4 / §2.5）

- `_ensure_polling()` 冪等：旗標 + 只在 `_poll_position` 內自我重排。**引擎消失時必須
  清旗標**，否則鏈條斷了之後永遠不會再啟動（換片後游標不動，另一種 bug）。
- `_adv_int(key, default)` 取代 6 處裸 `int(...)`，並在 `_start_generate` 外層包
  `try/except → messagebox`。Tk callback 內的例外只會去 stderr，用戶見到的是
  「按了按鈕沒有反應」。

#### 6. 長片記憶體（§2.6 P1）

`MAX_PCM_SECONDS = 1800`：超過就只串流掃 peaks（每段 5 秒 = 80000 samples = 1000 bins，
剛好整除 80 samples/bin，最後一段以外無 padding，串接後等同一次過處理），
`_pcm` 清空、`playback_degraded = True`。一小時：peaks 約 2.9 MB，而非 115 MB。

- 為何不用 `pygame.mixer.music` 串流：要重寫 play / seek / loop / play_range 全部
  播放邏輯，而 >30 分鐘的 MV 屬少數。本 ADR 只解決記憶體，不順手改播放架構。
- UI 必須明示「長片模式」（狀態行 + 按播放時的對話框），否則用戶會以為播放壞了。
- `load()` 開頭重設 `playback_degraded = False`：這個是 instance 狀態，換片不重設
  會「一次載過長片，以後全部沒有聲」。

#### 7. 全靜音偵測（9.2-1）

`main.detect_silent_wav()` 用 stdlib `wave` 逐段讀樣本（4 秒一段，門檻 int16=32 ≈ −60 dBFS），
`generate_timings` 命中時 `LOGGER.warning`（**不 raise** —— 全靜音 MV 可能是用戶
刻意測樣式；而 ASR 之後一定回空結果，硬 raise 只會擋死合理流程）。

- 為何不放 `ui/audio.py` 的 peaks 層（報告字面建議）：`generate` 管線根本不 import UI，

## ADR-026 · 逐字時間改用時間碼 + 跨字均分／修補（2026-11-03）

### 問題（用戶實測第 39 句）

1. **AI 漏詞，程式不識補**：ASR 只吐 word 級時間，`word_slot_to_group()`
   （`main.py:968`）只在**詞內部**按字數平分，`estimated=True` 就是這個意思。
   一旦整段詞被漏掉（「那裡保證何時能突破」），呢 8 個字擠在 3:41.995–3:42.958
   （每個 ~107ms），而 `respread_word()`（`models.py:266`）只作用於單一個 word
   內部 —— 跨詞的缺口永遠沒有人填。用戶手動把「破」的結束時間改成 3:53.158
   之後，中間 7 個字仍然原封不動。
2. **存檔時 normalize 反咬**：N4（`models.py:301`）見到 `begin < last_end` 就夾
   返 `begin`，再 `end <= begin → end = begin + 1`，於是重疊字被壓成 1ms，
   看落更似「程式沒有反應」。
3. **純毫秒不人性化**：面板直接顯示 `221995`，用戶要心算「這個字在曲中第幾分
   幾秒」；`editor.py` 明明已經有 `_fmt_ms()`，但只用在狀態列。

### 決策

| 項目 | 決定 | 理由 |
|---|---|---|
| 時間格式 | `3:41.995`（m:ss.mmm；過 1 小時自動 `1:03:41.995`） | 最短、最易讀，左欄無需加闊；`03:41.995` 多佔 10px 沒有額外資訊 |
| 輸入 | `timefmt.parse_time()` 接受 4 種寫法 | 新格式好用，但**純整數仍然當毫秒** —— 舊用戶肌肉記憶不可斷 |
| 編輯行為 | 改一個字只改那個字，另設 `⊞ 均分` / `⊞ 全段` / `✚ 修補` | 自動重攤會覆蓋用戶先前逐字對好的結果；可控性 > 少撳一下 |
| 均分預設 | **保留首末字**，只攤中間 | 用戶的實際流程是「先用耳對好尾字，再攤中間」，錨點是人手量度出來的事實 |
| 修補判斷 | 最長字 > `max(6 × 中位數, 1500ms)` → 整行重攤 | 漏字的真實徵狀是「一堆 107ms 字 + 一個 10 秒字」，逐字判斷捉不到（中間字個個都 > 1ms），只有看分佈先捉得到 |

### 實作

- 新增 `ui/timefmt.py`：`fmt_ms` / `parse_time` / `fmt_span`，**純函數、無 Tk**，
  格式化與解析對稱（`parse_time(fmt_ms(x)) == x`）。
- `ui/models.py`：`iter_flat_chars()` / `flat_index_map()`（跨 `words[]` 的單一
  索引）、`span_plan()`（試算，不改資料）、`redistribute_span()`、
  `repair_plan()` / `repair_line()`、`sync_word_bounds()`；`doc_stats()` 加
  `zero_chars`（時長 ≤ 1ms 的字數）餵狀態列。
- `ui/commands.py`：`RedistributeSpan` / `NudgeChars` / `RepairLine` 全部用
  **行級 snapshot**（跨多個 word 的逐字改動用差量會寫到崩，一行最多幾十字，
  快照成本可忽略）。
- `UndoStack.push()` 改回傳 `bool`：command 可設 `self.noop = True`（例如均分
  沒有位可攤），此時**不入棧、不標髒** —— 否則用戶撳一下沒有反應但「未儲存」亮起。
- `ui/pages/editor.py`：Treeview 改 `selectmode="extended"`；時間欄 64 → 84px；

### 補記（2026-11-05）：箭頭（spinner）要留返

- **症狀**：用戶「逐字編輯的時間旁沒有了 spinner，之前是有的」。上一版把
  `ttk.Spinbox` 換成純 `Entry`，箭頭就消失。
- **為何不可直接用回 `ttk.Spinbox`**：Spinbox 的箭頭本質是「數值 + increment」，
  對 `3:41.995` 會令 Tcl 的 `string is double` 失敗，然後**靜靜如此不做事項** ——
  「有箭頭但撳了沒有反應」比沒有箭頭更難察覺。
- **做法**：新增 `ui/widgets/time_spinbox.py`（Entry + 自繪 ▲▼）。箭頭語意是
  **改一個邊界**（開始欄的 ▲ = 開始時間 +10ms），移動整個字仍然交返「平移」掣，
  兩個動作不搶同一個控制。
- **undo 合併**：連撳 10 下應該是「一個動作」。`EditorState.reapply()` 原地
  重套棧頂 command（`SetCharTiming.new` 換新值），1.5 秒內同一目標不新增步驟；
  同時修正 `SetCharTiming` 只在**首次** apply 記低 `_old_estimated`（否則
  re-apply / redo 之後 undo 還原不返 estimated 旗標）。
- **回呼契約**：`on_step` 回傳**實際套用**的毫秒值（夾過邊界），回傳 `None` 就
  完全不更動輸入框 —— 未選中字時不會出現「顯示 0:00.000 但其實甚麼都沒有改」。
- **驗證**：`tests/test_time_spinbox.py` 9 條（真 Tk，無顯示器自動 skip；
  fixture 用 module scope —— 連續 create/destroy `ttkb.Window` 會令 ttkbootstrap
  的 Style 單例拋 TclError，測試會被靜靜 skip 成假綠）。全套 **166 passed**。

### 補記 2（2026-11-05）：箭頭要用 Canvas 畫，與「連動順延」

**（一）`▲` / `▼` 字元不可靠**

- 用戶實測：「繪畫的箭咀不是 ▲▼ 的樣子」。U+25B2/25BC 在 Windows 會 fallback
  去另一個字型，出到來是實心方塊或者大小走位，同 ttk 按鈕邊框又不夾。
- 改法：`TimeSpinbox` 改用 **Canvas 畫兩個多邊形**（上／下各一，中間一條分隔線），
  闊度 `ARROW_W=15px`、高度跟 Entry 的 `winfo_reqheight()`，並支援 hover 高亮。
  形狀完全自己控制，不受字型影響；亦順便比兩個 `▲`/`▼` 按鈕窄 28px。
- Canvas 不會跟 ttk style 自動變色 → `EditorPage.restyle()` 要叫 `spin.restyle()`。

**（二）改時間撞到鄰字，要不要自動推開？**

用戶提問：「前一個字的結束時間超過下一個字的開始時間，是否要自動把後面所有字
順延？反過來把開始時間拉前，是否要把前面的字向前移？」

- **決定：做，但預設關，由面板「連動」開關控制，並記入 `settings.json`。**
- 為何不預設開：**音軌是事實，字幕只是描述**。自動推開會默默改掉用戶已經用耳
  對好的鄰字（甚至整句），而連鎖推會令整句慢慢偏離音樂；錯了又好難察覺（畫面
  只是數字變了）。預設「只改那個字 + 提示重疊」最安全，要推就自己開。
- 為何仍然要做：漏字、插入字、整句改長度時，逐個字搬是体力活。開關一開就
  一次過推好，而且**一次 push = 一個 undo 步驟**（`SetCharTimingRipple`）。
- 對稱處理：尾邊超出 → `shift_range(i+1..last, +overlap)`；頭邊超前 → `shift_range(0..i-1, -overlap)`。
- 夾邊界：向前推最多推到 0。不夠位就**夾住自己**（`begin = prev_end - 可移距離`），
  寧願拖不到盡，都不要出負時間或者靜靜留低重疊 —— 手感同「拖到牆就停」一致。
- 字距保持：`shift_range()` 整段平移，不重新分配（重新分配是「均分」掣的工作）。
- 提示列會講返實際做了甚麼：「其後順延 +50ms」／「其前前移 -110ms」／
  「⚠ 與鄰字重疊 50ms（開「連動」可自動推開）」。

**驗證**：`tests/test_time_spinbox.py` 加到 13 條（新增連動四條：關閉時鄰字不動、
向後順延、向前前移、推到 0 就停）。全套 **170 passed**。UI 探針量度：時間欄那一行
reqwidth 248px（比用兩個按鈕時少 106px），左欄可用 378px。

## ADR-027 · 雙行歌詞：奇數句固定上行、偶數句固定下行，每行隔兩句才換（2026-11-09）

**狀態**：✅ 已接受

**背景**

用戶要求做到《舊夢不須記》卡拉OK 原片的效果：畫面固定兩行，進入下一句 1 秒後，
「上一句」被「再下一句」取代。逐幀核對原片（1920×1080 / 25fps）確認：

| 時間 | 上行 | 下行 |
|---|---|---|
| 18s | 舊夢不須記（白＝已唱） | 逝去種種昨日經已死（藍＝未唱） |
| 24s | 從前人妙 隨夢境失掉（藍） | 逝去種種昨日經已死（唱緊） |
| 27s | 從前人妙 隨夢境失掉（前半白） | 莫憶風裡淚流怨別離（藍） |
| 33s | 舊事也不須記（藍） | 莫憶風裡淚流怨別離（白） |

即：**上行永遠放第 1、3、5… 句，下行永遠放第 2、4、6… 句**；每句在「下一句開唱
+1000ms」時被同行的再下一句取代。

**決策**

- `StyleConfig` 加 `dual_line` / `switch_delay_ms`（預設 1000）/ `line_gap`（0 = `font_size × 1.45`）。
  三個欄位只在 `dual_line=True` 時寫入 `timings.json`，**單行輸出維持 byte-identical**。
- 每句仍然只產生 **1 個 Dialogue**（不拆兩個 event），用 `\an2` + `\pos(x, y)` 固定行位：
  `y_down = PlayResY - margin_v`、`y_up = y_down - line_gap`。
- 顯示窗口（`_dual_line_window`）：
  `start = 0`（前兩句）或 `lines[i-1].start_ms + delay`；
  `end = lines[i+1].start_ms + delay`（最後一句用 `line.end_ms`）。
- 預覽期（event 早過第一字）用前置 `{\k<gap>}` 佔住時間軸，令 `\kf` 準時啟動 ——
  同 C-5 停頓補償是同一招，只是由「字與字之間」擴展到「行首」。
- UI 預覽 `overlay.draw_dual_subtitle()` 用**同一條窗口規則**，否則編輯器所見非所得。

**為何不拆兩個 event**

一句只在一行出現，event 數同單行一樣（N）。傳統「上下兩行都顯示當前/下一句」的做
法要每句拆兩個 event（2N），先可以在中途換字；這個設計用不著，libass 負擔最細。

**邊界**

- 句距 < `delay`：窗口會 `end <= start` → 把 `start` 移前到 `line.start_ms`，
  **寧願本句遲少少出，都不要同一行兩個 event 疊字**。
- 最後一句沒有「下一句」→ `end = line.end_ms`。
- 編輯器改斷句後，句子索引會整體位移 → 每次 `render` 即時按 `lines[]` 計，**不可寫死**。

**驗證**

`sample_v3.json`（12 句）雙行輸出時間窗與原片一致；1080p 黑底實燒 18/24/27/33 秒
截圖對比，兩行位置、逐字變色、換行時機全部對得上。

## ADR-028 · 上傳／燒錄顯示真實進度，不再只有跑馬燈（2026-11-09）

**狀態**：✅ 已接受

**背景**

用戶回報「上傳到百煉雲／燒錄時均沒有 progressbar，不知何時完成」。診斷出三個**獨立**
原因，任何一個都會造成「沒有進度」：

1. 主頁「進度」框是右欄**最後一個** `pack()` 的 widget，右欄沒有 scroll → Tk 空間不足
   時直接裁走（同 `burn_dialog.py` 踩過的坑一模一樣）。
2. `StageProgress` 對「有 message 的 active 階段」刻意設做 `indeterminate`（跑馬燈）。
3. 上傳同燒錄**根本沒有進度資料源**。

**決策**

| 位置 | 做法 |
|---|---|
| 燒錄 | `ffmpeg -progress <tempfile> -nostats`，poll 迴圈每 0.2 秒讀 `out_time_us`，除以 ffprobe 總時長 |
| 上傳 | 自建 multipart POST（`requests`），file-like 分塊讀取、累加位元組回報百分比；失敗**自動 fallback** 去 `dashscope.Files.upload` |
| UI | `StageProgress.set_fraction(pct)`：餵過真百分比後保持 determinate，不會被同階段的 `report()` 打回跑馬燈 |
| 佈局 | 主頁進度框改 `side="bottom"` **最先** pack，確保永遠可見 |

**理由**

- `-progress` 寫**臨時檔**而並非 pipe：沿用 ADR-025 的教訓 —— poll 迴圈期間沒有人讀
  pipe，ffmpeg 寫滿 64KB 緩衝就會死鎖，連取消都取消不到。
- 自建上傳：`dashscope 2.0.3` 的 `Files.upload` 在 `_upload_form()` 一次
  `content = f.read()` 讀完整個檔才交給 transport，**中間沒有任何回調點**；
  不自己發請求就永遠拿不到真進度。
- Fallback 必要：實測本機代理環境下，大 POST 到 `/api/v1/files` 會在約 23% 被
  `ConnectionResetError(10054)` 斷線，但 SDK 路線（同樣 endpoint）成功 —— 所以
  自建失敗必須靜靜退回，不可令整個 generate 失敗。

**驗證**

- 60 秒黑底片燒錄：收到 17 次進度，2.2% → 100%，文字「燒錄中 0:29 / 1:00（48%）」。
- 真實 212 秒 MV 上傳：4% → 23%（代理斷線）→ 自動退回 SDK 並成功。
- `pytest -m "not slow"`：**170 passed**。

## ADR-029 · 整體時間平移 `shift_ms`，不改 `timings.json` 原始時間（2026-11-09）

**狀態**：✅ 已接受

**背景**

用戶要求「用 480p timings 對 1080p 畫面做整體平移對齊」。實測後發現**兩版其實同步**：

| 錨點 | timings 第一字開始 | 1080p 實際（量紅色填充） | 差 |
|---|---|---|---|
| 第 1 句「舊夢不須記」 | 14.06s | 14.2–14.4s | +0.15s |
| 第 3 句「從前人妙」 | 25.63s | 25.6–25.7s | −0.03s |

差異只有 1–3 幀（25fps）。之前判成「差 1.6 秒」是**預覽方法的錯**：把 `-ss` 放在
`-i` 前面時，ffmpeg 會把輸出 PTS 歸零，ass 由第一句重新播，看起來就像整條時間軸
提前了 —— 這個陷阱要記住。

**決策**

仍然提供整體平移，但**只作用於 render 層**：

- `StyleConfig.shift_ms`（預設 0）；`_shift_lines()` 對所有 `start_ms` / `end_ms` /
  `chars[].begin_ms` / `end_ms` 統一加減，並 clamp 到 ≥ 0。
- 不改 `timings.json` 的原始時間（canonical 不變）；只在非 0 時寫入 json 記住。
- CLI：`render --shift-ms -250`；UI：主頁樣式「整體平移」spinbox（±5000ms，步進 50）。

**理由**

換另一版剪輯的 MV（前奏長度不同）時，用一個固定 offset 微調比逐句改快得多；
保留 canonical 令「換片再對」可以隨時歸零，亦不會污染原始辨識結果。

**驗證**

`tests/test_dual_line.py` 加 3 條（平移、負值 clamp、json round-trip）；
全套 **180 passed**。27 秒實燒：新舊字幕逐字同步（見 `_probe/dual_out/ok_27.png`）。

**教訓**

用 ffmpeg 抽片做字幕預覽時，`-ss` 必須放在 `-i` **之後**（output seek）或改用
`trim` filter；放前面會令 PTS 歸零，字幕由頭播，容易誤判成時間軸偏移。

**狀態**：✅ 已接受

**背景（用戶三個回報）**

1. 「已在對齊設定頂部置中，但字幕仍然燒錄在下方」

## ADR-031 · 歌詞提前顯示上限、倒數圓點、句尾停留新語義（2026-11-11）

**狀態**：✅ 已接受

**背景（用戶四個回報，取自《舊夢不須記》原片對照）**

1. 「在一段長時間無字幕區段，要像原片一樣不要呈現下一句，在歌詞開始時間前 3 秒才顯示」
2. 「無字幕區段進入歌詞前可加入倒數 3 個圓點（每 0.5 秒一點），如同正式 KTV 的效果」
3. 「用戶可以自訂字幕距離底部的 px」
4. 「可自訂預覽窗格的 resolution，使用戶可按輸出 video 的真實解析度預覽」

**根因**

| # | 問題 | 根因 |
|---|---|---|
| 1 | 30 秒間奏提早 30 秒見到下一句 | ADR-027 的雙行窗口 = `前一句 start + 1000ms`，**沒有上限**；單行模式則完全沒有提前顯示 |
| 2 | 沒有倒數提示 | 功能未做 |
| 3 | 底部留白只有滑桿（0–400），打不到準確 px | UI 缺數字輸入 |
| 4 | 預覽假設 1920×1080 並自動填滿窗格 | `_redraw_video()` 寫死 `h * 16 / 9` |

**決策**

- **窗口計算抽出單一真源**：新增 `main.compute_display_windows(starts, ends, *, lead_in_ms, dual_line, delay_ms)`。
  `main.build_karaoke_ass()` 同 `ui/widgets/overlay.py` 都呼叫它 —— 舊版 overlay 自己抄了一份
  `_dual_rows()`，是 ADR-027 講的「所見非所得」隱患，今次一次過消滅。
- **提前顯示上限** `lead_in_ms`（預設 3000）：
  - `lead_in_ms > 0`：`disp_start = max(0, start − lead, 同排上一句的 disp_end)`
  - `disp_end = end_ms + switch_delay_ms`，但**夾住 `starts[下一句]`**（不可拖到人們開唱）
  - `lead_in_ms == 0`：完全走回 ADR-027 舊算法，輸出 **byte-identical**（回歸保障）
- **「換行延遲」語義升級**（用戶明確要求保留）：`lead_in_ms > 0` 時它 = **句尾停留**
  （最後一字後多留多久才清空）。長間奏自然全空，密句自然無縫。
- **倒數圓點** `compute_countdown_dots()`：3 點 × 0.5 秒，即開唱前 `−1.5 / −1.0 / −0.5 秒`
  逐個亮起，最後一點亮到開唱一刻；全部用**唱過色**（用戶指定，不用漸變）。
  - 幾何：字級 `0.40×`、與歌詞行間距 `0.12×`、字距 `0.35×`（用 `\fsp` —— 半形空格在 CJK
    字型太窄，實測三點會黐成一嚿）
  - 位置：目標行**上方**；`\an8`（頂部對齊）上方沒有位 → 改放行下方，永遠不出畫面
  - 只在「完整空白 lead-in」才出（`disp_start ≤ start − 1.5s`）；密句／上一句仍在畫面時不出
- **底部留白**：滑桿 + 精確 px 數字框（0–1000，0 = 自動），共用同一個 `IntVar` 雙向同步。
- **UI**：主頁新增「提前顯示 [3000] ms」「☑ 倒數圓點」；「換行延遲」保留，提示改為「句尾多留」。
- CLI 同步加 `--lead-in-ms` / `--countdown-dots` / `--no-countdown-dots`；
  `ui/clidoc.py` 支援 `BooleanOptionalAction` 的否定 flag（否則「複製等價指令」會靜靜漏掉 `--no-...`）。

**理由**

「下一句何時出現」是觀感問題，不應該由「上一句何時開唱」間接決定；而 KTV 的倒數圓點
本質是「提示即將入歌」，屬輔助資訊，放在歌詞上方就不會同文字爭位。
窗口邏輯只留一份，是避免同類 bug 再出現的根本做法。

**驗證**

- `tests/test_lead_in.py` 新增 14 條契約；`tests/test_dual_line.py` 明確 pin `lead_in_ms=0`
  鎖住舊契約。全套 **208 passed**（含 slow：真實 ffmpeg 燒錄與大數據量）。
- 1280×720 合成片真實 libass 燒錄，逐幀目視（`_probe/lead_in/`）：
  - 3.4s：未唱的歌詞已出現（開唱 6.0s，提前 3.0s）
  - 5.4s：上方 2 粒綠點（第 1、2 點已亮）
  - 6.2s：圓點消失，第一個字開始掃綠

**注意**

- **舊 `timings.json` 打開即變 3 秒提前顯示**（正是需求）。要回到舊觀感：主頁「提前顯示」設 0。
- 圓點顏色固定跟「唱過色」，換色盤會自動跟。

### 補記（2026-11-11 第二次修訂：對齊第一個字、5 秒門檻、燒錄按鈕）

**用戶三個回報**

1. 「小圓點要對齊歌詞第一個字，不是置中」
2. 「小圓點在間隔很短的情況下會出現，改為下一句距離現句最小 5 秒（預設 5 秒，用戶可在主頁設定）」
3. 「燒錄完成後，『取消燒錄』的按鈕仍呈現」

**難題：libass 不對外提供字型度量**

要對齊第一個字，就要知道置中文字由哪裡開始。直覺做法是「字數 × 字級 ÷ 2」，但實測
**同一個字級下不同字型的實際 advance 差好遠**（1280×720，字級 80，量度相鄰字左邊界）：

| 字型 | 每個全形字 advance | ÷ 字級 |
|---|---|---|
| Microsoft JhengHei（未安裝 → fallback） | 53.3 px | 0.67 |
| Microsoft JhengHei UI | 56.1 px | 0.70 |
| SimSun | 80.0 px | 1.00 |
| PMingLiU | 71.1 px | 0.89 |

原因：libass 用字型自身 ascent+descent 換算字級，不是 em。任何單一常數都會令 SimSun
用戶偏左一個字以上 —— 所以**放棄估算**。

**解法：寬度配平（metric-free）**

實測 `●`（U+25CF）與中文字同為全寬：字級 90 時 ● advance 71 px、中文 70.9 px。所以：

- 圓點字級 = `font_size / 3` → **3 粒「●」剛好佔一個全形字位**
- 圓點事件文字 = `「●」×3` + `{\alpha&HFF&}` + **原文去掉第一個字**（隱形尾巴）
  → 總寬度 = 原句寬度（誤差 0，只依賴「advance 隨字級線性縮放」，同一字型必然成立）
- 事件照舊用 `\an2` 同一個 `x`／同一個 y 偏移 → 兩條 event 左邊界完全重合，
  第一粒點自動緊貼第一個字，**不需要任何字型度量**
- 三條 event（1／2／3 粒亮點）**永遠保持 3 粒點**，未亮的用 `{\alpha&HFF&}` 隱形，
  所以亮點增加時總寬度不變、左邊界不會左右跳

實測驗證（1280×720，字級 80，雙行右偏移 +10%）：圓點左邊 **494 px**、文字左邊 **502 px**
（差 8 px ≈ 0.1 字，來自 `\fsp` 字距）；圓點底 519、文字頂 535（淨空 16 px）。

**圓點尺寸的代價**：3 粒點限死一個字位，所以點直徑只能是字級的 1/3（實測 ink ≈ 0.19 字級）。
用戶原話是「**小**圓點」，尺寸偏小反而符合；若要更大就要佔兩個字位，左邊界會偏 0.2 字，故不取。

**5 秒門檻**：新增 `dot_min_gap_ms`（預設 5000，0 = 停用），以「**上一句結束 → 本句開唱**」
的空白計。用「開唱→開唱」計會令連續長句（每句 6 秒、無空隙）誤判為長間奏，所以必須用
「結束→開唱」。主頁「圓點條件」可直接改；CLI 對應 `--dot-min-gap-ms`。

**燒錄完成後「取消燒錄」仍可按**：`worker` 的成功分支只改標題，沒有停用按鈕。現在
成功／失敗／取消三條路徑都經 `_finish_cancel_btn()` 停用並改字
（`✔ 已完成` / `✕ 已失敗` / `已取消`），並吞 `TclError`（視窗可能已被用戶關掉）。

**驗證**：`tests/test_lead_in.py` 由 14 條增至 18 條（對齊不變量、寬度配平、5 秒門檻、
門檻可調、門檻 0）；全套 **213 passed**。真實 libass 燒錄逐幀目視（`_probe/lead_in/`）：
圓點起點對齊第一個字；頂部對齊時圓點落在行下方，同樣對齊第一個字。

## ADR-033 · 以字元為單位斷句：詞組可切分且時間軸保持無損（2026-11-12）

**狀態**：✅ 已接受

**背景**

舊有的 `split_line_at_word()` 只容許在 WordGroup 邊界斷句。使用者在「逝」字執行斷句時，「去」字仍與「逝」字留在同一行，因為兩者屬於同一個由語音辨識產生的詞組；此限制源自「斷句必須以詞為單位」的假設。

**決策**

新增 `split_word_at_char()` 與 `split_line_at_char()`（`ui/models.py:259`、`:306`），並將 `SplitLine` 擴充為接受 `char_i`（`ui/commands.py:132`）。切分時沿用每個 CharSlot 既有的 `begin_ms` 與 `end_ms`，僅重新分配 `chars[]`、`text`、詞組邊界與 `punctuation`；標點一律歸入尾段，因此「標點屬於最後一個字」的不變量維持不變。

**理由**

語音辨識只提供詞級時間，但 `word_slot_to_group()` 已按字數比例為每個 CharSlot 配置獨立的開始與結束時間。既然字元本身已有時間區間，切穿詞組即為無損操作，無需重新估算或插值；強制以詞為單位反而令使用者無法修正辨識結果的斷句錯誤。

**驗證**

## ADR-034 · 空格採單一資料來源：標點衍生空格實體化為真實字元（2026-11-12）

**狀態**：✅ 已接受

**背景**

`display_text()` 舊版以 `re.sub(r"\s+", "", ...)` 全數刪除空白，而「詞尾標點轉半形空格」僅在顯示時即場推導，`chars[]` 中並不存在該空格。結果歌詞樹顯示「逝去種種 昨日經已死」，逐字微調與預覽卻沒有空格；另一方面，使用者刻意輸入的半形空格又被正規化邏輯刪除，形成編輯器與成品不一致。

**決策**

`display_text()`（`ui/models.py:112`）與 `set_line_text()` 改為將連續空白折疊為單一空格並去除首尾，不再全數刪除。新增 `materialize_punct_spaces()`（`ui/models.py:78`）：在下一個詞的 `chars[0]` 插入一個 1 ms 的空格字元，其 `begin_ms` 等於該詞起始時間；`load_doc()` 與 `normalize()` 皆會呼叫，並以 `chars[0]["text"].startswith(" ")` 保證冪等。`main._karaoke_pieces` 亦以相同條件避免重複補空格。

**理由**

空格若只是推導結果，便會出現多個互相衝突的真相來源；將其寫入 `chars[]` 後，歌詞樹、逐字微調、Canvas 疊字與 ASS 燒錄皆讀取同一份資料。使用 1 ms 而非 0 ms，可令該字元在時間軸上仍然具備合法且可視的區間，同時不會對卡拉 OK 逐字著色造成可察覺的影響。

**驗證**

`tests/test_split_and_space.py` 驗證冪等性（重複執行不再插入）、歌詞樹與 `display_text()` 一致、ASS 事件僅含單一空格，以及半形空格在儲存與載入後仍然存在。

## ADR-035 · 預覽字級改用像素單位，與 libass `Fontsize` 對齊（2026-11-12）

**狀態**：✅ 已接受

**背景**

Tk 的字型 `size` 為正數時以點為單位，為負數時以像素為單位；libass 的 `Fontsize` 則是相對於 `PlayRes` 的像素值。舊版預覽以正數傳遞字級，在 96 dpi 下 96 pt 會被渲染成 128 px，令預覽文字比燒錄成品大 4/3，使用者無法以預覽判斷字級與底部留白設定。

**決策**

新增 `pixel_font()`（`ui/widgets/overlay.py:35`），以 `tkfont.Font(size=-px)` 建立字型，並讓 `measure` 與 `create_text` 共用同一 Font 物件；`style_preview.py` 同步改用。快取鍵包含 `id(root)`，並設 64 筆上限與 `TclError` 重建機制，避免舊 root 銷毀後取得失效字型。

**理由**

測量與繪製必須使用同一個字型實例，否則即使單位正確，字寬度量仍會與實際繪製不一致。相較於在應用層換算 dpi，直接使用 Tk 的負值語義是唯一不依賴平台 dpi 設定的做法。

**驗證**

測試以虛假 Font 物件驗證 `size` 為負值，並確認 `measure` 與 `create_text` 使用同一字型實例；相關案例收錄於 `tests/test_split_and_space.py`。

## ADR-036 · 逐字微調限定單字元操作（2026-11-12）

**狀態**：✅ 已接受

**背景**

逐字微調原先只提供斷句與插入字，且插入動作以 WordGroup 索引為依據：選中「去」字執行「字前插入」時，新字會落在「逝」字之前。其後雖加入「修改」功能，但一度容許輸入多個字元，與「一個 CharSlot 對應一個時間區間」的資料模型衝突；此外 `strip()` 會把半形與全形空格清成空字串，令使用者無法以空格製造可見間隔。

**決策**

`_apply_ask()`（`ui/pages/editor.py:1277`）對 `char_edit`、`char`、`char_after`、`char_before` 四種模式一律要求 `len(one) == 1`，其中 `one = raw.strip() or raw`；`set_char_text()`（`ui/models.py:498`）不再 `strip` 或套用正規表達式，因此半形 `" "` 與全形 `"　"` 皆為合法輸入。`insert_char_before()` 先切分目標詞組以確保插入位置正確，行尾加字時將 `punctuation` 移至新的尾詞。`DeleteChar` 在該行僅剩一個字時拒絕執行並引導使用「刪行」。插入時長由 `char_insert_ms` 控制（預設 100 ms，`ui/settings.py:47`），按鈕標籤統一改用 ASCII `+`。

**理由**

此資料模型中每個 CharSlot 承載一組獨立的開始與結束時間；容許多字元輸入會令文字與時間軸的一對一關係失效，亦會使卡拉 OK 逐字著色無法判定應對應哪一段時間。將「修改」與「插入」皆收斂為單一字元後，所有變更皆可用同一組 command 與 undo 機制表達。保留全形空格，是因為使用者需要比半形空格更明顯的視覺間隔，而 `raw.strip() or raw` 可在不影響一般實字輸入的前提下保留純空白字元。

**驗證**

`tests/test_insert_and_lines.py` 覆蓋多字元遭拒、空值遭拒、半形與全形空格可改字與加字、選中字前方插入位置正確、行尾加字後標點歸屬，以及最後一個字不可刪除。

## ADR-037 · 歌詞樹增刪行與新增行的時間區間來源（2026-11-12）

**狀態**：✅ 已接受

**背景**

語音辨識偶爾漏掉整句歌詞，或產生錯誤句子，但舊版歌詞樹只能在既有行上修改，新增行一律附加在尾行之後 3 秒，無法對應歌曲中段的無字幕區段；工具列的重複「斷句」按鈕亦與逐字微調功能重疊。`start` 與 `end` 欄位直接顯示毫秒整數，使用者須自行換算時間位置。

**決策**

工具列改為 `✏ 修改`、`+ 此行前`、`+ 此行後`、`🔗 合併`、`🗑 刪行`，右鍵選單提供同一組操作，並移除重複的斷句按鈕；欄位更名為「開始」與「結束」，值以 `timefmt.fmt_ms()` 顯示為 `1:08.765`。`AddLine`（`ui/commands.py:441`）接受 `at_line_i`，undo 以物件識別比對索引，避免內容相同的行被誤刪。時間軸空白處橫向拖曳可建立範圍（`range_ms()` 與 `clear_range()`，`ui/widgets/timeline.py:224`）；新增行依序採用拖曳範圍、游標所在空白段，最後才回退至尾行後 3 秒，`new_line_ms` 預設 3000 ms 並限制於 200 至 30000 ms。

**理由**

新增行的時間必須由使用者在時間軸上指認，而非由程式假定；拖曳範圍是最直接且可視化的指認方式，游標空白段則可作為未拖曳時的合理推斷。`at_line_i` 與 identity 比對同時解決插入位置與重複內容兩個正確性問題。時間碼顯示沿用 ADR-026 的既定格式，避免編輯器內出現兩套時間表示法。

**驗證**

`tests/test_insert_and_lines.py` 覆蓋此行前與此行後插入、刪行與 undo、相同內容行的索引正確性、拖曳範圍被採用，以及時間碼格式；UI 探測確認工具列與右鍵選單皆可用。

## ADR-038 · 停用 libass 即時預覽，還原縮圖加 Canvas 疊字（2026-11-12）

**狀態**：✅ 已接受

**背景**

為讓使用者預覽最終燒錄結果，曾陸續加入 libass 精確單幀、燒錄成品預覽與滑窗預燒三種模式。精確單幀每次需 0.2 至 0.4 秒，無法跟上播放；改以 rawvideo 串流與滑窗預燒後，字幕渲染與音訊播放仍存在可察覺偏差。兩次迭代皆未能解決聲畫同步，反而增加 `preview_source`、`preview_output_path` 等設定與 Pillow 依賴。

**決策**

移除全部三種模式，`ui/widgets/preview.py` 還原為單一「原片縮圖加 Canvas 疊字」預覽，即 ADR-032 之前的既有行為。保留「換原片…」：`reassign_video()` 更新 `timings.json` 的 `source.video`，`reload_source()` 與 `_start_thumbs_for()` 重抽縮圖，`on_video_changed` 通知編輯器重載音訊與波形，時間軸資料不變。`ui/settings.py` 移除 `preview_source` 與 `preview_output_path`，`requirements-ui.txt` 移除 Pillow；worker thread 的 `after(0, ...)` 回呼統一經 `_ui_call()` 包裹。

**理由**

近似但流暢的預覽，較「聲畫不同步但聲稱精確」的預覽更具可用性；後者會令使用者誤以為時間軸本身有問題。準確度改以最終燒錄成品為唯一依據，並在 README 明確標示此限制。`_ui_call()` 則解決 worker thread 在視窗關閉或 mainloop 尚未建立時呼叫 `after()` 所引發的 `RuntimeError`，此修正與預覽模式精簡一併保留。

**驗證**

`git diff` 對比確認 `preview.py` 僅保留「換原片…」、`reload_source()`、`_start_thumbs_for()`、`_ui_call()` 與 `on_video_changed`；掃描 `preview_source`、`_exact_`、`_pre_`、`PRE_FPS`、`_live_`、`on_is_playing`、`play_state` 皆無殘留；全套測試 251 passed，UI 探測全綠。

## ADR-039 · 雙行行距改以倍數設定，純音檔加背景合成（2026-11-12）

**狀態**：✅ 已接受

**背景**

雙行歌詞的行距自 ADR-027 起固定為「`font_size × 1.45`」，只寫入 `timings.json` 的 `line_gap`，主頁樣式面板沒有任何控制項。使用者反映 1.45 偏鬆，希望把兩行壓得更密，但無法在不直接改 JSON 的情況下調整；若改為以像素輸入，換字級時行距不會跟隨，視覺比例會失衡。

另一方面，匯入流程只接受影片檔。`probe_has_video()` 與 `compare_sources()` 都會擋住純音檔，`burn_subtitles()` 亦以 `-c:v libx264` 直接編碼來源畫面。若使用者手上只有歌曲的 mp3 或 wav，即使語音辨識、斷句、字幕渲染全部可行，仍無法產出成品。

**決策**

一、`StyleConfig` 新增 `line_gap_ratio: float`，與既有 `line_gap: int` 並存。`resolved()` 的優先序為 `line_gap`（px）→ `line_gap_ratio`（倍數）→ 1.45 舊公式；`main.py:520`、`ui/widgets/overlay.py:66`、`ui/widgets/style_preview.py:123` 三處使用同一條規則。主頁「樣式」面板於「換行延遲」與「上行位置」之間加入「雙行行距」列，以 `DoubleVar` 綁定 Spinbox（`format="%.2f"`、`increment=0.05`）與 Scale，範圍 1.00 至 2.50，預設 1.45；Scale 的 `command` 自行吸附至 0.05 級距。倍數低於 1.10 時提示改為「貼近，可能疊字」。`style_snapshot()` 同時輸出 `line_gap_ratio` 與 `line_gap: 0`，後者是為清除舊 `timings.json` 內既有的 px 值，否則 px 優先會令面板調整無效。CLI 補上 `--dual-line` 與 `--line-gap-ratio`，`render --sync-style` 一併支援覆寫。

二、主頁來源對話框的 `VIDEO_PATTERNS` 加入 mp3、wav、m4a、flac、aac、ogg，且**影片與音檔放在同一個 filter**（`影片及音檔`），而非分成兩個 filter。`_probe_video()` 先以 `probe_has_video()` 判斷，純音檔顯示「音檔（無畫面）· 時長 · codec · 燒錄時用背景合成」，不再誤報 1920×1080。`generate_timings()` 在無視訊軌時把 PlayRes 固定為 1920×1080，並於 `source` 寫入 `source_has_video: false`。

三、新增 `main._burn_base()` 專責組裝燒錄命令，`burn_subtitles()` 與 `burn_video()` 接受 `background` 參數。三條路徑：有視訊軌時維持原命令且不加 `-map`；純色以 `-f lavfi -i color=c=0xRRGGBB:s=WxH:r=25` 產生畫面；圖片以 `-loop 1 -framerate 25 -i cover.jpg` 為輸入，`cover` 用 `scale=W:H:force_original_aspect_ratio=increase,crop=W:H`，`contain` 用 `force_original_aspect_ratio=decrease` 加 `pad`，補邊色取背景色。`ass=` 一律置於 filter chain 最後。畫面來源為無限長時以 `-t <時長>` 封頂，讀不到時長則退回 `-shortest`。`burn_dialog` 新增「背景」區塊（純色色塊加檢色器、自選圖片、填滿或完整），只在來源無視訊軌時顯示；`ask_burn_source()` 的回傳值由 `Path` 改為 dict，`compare_sources()` 對純音檔回傳可用並附警告。對話框原「燒錄音源」標題改為「燒錄來源（影片或音檔）」，主按鈕由「選擇音源…」改為「選擇影片／音檔…」——「音源」在中文語境專指聲音，用作統稱會令使用者以為只可揀音檔。

**理由**

倍數而非像素，是因為行距的視覺意義本來就是字級的函數；以倍數表達後，換字級時比例自動保持，使用者只需決定「鬆緊」一個維度。保留 px 欄位並使其優先，可讓既有 `timings.json` 在升級後輸出不變，符合本專案一貫的向後兼容原則。

背景合成選擇由 ffmpeg 而非預先生成一張靜態影片，是因為 `-loop 1` 與 `lavfi color` 都不需要額外磁碟空間與前置步驟，且 `-t` 可直接以音軌時長封頂。純音檔固定 1920×1080 而非沿用「上次影片解析度」，是為了讓同一首歌每次匯入都得到相同座標系，避免字幕大小在無預警下改變。

影片與音檔合併為單一 filter，是因為 Windows 開檔對話框只會預設顯示第一個 filter；若分成「影片」與「音檔」兩項，使用者必須自行拉下拉選單才見到 mp3，實測會誤以為程式不支援音檔。同理，燒錄對話框改用「影片或音檔」而非「音源」統稱，是避免語意誤導，而非單純措辭偏好。

**驗證**

`tests/test_line_gap_ratio.py` 十項覆蓋預設值、倍數隨字級縮放、px 優先、`resolved()` 冪等、`timings.json` 往返、缺鍵時不新增欄位、壞值回退，以及倍數確實改變 `\pos` 的 y。`tests/test_burn_background.py` 七項覆蓋有視訊軌命令不變、純色 lavfi 輸入、`-shortest` 退路、圖片 `cover` 與 `contain` 的濾鏡次序、未揀圖片時退回純色、缺圖拋 `BurnError`，以及路徑保持相對。`tests/test_burn_dialog.py` 的音檔測試改為斷言「可用且附背景警告」。全套測試 268 passed。

端到端以 5 秒正弦波 wav 實測：純色背景輸出 1920×1080 h264 加 aac，抽取畫面確認字幕燒入且背景色正確；圖片背景以 1280×720 測試圖驗證填滿無黑邊；mp3 來源走 `-c:a copy` 分支成功。UI 探測確認「雙行行距 1.45 × 字級 = 139px（96 字級）」顯示正確，排版無重疊。

## ADR-040 · 行邊界跟隨逐字時間改動（2026-11-12）

**狀態**：✅ 已接受

**背景**

使用者在逐字微調面板以「−100 / −10 / +10 / +100」平移選取的字之後，歌詞樹的「開始」與「結束」欄仍停留在舊時間，必須切換行或重新開檔才更新。時間軸上的行寬亦同樣過時。

檢查後確認問題不在刷新機制：`ui/state.py` 的 `push()` 會 `notify("edit")`，`LyricTree._on_state_change()` 收到 `edit` 即重建整棵樹，逐字微調面板本身亦已正確顯示新的逐字時間。真正原因是 `ui/models.py` 的 `sync_word_bounds()` 只把 `word["begin_ms"]` / `word["end_ms"]` 由首尾 char 推導，**從未改動 `line["start_ms"]` / `line["end_ms"]`**，而歌詞樹與時間軸顯示的正是行邊界。

**決策**

`sync_word_bounds()` 在更新 word 邊界之後，一併以**差量**移動行邊界：以「同步前的 word 邊界」對比「同步後的 char 值」，得出首字 begin 與尾字 end 的位移，再把同一位移套用到 `line["start_ms"]` 與 `line["end_ms"]`（下限夾 0）。因為所有改動字時間的命令（`NudgeChars`、`SetCharTimingRipple`、`RedistributeSpan`、`shift_range`、`repair_line`）都會呼叫此函式，一處修正即覆蓋全部路徑。

**理由**

不直接把行邊界重推為「首字 begin / 尾字 end」，是因為 `line["end_ms"]` 通常已含句尾 hold：`normalize()` 的 N3 會把 `hold_ms`（預設 300，實測作品常見 500）加在最後一個字之後。重推會靜默吞掉這段停留，令每句結尾提早清空——比原本的顯示過時更難察覺。

差量的比較基準必須是**舊的 word 邊界**而非舊的 char 值：呼叫者的次序一律是「先改 char，再叫 sync」，此時 char 已是新值，只有 word 仍停留在舊值，這個差才是本次改動量。若誤用 char 作基準，差量恆為 0，等於沒有修正（此點在實作時已踩過一次，測試已鎖住）。

只改動中間字時，首尾 word 的差為 0，行邊界原封不動，因此對「改中間字」的呼叫者沒有副作用。行與行重疊的情況不在命令層收口，仍交由 `normalize()` 的 N5 在存檔時裁剪，與逐字時間本身容許短暫重疊的既有行為一致。

**驗證**

新增 `tests/test_line_bounds_sync.py` 十二項，覆蓋平移尾字改行 end、平移首字改行 start、只改中間字不動行邊界、首字推到負數時行 start 夾 0、句尾 hold 保持 500ms、首尾同時選中、undo 完整還原（比對整份 doc）、連動順延改行 end、全段重攤在端點不變時不動行邊界、改一行不影響另一行，以及 word 邊界推導的原有職責不受破壞。

UI 實測以真實 `timings.json` 載入編輯器，對第 2 行尾字 push `NudgeChars(…, -100)`：行 `end_ms` 由 22700 變 22600，歌詞樹該行即時由 `0:22.700` 變 `0:22.600`，估算標記由 `●4` 降為 `●3`（人手校過會清 `estimated`），無需切換行。全套測試 280 passed。
