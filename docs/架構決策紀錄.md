## ADR-001 · `-l yue` 內部重映射為 `language_hints=['zh']`

**狀態**：✅ 已接受（2026-10-29）

**背景**
原規格書假設 `-l yue` 可以指定粵語識別。實測發現呢個假設唔單止錯，而且**反效果最嚴重**。

**決策**
`--language yue` **唔會**把 `yue` 傳畀百煉。程式內部統一重映射為 `language_hints=['zh']`，並喺 log 明確印出：
```
[warn] 已將 --language=yue 重映射為 language_hints=['zh']（見 ADR-001：yue 會觸發粵語→普通話轉寫）
```
其餘語言碼（`zh` / `en` / `ja` …）原值直傳。

**理由（實測）**
同一段粵語音源（ground truth：`我哋今晚一齊去食飯啦，你唔好唔記得帶埋個銀包。`）：

| `language_hints` | 輸出 | 粵語口語字 | 粒度 |
|---|---|---|---|
| 唔傳（auto） | `我们今晚一起去吃饭啦，你不要不记得带个钱包。` | ❌ 全蒸發 | 詞級 |
| **`['zh']`** | **`我哋今晚一齐去食饭啦，你唔好唔记得带埋个银包。`** | ✅ **全保留** | ✅ **18/21 字級** |
| **`['yue']`** | `我们今晚一起去吃饭啦，你不要不记得带上个钱包。` | ❌ **全蒸發** | 詞級 |

`yue` 喺呢個 API 嘅實際語義係「**識別粵語，但輸出規範普通話書面語**」，等同於要求模型做方言轉寫。
另外：官方 `language_hints` 語言碼清單亦**根本冇 `yue`**（只有 `zh en ja ko vi th id ms tl hi ar fr de es pt ru it nl sv da fi no el pl cs hu ro bg hr sk`）。

**被駁回的選項**
- **粵語自動改用 `fun-asr`**（官方唯一明文支援粵語）— 實測 fun-asr 確實正確輸出粵語（19/21 字級），但冇 `usage` 字段、`confidence` 尺度唔同，要雙軌處理。列為後備 model，唔做自動切換：**自動切換會令 `--model` 參數失去決定性，對教學場景係災難**。
- **argparse 層面拒絕 `yue`** — 對香港用戶最唔友善，佢哋唔會理解點解「粵語唔畀揀粵語」。

**後果**
- 代價：`--language` 的語義唔再係「原值轉發」，code 必須有 mapping table。
- 好處：用戶打 `-l yue` 得到正確嘅粵語歌詞，而唔係一堆普通話。

## ADR-002 · 唔傳 `enable_words` 與 `enable_itn`

**狀態**：✅ 已接受（2026-10-29）

**背景**
原規格書要求「必須開啟 `enable_words=True`」同埋「`enable_itn=False` 避免數字被轉阿拉伯數字」。兩者**都唔存在於本 model**。

**決策**
提交轉寫任務時**只傳** `model` / `file_urls` / `language_hints`（視情況）。其餘參數一律不傳。

**理由（實測）**
- 官方文件中 `enable_words` **只屬於 `qwen3-asr-flash-filetrans`**。本 model（`Qwen-Audio-3.x-ASR-Flash-Filetrans`）嘅時間戳係「**永久開啟、不可關閉**」，而 word-level **本來就自帶**。
- `enable_itn` 只存在於 `qwen3-asr-flash` 的 **OpenAI 兼容模式** `asr_options`。
- 實測：傳 `enable_words=True` / `enable_itn=False` **冇報錯亦冇可觀測差異**（both 200 OK，`words[]` 照樣有）。
- 唔傳嘅好處係**減少對未文件化參數的依賴**：呢啲參數今日被靜默忽略，聽日可能變成 `400 InvalidParameter`。

**後果**
- 數字歌詞點樣呈現由模型決定，我哋控制唔到（原規格書想解決嘅問題仍然存在，但**無解**，唔係我哋唔做）。
- code 更簡單、更抗 API 變動。

## ADR-003 · 本地音頻上傳走 `Files.upload → Files.get()` 預簽名 URL

**狀態**：✅ 已接受（2026-10-29）

**背景**
Filetrans 模型唔收本地路徑，必須先上傳。原規格書建議用 `oss://` + `X-DashScope-OssResourceResolve` header。

**決策**
主路線：
```python
up   = dashscope.Files.upload(file_path=wav, purpose="assistants")
fid  = up.output["uploaded_files"][0]["file_id"]
url  = dashscope.Files.get(file_id=fid).output["url"]   # 預簽名 https URL
if url.startswith("http://"):
    url = url.replace("http://", "https://", 1)
```
後備路線（`Files.get()` 失敗時）：`OssUtils.upload()` + `Transcription.async_call(..., headers={"X-DashScope-OssResourceResolve": "enable"})`。

**理由（實測）**
四種做法全部試過：

| 做法 | 結果 |
|---|---|
| `file://C:\...` 直塞 `file_urls` | ❌ `DECODE_ERROR` |
| 裸絕對路徑 | ❌ `REQUEST_INVALID_FILE_URL_VALUE` |
| `oss://...`（**冇** header） | ❌ `REQUEST_INVALID_FILE_URL_VALUE`（13.8s 後 FAILED） |
| `oss://...` + `OssResourceResolve` header | ✅ SUCCEEDED |
| **`Files.get()` 預簽名 https URL** | ✅ **SUCCEEDED（唔使額外 header）** |

⚠️ **陷阱**：`dashscope.Files.upload()` 返 200 但淨係畀一個 `file_id`，**唔係**可以直接餵畀 ASR 嘅 URL；必須再 `Files.get()` 拎 `url` 字段。
⚠️ 預簽名 URL 有 `Expires` 參數（實測約 7 日有效），必須「上傳即提交」，唔好 cache。

**後果**
- 主路線唔依賴任何未公開嘅 header，SDK 升級更穩。
- 需要兩次 API call（upload + get）而非一次。

## ADR-004 · 永久禁用 `paraformer-v2`（假時間軸）

**狀態**：✅ 已接受（2026-10-29）

**背景**
為咗搵「粒度最幼」嘅 model，測咗成個 model 清單。`paraformer-v2` 表面數據**最好**，實際上係最差嘅選擇。呢條決定特別記低，因為**下一個人好大機會會再揀佢**。

**決策**
唔准用 `paraformer-v2`（或任何 paraformer 變體）黎產生卡拉OK 時間軸。code 層面加 assertion log。

**理由（實測）**
粵語測試音源（21 個有效字）：

| 指標 | `paraformer-v2` | (`qwen-audio-3.1 + zh` 對照) |
|---|---|---|
| WordSlot 數 | **21（看似完美 100%）** | 18（86%） |
| 每個 duration | `244, 245, 245, 245, 244, 245, …` | `120, 240, 280, 320, 200, 120, 200, 280, …` |
| **duration 唯一值數量** | **2** | **7** |
| word 間 gap | **全部 0** | 有非零值 |
| 起始時間 | **0 ms**（實際語音 280 ms 先開始） | 280 ms |
| `confidence` 字段 | **冇** | 有 |

→ 係**均勻線性插值**，唔係聲學對齊。仲衰嘅係佢**冇句子內部停頓**：實測 ground truth 兩句之間有明顯停頓，paraformer 當冇到。

**後果**
用佢做出嚟嘅卡拉OK 會係**機械等速掃過**，完全唔跟歌手節奏，而且因為冇 gap，字幕永遠唔會喺停頓位停低。

## ADR-005 · ASS 時間戳統一格式為 `H:MM:SS.cc`，並集中於單一 helper

**狀態**：✅ 已接受（2026-10-29）

**背景**
開發期間踩過一次：時間戳寫成 `M:SS:cc`（如 `0:00:28`），ffmpeg 冇報錯退出，淨係喺 verbose log 印咗兩行 `Bad timestamp`，然後**輸出一條完全冇字幕、而且 md5 同輸入完全一樣嘅 mp4**。

**決策**
- 全專案只准有一個 `ms_to_ass_time()` helper，格式 `"{h:d}:{m:02d}:{s:02d}.{cs:02d}"`（例：`0:00:00.28`）。
- 分鐘與秒**必須兩位數**，毫秒位必須用小數點分隔。
- ms → cs 嘅換算（`max(1, round(ms/10))`）亦只准有一個 helper。

**理由**
1. ASS 規範硬性要求 `H:MM:SS.cc`。寫 `0:00:28` 時 libass 會解讀成「28 秒」，導致 event 時間錯位。
2. **失敗模式極度隱蔽**：ffmpeg exit code 0、輸出檔案存在、size 正常，淨係冇字幕。肉眼驗收先會發現，自動化測試唔 check frame content 就過咗。

**後果**
- 所有時間運算集中喺兩個 function，改算法淨係改一處。
- **要求**：任何改動呢兩個 helper 嘅 PR，必須附「抽 frame 目視驗證」嘅證據（对比 `_probe/burn test dir/frame_C_*.png`）。

## ADR-006 · ffmpeg 燒錄：切 cwd + 相對路徑 + `original_size`

**狀態**：✅ 已接受（2026-10-29）

**背景**
原規格書已預警 `ass=` filter 嘅路徑跳脫問題。實測確認存在，而且爆法好具體。

**決策**
1. **永遠唔好**把路徑直接寫入 `-vf ass=<path>`。改為：設 `subprocess.run(..., cwd=<ass 檔案所在目錄>)`，filter 只寫 `ass=<檔名>`；輸入影片用 `os.path.relpath()` 轉相對路徑。
2. ffmpeg 命令**必須**帶 `original_size=WxH`；同時 ASS 檔嘅 `PlayResX/PlayResY` 由 **ffprobe 讀取原片**填入，唔准寫死。

**理由（實測）**
```
$ ffmpeg -vf "ass=C:\Users\pslam\...\burn test dir\karaoke.ass"
[Parsed_ass_0] Unable to parse "original_size" option value
               "UserspslamDocumentsAgents_workspaceskaraoke_probeburn test dirkaraoke.ass"
               as image size
→ rc = 4294967274
```
Windows 路徑嘅 `C:` 冒號被 ffmpeg 當成 **filter option 分隔符**，路徑被切成兩段。目錄入面嘅**空格**進一步惡化。
切 cwd + 相對檔名 → 立即成功。

`original_size` 嘅必要性：libass 需要知道原片尺寸，先至可以用正確比例擺放字幕；唔加會喺輸出 canvas 與輸入尺寸不一致時走位。

**後果**
- `subprocess` call 必須帶 `cwd=`，而且 input path 要 `relpath` — 呢個約束要寫喺 function docstring。
- 需要先跑一次 `ffprobe` 拎解像度（多一次 subprocess call，可接受）。

## ADR-007 · 歌詞校正必有「字數鎖」，且思考模式必須 ON

**狀態**：⚠️ **已被 ADR-012 取代**（2026-10-29）——歌詞校正整體由 CLI 移除。
本 ADR 保留作歷史紀錄，其實測結論（思考模式係字數鎖必要條件）仍然有效，
若日後要重新引入校正功能，請先讀本 ADR 再讀 ADR-011 / ADR-012。

**背景**
用戶要求加入 LLM 歌詞校正（用百煉 `qwen3.8-27b`）。風險係：LLM 改寫歌詞後**字數改變**，會令所有 CharSlot 嘅時間軸失去對應關係。

**決策**
1. **字數鎖係鐵律**：校正後每行字數必須 `==` 校正前。**由程式驗證，唔係靠 prompt 保證**。
2. **驗證失敗 → 棄用校正結果，原地退回 ASR 原文**，並 warn log。（寧願歌詞有錯字，都唔可以令時間軸錯位。）
3. **思考模式必須保持 ON**。`enable_thinking=False` 喺本專案係**[禁用]**。
4. 預設 model = **`qwen3.8-flash`**；`qwen3.8-27b` 保留為 `--correction-model` 進階選項。
5. 以**批量**（每行 `N|原文（X字）`）發送，行號對齊輸出。

**理由（實測，同一份 6 行測試歌詞）**

| model | thinking | 用時 | 字數鎖 |
|---|---|---|---|
| `qwen3.8-27b` | ON | 134.6 s（22.4 s/行） | ✅ 6/6 |
| `qwen3.8-27b` | OFF | 2.9 s（0.5 s/行） | ❌ **5/6** |
| **`qwen3.8-flash`** | **ON** | **51.9 s（8.6 s/行）** | ✅ **6/6** |
| `qwen3.8-flash` | OFF | 2.5 s（0.4 s/行） | ❌ **5/6** |

→ **思考模式係守住字數鎖嘅必要條件**。關思考快 ~60 倍，但會數錯字數（實測把「其实我好想你知道我一直都在这里等你」改成少咗字）。

校正質素實測結果（正確）：
`我们→我哋` / `已经→已經` / `光竟→光景` / `不要说话→唔好講嘢` / `在这里→喺呢度` / `天塌下来→天塌落嚟`

**被駁回的選項**
- **唔鎖字數、校正後重新分配時間軸** — 本末倒置：重新分配就係重新引入估算誤差，抵消咗 ASR 時間軸嘅價值。
- **用 `fun-asr` 嘅 `confidence` 做門檻代替 LLM** — confidence 只能話你低信心，唔會話你應該改成咩字。

**後果**
- 一首 40 句嘅歌，校正階段約需 `40 × 8.6s ÷ 併發數`。**必須做並行分批**（ADR-007 後續：預設 batch=6 / workers=4），並顯示進度。
- 呢個係全 pipeline 最慢嘅一步，要有 `--no-correction` 開關畀用戶跳過。

## ADR-008 · 處理管線次序：OpenCC 押後到最後一步

**狀態**：✅ 已接受（2026-10-29）

**背景**
直覺做法係「ASR 一出就跑 OpenCC 轉繁體」。實測發現咁做會被後面嘅步驟破壞。

**決策**
固定次序，唔准調亂：
```
ASR → 字數鎖校正（LLM）→ 拆字（WordSlot→CharSlot）→ OpenCC s2hk → 斷句 → 生成 ASS
```
理由分層：
1. **校正必須喺拆字之前** — 字數鎖係以「行」為單位；拆完字再改就無從保證字數對應。
2. **OpenCC 必須喺 LLM 之後** — LLM 輸出**繁簡混雜**，實測：`我哋遊過當晚漆黑嘅海港`（前半繁、後半簡）。OpenCC 做最後一道**正規化閘門**，保證落地前全部係港式繁體。
3. **`config` 固定係 `s2hk`**，唔用 `s2twp`（差異：`裏vs裡`、`説vs說`、`着vs著`），亦**唔用 `t2hk`**（實測 `t2hk` 對本專案輸入反而輸出簡體，行為反直覺）。

**理由（額外）**
- OpenCC `s2hk` 喺 53 個測試詞上 **0 個長度變化**（如 `里面→裏面`、`干什么→幹什麼`），**唔會破壞字數鎖**，所以放最後安全。
- ⚠️ 但注意：字數鎖嘅驗證必須**喺 OpenCC 之前**用「同一個基準」做（LLM in vs LLM out），唔可以跨 OpenCC 比較。

**後果**
- OpenCC 只跑一次（對最終 CharSlot），效能最好。
- 若日後加新嘅文字變換步驟，必須插入呢條 chain 嘅正確位置並更新本 ADR。

## ADR-009 · 輸出規格固定：mp4 / libx264 crf18 medium / `-c:a copy`

**狀態**：✅ 已接受（2026-10-29）

**背景**
目標用戶係香港社福界同工（課堂環境、設備參差）。輸出規格要「一定播到」。

**決策**
- 輸出容器**一律 `.mp4`**，檔名 `<原檔名>_karaoke.mp4`（即使輸入係 `.mkv` / `.mov`）。
- 視頻：`-c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p`。
- 音頻：**`-c:a copy`**（原規格書要求保留原聲軌 + 加速）。**若失敗則降級** `-c:a aac -b:a 192k` 並 warn。
- 解析度、幀率**跟原片**（唔縮不放）。

**理由（實測）**
- `-vf ass=` **必然導致 video re-encode**，`-c:a copy` 只對音頻有效 — 所以「保持原片畫質」實際上係「以 crf18 接近無損重編」，要講清楚。
- crf 18 / preset medium 係「接近無損 + 可接受編碼時間」的平衡點，對 4-12 小時課程嘅示範 MV 長度（3-5 分鐘）綽綽有餘。
- 遇到 mkv 常見嘅非 mp4 相容音頻編碼（eg. 某些 PCM / Vorbis），`-c:a copy` 會失敗 → 必須有降級路徑。

**被駁回的選項**
- **保留原容器**（mkv 出 mkv）— 社福界設備參差，mkv 唔係部部播到。
- **NVENC 硬體加速** — 用戶機器唔一定有 N 卡，要寫 fallback，複雜度換唔到確定性收益。日後可加做 `--hwaccel` 可選 flag。

**後果**
- 實現上要根據 ffprobe 結果決定音頻 codec，唔可以無條件 copy。

## ADR-010 · 重依賴一律「懶安裝 + 友善提示」

**狀態**：✅ 已接受（2026-10-29）

**背景**
`--separate-vocals` 需要 AI 人聲分離（`audio-separator` / `demucs`），呢啲會拖入 `torch` / `onnxruntime`，體積以 GB 計。而本工具嘅用戶係課堂環境嘅社福界同工。

**決策**
- `audio-separator` **唔入** `requirements.txt`。
- 基礎 `requirements.txt` 只放：`dashscope`、`requests`、`python-dotenv`、`opencc-python-reimplemented`、`openai`。
- 用到 `--separate-vocals` 時先 `importlib.util.find_spec("audio_separator")` 檢查；冇裝就**印出具體安裝指令**並乾淨退出：
  ```
  [error] 未偵測到 audio-separator。請先執行：
          pip install audio-separator
      （人聲分離會額外安裝 onnxruntime，約需 500MB～2GB 磁碟空間）
      （唔用人聲分離可改用 --separate-vocals 以外嘅預設模式）
  ```
- 同理適用於未來任何重依賴。

**理由**
一般 `--separate-vocals` 係**可選強化**：背景音樂強烈時先用。基礎用戶（八成以上）裝唔到 GB 級依賴。
另外實測已知：`qwen-audio-3.1 + language_hints=['zh']` 喺**冇人聲分離**嘅情況下，對純人聲 TTS 嘅粵語識別已達 21/21 全中 —— 人聲分離並非常必需。

**被駁回的選項**
- **直接寫入 `requirements.txt`** — 對課堂環境係災難。
- **改成 `extras_require`（`pip install -e .[vocals]`）** — 標準做法，但要改成完整 package 結構（`pyproject.toml`），放棄「單一 `main.py` 拎去就用」嘅簡單交付，同課程教材嘅定位唔夾。

**後果**
- 「懶依賴」嘅錯誤訊息必須寫清楚安裝指令同磁碟空間，否則用戶會卡死。

## ADR-011 · 歌詞校正改為「保留原文語體」，禁止書面語⇄口語互相改寫

**狀態**：✅ 已接受並實作（2026-10-29，真實 MV 端到端實測後修訂 ADR-007）

**背景**
ADR-007 定落嘅校正 prompt 第 4 條係「輸出繁體中文，用香港粵語口語字（嘅、佢、唔、哋、咗、係、喺、諗、睇）」。
初版喺 edge-tts 朗讀語料上測試表現良好（`我们→我哋`、`光竟→光景`），但**嗰份測試語料全部係粵語口語**。真實 MV 一上場就出事。

**測試條件（首次真實歌唱場景）**
- 素材：林家謙《普渡眾生》（電影《破．地獄》主題曲）MV，1920×1080 / AV1 / 60fps / AAC / 180 秒
- Ground truth 歌詞：239 字（取自百度百科、Shazam、官方 MV 描述三方交叉驗證）
- ⚠️ **關鍵：呢首歌嘅原詞係標準書面語**（`輪迴塵間的人`、`徘徊來生的往生`），**唔係**粵語口語

**決策**
1. 校正 prompt 第 4 條改為：**只修正語音識別造成嘅同音／近音錯字；原文係書面語定口語，必須原樣保留**，
   並逐項列明禁止嘅轉換（`的↛嘅` `不↛唔` `這↛呢` `來↛嚟` `給↛畀` `了↛咗` `還↛仲`）。
2. ASR 片尾嘅**單字雜訊殘句直接丟棄**（實測吐出過 `"用。"`）。

**理由（實測，同一份 ASR 結果、同一 model、只換 prompt）**

| 策略 | 相似度 | 正確字數 | Δ vs 唔校正 | 用時 |
|---|---|---|---|---|
| 唔校正（基準） | 89.54% | 214/239 | — | — |
| V1 強制口語化（ADR-007 初版） | 80.75% | 193/239 | **−21 字** | 126 s |
| **V2 保留語體（本 ADR）** | **90.38%** | **216/239** | **+2 字** | 340 s |

→ LLM **無從判斷**一首歌係書面語定口語，強制改寫必然錯一半。
第二次完整重跑（ASR 每次結果略有唔同）V2 只改咗 3 處：修好 `循回→輪迴`，但整壞兩處 `迴→回`，**淨收益 −1 字**。

**同時落實嘅驗證結論**
- **ADR-001 喺真實歌唱場景成立** ✅：  `language_hints=['zh']` 對有伴奏、有唱腔嘅真 MV 出到 **89.7% 相似度**，
  而且原詞嘅書面語格式保留完整（`輪迴塵間的人`、`徘徊來生的往生` 全部踢中）。
  初版用 edge-tts 朗讀語料得出嘅結論冇被推翻。
- **`PrimaryColour` = 「唱過」嘅高亮色** 已經**目視雙重確認** ✅（抽 frame 實拍：6.0s 時前 5 字黃色、其後白色；100s 時約 15 字黃、6 字白）。
  名詞表 C 組嘅語義定義正確，唔需要調轉。

**Observed：ASR 與 LLM 兩者都係非確定性的**
兩次完整重跑同一段 MV：ASR 產生 13 句 vs 12 句、字數 239 vs 238、逗號位置亦有差異；
同一 prompt 嘅校正結果亦有明顯差異。**同一輸入可以出唔同質素嘅字幕**，呢點要寫落 README 風險章節。

**尚未定案（等使用者拍板）**
V2 雖然消滅咗災難模式，但**喺呢首書面語歌上淨收益只係 −1 ~ +2 字，卻要等多 2～7.5 分鐘**。
口語比重高或咬字含糊嘅歌可能更有價值，但**未實測**。
→ 待決：校正維持「預設開啟」定改為「`--correct` 手動開啟」。

## ADR-012 · timings.json 做 canonical；CLI 拆 generate / render / burn；移除 LLM 校正

**狀態**：✅ 已接受並實作（2026-10-29）

**背景**
smoke test 之後使用者進一步釐清產品定位，兩點根本變化：
1. **範圍收窄**：本工具只處理**粵語、國語、英語的書面語歌**。
2. **會加字幕編輯 UI**：讓使用者自己精準對齊每個詞的時間戳。
3. 既然有 UI 可以人手改錯字 → **LLM 歌詞校正變成負 ROI**（ADR-011 實測淨收益 −1 ~ +2 字，卻要等 2~7.5 分鐘）。

呢三點令原本「一條龍 ASR→ass→mp4」嘅單一命令變得唔合用。

**決策**

1. **`*_timings.json` 係 canonical interchange format**；`.ass` 降級為**由 json 渲染出嚟的衍生物**。
2. **CLI 拆三個 subcommand**：
   ```
   generate   影片 → ASR → timings.json + ass      （**預設唔出影片**）
   render     timings.json → ass                   （毋須重跑 ASR）
   burn       影片 + ass → mp4                     （淨係食 ass）
   ```
3. **`generate` 預設唔再出 mp4**，要影片請另外行 `burn`。
4. **徹底移除 LLM 歌詞校正**（code 清走，`openai` 亦移出 requirements.txt）。錯字交畀 UI 人手改。
5. **`burn` 淨係食 `.ass`**，永遠唔會隱含 render，避免靜默洗走人手 / UI 嘅改動。
6. **OpenCC 只喺偵測到中日韓字元時先跑**（使用者提出會做英語歌）。
7. **斷句改喺 WordGroup 邊界切**，唔再切穿一個詞。
8. **`burn` 由 `.ass` 自己讀 `PlayResX/PlayResY`**，令 burn 唔使依賴 timings.json 都行得通。

**timings.json schema（v1）**

```jsonc
{
  "schema_version": 1,
  "source": { "video": "...", "model": "...", "language_hints": ["zh"], ... },
  "style":  { "play_res_x": 1920, "font_name": "...", "primary_color": "#FFFF00", ... },
  "lines": [{
    "start_ms": 3950, "end_ms": 8890, "text": "輪迴塵間的人，揮之不能",
    "words": [{
      "text": "輪迴", "begin_ms": 3950, "end_ms": 4670,
      "estimated": true,                       // ← 詞內逐字邊界係按比例平分估出嚟
      "chars": [ { "text": "輪", "begin_ms": 3950, "end_ms": 4310 }, ... ]
    }]
  }]
}
```

- **兩層結構 `words[] → chars[]`**：保留 API 原本嘅詞邊界，UI 可以畀用戶拖成個詞、亦可展開逐字微調。
- **`estimated` flag 係本 schema 最重要嘅字段**：實測呢首 MV 有 **40% 嘅詞 / 57% 嘅字**嘅逐字時間軸係程式估出嚟。
  冇呢個 flag，UI 用家無從知道邊啲要人手校。
- `style` 內嵌 → render self-contained，改樣式唔使重跑 ASR。
- 每行嘅 `start_ms/end_ms` **存絕對值**，`render` 直接用、**唔重新推算**（避免 UI 改動同輸出對唔上）。

**理由（實測，2026-10-29 林家謙《普渡眾生》MV）**

| 項目 | 舊一條龍 | 新 generate |
|---|---|---|
| 執行時間 | 7m45s ~ 9m24s | **11 秒** |
| 產出 | ass + mp4 | **json + ass**（冇 mp4） |
| API 花費 | ASR + LLM 校正 | 淨係 ASR |

驗證結果：
- `render` 同一份 json 行兩次 → **byte-identical**（冇 round-trip 漂移）✅
- `render` 唔會改動輸入 json（除非加 `--sync-style`）✅
- `render --primary-color "#00FFFF" --font-size 64` → ASS `&H00FFFF00` / fontsize 64，覆寫生效 ✅
- `burn` 由 `.ass` 讀到 `PlayResX/Y = 1920x1080`，出 57.33MB mp4、保留 AAC 44.1kHz 立體聲原音軌 ✅
- 目視：7.0s 時前 8 字黃色（已唱）、後 3 字白色，底部居中 + 黑色描邊 ✅

**被駁回的選項**
- **`.ass` 繼續做 canonical** — UI 要自行處理 `\kf` 累加值嘅相對時間運算，而且 `estimated` 資訊喺 ass 入面**永久消失**。
- **`burn` 自動由 json render** — 會令「人手改過嘅 ass」被靜默覆寫，屬災難級 silent clobber。
- **保留 LLM 校正做 suggestions 清單** — 使用者最終決定：既然 UI 可以直接改錯字，範圍又淨係書面語歌，校正冇存在價值。
- **加 preview 功能（抽單格 / 短片）** — 使用者否決，直接 burn 全片。

**後果**
- `.ass` 檔案頭有註明「改時間請改 json 再 render」，但**冇技術上強制**；UI 要引導用戶唔好直接改 ass。
- `schema_version` 已加；日後加字段要 bump 版本並更新本 ADR。
- `timings.json` 若被人手改壞（例如顏色寫 `null`），`render` 有兜底預設值 + 清晰錯誤提示（實測撞過）。

## ADR-013 · 標點優先斷行 + 歌詞去標點（2026-10-29）

**決策**

1. **斷行改為「標點優先」**：全部句讀符號（`，。！？；：、…` ＋英文對照）都係斷行點；
   ASR `sentence` 邊界當「隱含句末標點」（防 ASR 漏標點）。
   `max_chars=18` 同 `gap>800ms` **降級做安全網**，淨喺「分句本身超長」時喺 WordGroup 邊界兜底。
2. **歌詞顯示剝走標點**（預設），統一規則：**行尾標點 → 剝走；行中標點 → 變半形空格 + `{\k<gap_cs>}` 停頓**。
   `--keep-punctuation` 可以還原 v1 行為（byte-identical 已實測）。
3. **短句定向合併**：雙條件（字數 ≤3 **且** 自身時長 <1500ms，`--min-clause-chars` / `--min-clause-ms`）
   先算「太短」；句末（hard）收尾 → **向後併**（黐返上一行尾）、句讀（soft）收尾 → **向前併**（帶住下一句）；
   合併會令行超 `max_chars` 就放棄、照出短行。
4. **資料結構**：`punctuation` 由 `CharSlot.text` 尾搬去獨立嘅 `WordGroup.punctuation` 字段，
   `CharSlot` 從此**永遠純字**；`WordGroup` 加 `sentence_end` flag；`LyricLine` 加 `break_reason`
   （`punctuation` / `sentence` / `max_chars` / `gap`）。
5. **timings.json bump `schema_version=2`**：`words[]` 加 `punctuation`、`lines[]` 加 `break_reason`、
   `lines[].text` 改為顯示用文字；v1 舊檔**自動相容**（讀入時將黐喺 text 尾嘅標點拆返出嚟，只 warn 唔 fail；
   英文句號 `.` 刻意唔剝，避免動到 `Mr.` 呢類縮寫）。

**理由（實測，2026-10-29 林家謙《普渡眾生》MV，23 行 / 169 詞 / 32 個標點）**

| 證據 | 數字 |
|---|---|
| 舊 `max_chars` 切法錯位 | 4 處（`…分叉的走`／`馬路，…`、`…偏偏起`／`了一次…`、`…世塵`／`傷感。`、跨 sentence 砌行 `…遺憾中，`／`普渡的眾生`），仲製造 2 字殘行 `不能。`／`傷感。` |
| 純按標點分句 | 32 個分句、**最長 13 字、最短 4 字**，全部 < 18 → 兜底完全唔使觸發 |
| ASR sentence 邊界 | 15 句入面 14 句本身以 `。`／`？` 收尾（同標點斷點高度重疊） |
| 標點唔影響時間軸 | `punctuation` 喺 ASR **冇獨立 begin/end**，剝唔剝都唔使改任何 `\kf` / `hold_ms` |
| v1 相容驗證（probe16） | 169 詞標點全數拆返出嚟、CharSlot 時間軸 **0 drift**；`--keep-punctuation` render 出嚟 Dialogue **byte-identical** |
| 新斷句驗證 | 32 行全部 ≤18 字、顯示文字 0 標點、4 個錯位全數修復、`break_reason` 全部 `punctuation`（兜底零觸發） |

**被駁回的選項**

- **`max_chars` 做主、標點只係建議** —— 實測標點分句天然就 fit（最長 13 字），而 `max_chars` 先至係錯位切法嘅元兇。
- **淨係句末符號（。！？）斷行** —— 會放棄好多好斷點，出 13 字以上長行。
- **短句一律向前合併** —— 句末短樂句（如 `好冇。`）會俾人拉咗入下一句，聽感割裂；分方向先至語義正確。
- **Stage 6 直接掉咗標點** —— timings.json 永久失去標點資訊，日後 UI 想還原／顯示都冇得返轉頭。
- **保持 v1 格式加冗餘字段** —— `text` 會有歧義（含唔含標點？），寫入讀取容易重複剝。

**後果**

- **ASR 標點擺錯位會照錯位斷行**（實測有 `揮之不能徘徊，` 呢類）—— 固有風險，algorithm 層減唔到；
  靠 `break_reason` 記錄 + 日後字幕編輯 UI 人手改（同 ADR-011/012 方向一致）。
- `WordGroup.text` 語義改變（唔再含標點）；`LyricLine.text` 係純字，**顯示一律行 `display_text()`**。
- 渲染時插空格 + `\k` 要將 `prev_end` 更新為下一詞 `begin_ms`，否則會重複插 `\k`、停頓雙倍（probe16 已驗證）。
- 短句合併後行中可能有多於一個空格（連鎖合併），屬預期行為。
- 驗證腳本：`_probe/probe16_punct_split.py`（25 項全 PASS）。

**修訂（2026-10-29 同日，實測《每當變幻時》後）**

1. **短句門檻放寬**：`min_clause_chars` 3 → **5**、`min_clause_ms` 1500 → **2500**——
   舊門檻太保守，4-5 字快句照出會太散（《每當變幻時》28 行 → 24 行）。
2. **合併上限獨立**：新增 `MERGE_MAX_CHARS = 16`（`--merge-max-chars`）——
   合併係為咗消滅短行，唔係為咗砌長行，所以同兜底嘅 `max_chars=18` 分開；
   合併後超 16 字就放棄、短行照出。
3. **`_kind()` 標點優先過 `sentence_end`**：word 自帶標點先至決定 hard/soft，
   `sentence_end` 淨係「冇標點」時嘅 fallback（B2「隱含」嘅原意）。
4. 驗證：probe16 加 (c2)/(g1)/(g2) 三個 case，**28 項全 PASS**；

## ADR-016 · 預覽／時間軸分界改「像素制」，波形高度改「目標值 + 夾高」（2026-11-02）

### 狀態
✅ 已採納（最終定案：sidebar 160px／左欄 386px（歌詞樹 5 欄 370px）／品牌兩行 15px／
預覽 +80px → 波形 192px、字塊 33px）

### 背景
1. **比例制**下 `_preview_ratio = 0.55` 只保證「大約」，任何視窗高度變化都會令 +100px 走位；
   用戶要求嘅係**實數**（預覽加、時間軸減），比例制做唔到。
2. **物理衝突**：1920×1009 視窗下右欄高 899px。時間軸畫布高 = 窗格 − 52px（標題＋zoombar）。
   「波形 128→192（+50%）＋字塊 22→33（+50%）」要
   `20(刻度)+192+4+33+16(概覽) = 265px` 畫布高 → 對應時間軸窗格 317px（= −80px）。
   所以 **預覽 +80 / 時間軸 −80** 先可以同時滿足「波形 +50% ＋ 字塊 +50%」；
   一開始試 +100 只做到波形 172px（+34%），差 20px 擠唔落。

### 決策
- `editor._preview_h` 改**像素制**：首次量度 = `int(右欄高 × 0.55) + PREVIEW_EXTRA_H(80)`，
  之後拖曳直接改像素；夾 `[120, 右欄高 − MIN_TIMELINE_H(200)]`（等價於舊有 30%–75% 保護）。
- `timeline.WAVE_H = 192` 係**目標值**，`_wave_h_for()` 夾成
  `min(192, 畫布高 − 刻度 − 概覽 − 4 − 一條 LANE_H)`：「先保證有一行字幕塊，剩落嘅全畀波形」。
  317px 窗格下剛好食到 192px（不再縮水）；若用戶日後拖矮時間軸，波形會自動讓位而唔會蓋住字塊。
- 字塊 `LANE_H 22→33`、`BLOCK_GAP 6` → 方塊高 18→27（+50%）。
- 字塊 lane 下限由 2 改 1：時間軸變矮之後強行留 2 行只會浪費；行與行本身唔重疊，
  first-fit 實際上永遠用第 1 行（同改動前觀感一致）。
- 圖例由獨立一行搬上 `_tl_box` 的 LabelFrame 標題，回收 ~20px 垂直空間畀波形。
- sidebar 總寬 200 → **160px**（`SIDEBAR_MIN_W` 160→140，仍可拖曳）。
- 品牌方塊 `Karaoke AI Subtitler` **分兩行**（`Karaoke` / `AI Subtitler`），11pt（≈15px @96dpi）；
  一行要 146px，160px 欄減 padx/內距只剩 134px，一定爆格。窗口標題同步改 `Karaoke AI Subtitler`。
- 左欄 260 → **386px**：歌詞樹 5 欄總寬鎖 **370px**（32+174+66+66+32），
  加 scrollbar 8 + LabelFrame 邊框/內距 8 = 386，五欄一欄都唔裁。
  逐字微調「詞」欄 64→140。

### 影響
- `ui/theme.py`（`SIDEBAR_W`）、`ui/app.py`（標題、品牌 Label、`SIDEBAR_MIN_W`）、
  `ui/pages/editor.py`（`LEFT_W`／`PREVIEW_EXTRA_H`／`MIN_TIMELINE_H`／`_clamp_preview_h`／圖例位置）、
  `ui/widgets/timeline.py`（`WAVE_H`/`LANE_H`/`BLOCK_GAP`/`MIN_WAVE_H`、`_wave_h_for`、`_lanes_y_top`）、

## ADR-017 · 導航字級要經 ttk style；顏色色塊改 grid + 雙重上色（2026-11-02）

### 狀態
✅ 已採納（用戶需求：sidebar 160→140px、導航按鈕字級 +2、色塊顏色要同選取一致）

### 背景
1. **ttk::button 冇 `-font` option**（唔似 tk.Button）：`ttkb.Button(..., font=...)` 直接
   拋 `_tkinter.TclError: unknown option "-font"`。字級一定要經 `ttk.Style().configure(style, font=...)`。
   但 `bootstyle="primary"/"secondary"` 每次切頁都會改寫 widget 嘅 `style`，
   想「只在導航按鈕加大字」就唔可以只設一次。
2. **色塊唔跟選取色**（用戶附截圖回報）：原本用 `pack` 排「色塊 + hex 輸入框」，
   視窗一窄，pack 會先壓細第一個子元件 → 色塊縮到睇唔到（或只剩一兩 px），
   而 hex 輸入框照樣顯示新色 → 用戶見到「色塊同揀嘅色唔一致」。
   另外舊 code 只寫 `canvas["bg"]`，而且只 catch `ValueError` ——
   Tk 對 `#0000F` 呢類 5 位 hex 會拋 `TclError`，令色塊靜靜停留在舊色。

### 決策
- 導航按鈕改自訂 style：`Nav.TButton`（未選中）／`NavActive.TButton`（當前頁），
  兩者 `font=(ui_font, 11)`（主題預設 9pt +2），顏色用專案色票
  （`BG_HOVER` / `ACCENT`），切頁時切 style 而唔再切 `bootstyle`。
- 色塊 cell 由 `pack` 改 `grid`（label 跨兩欄、色塊 column 0、輸入框 column 1），
  子元件唔會再被擠到消失。
- 新增 `_set_swatch(key, color)`：**Canvas 背景 + 填滿嘅 rectangle item** 雙重上色；
  `color=None`（輸入未合法）就保留舊色並把邊框轉紅，唔會出現「輸入新色、色塊舊色」。
- 新增 `_normalise_hex()`（regex `^#?[0-9a-fA-F]{6}$`）：接受冇 `#`、大小寫混寫；
  輸入框失焦／Enter 時寫返 `#RRGGBB`，所以文字同色塊一定對得上。
- sidebar 總寬 160 → **140px**（`SIDEBAR_MIN_W` 140→120）。

### 影響
- `ui/theme.py`（`SIDEBAR_W`）、`ui/app.py`（`_nav_styles`、`NAV_FONT_SIZE`、切頁改用 style）、
  `ui/pages/home.py`（`_HEX_RE`／`_normalise_hex`／`_set_swatch`／`_normalise_entry`／色塊 grid 化）。

### 驗證
`_probe` 實機截圖：sidebar 140、品牌兩行、4 顆導航 11pt 無裁切、當前頁藍底深字；
主頁色塊 #00FFFF / #FF8800 / #000000 與輸入完全一致；
`#1234`（未打完）→ 保留舊色 + 紅框；`FF8800`（冇 `#`）→ 認得並上色。
`tests/test_editor_core.py` 26 checks PASS。

## ADR-019 · 三套主題可即時切換；視窗圖示改用 WM_SETICON（2026-11-02）

### 狀態
✅ 已採納（用戶需求：① 之前 darkly／superhero 兩個主題消失要返嚟；② 逐字微調「詞」欄要左對齊；
③ 品牌方塊字級 18px；④ 要 app icon）

### 背景
1. ADR-018 為咗避免「深殼＋淺面板」混搭，把主題下拉收起、UI 寫死淺色票。用戶其後要求
   **三套主題都要揀得返**（litera / darkly / superhero）。
2. 舊做法係模組級常數（`BG_DEEP = "#FFFFFF"` 等），換色一定要改檔案；而且部分 widget
   喺 `__init__` 就把色值寫入（Canvas bg、Text tag），換主題唔會跟。
3. **`wm iconbitmap` 喺 ttkbootstrap Window 上唔生效**：呼叫後 `wm iconbitmap` 查詢回空字串，
   標題列仍然是 ttkbootstrap 預設嘅羽毛圖示（用 `ImageGrab` 截標題列實測）。
   而且 `GetParent(winfo_id())` 喺視窗 map 之前攞到 0，太早送 `WM_SETICON` 等於冇送。

### 決策
- `theme.py` 改**色票註冊表**：`PALETTES = {"litera": {...}, "darkly": {...}, "superhero": {...}}`，
  token 集合三套必須一致（缺 key 直接 `KeyError`，寧願啟動就爆都唔好半深半淺）。
  `set_palette(name)` 用 `globals().update()` **重新綁定**模組全局色名 ——
  所以 widget 一律寫 `theme.BG_PANEL`（屬性存取），**禁止** `from theme import BG_PANEL`。
- `apply_ttkbootstrap_theme(root, name)` 先 `style.theme_use(base)` 再用色票覆寫；
  可重複呼叫（啟動 + 換主題）。Treeview 標題要連 `light.Treeview.Heading` /
  `dark.Treeview.Heading` 一齊覆寫，否則深色主題會見到淺灰標題列。
- `App.apply_theme(name)`：換色票 → 重設 ttk style → `_nav_styles()`（含 `Brand.TLabel`）
  → `_restyle_tree()` 遞歸為 tk 原生控件補色（有 `restyle()` 就交畀它，有 `_theme_token`
  就直接 configure bg）→ 寫入 settings.json。**唔需要重建頁面**，編輯中嘅 timings 唔會流失。
- 品牌方塊改 `Brand.TLabel` 自訂 style（`ACCENT` 底 + `ON_ACCENT` 字），
  唔再用 `inverse-<hex>`（ttkbootstrap 自己推算對比色，深色主題下變深字壓藍底）。
  字級 `size=-18`（Tk 負數 = **像素**；寫 `18` 會變 18pt ≈ 24px 爆格）。
- 逐字微調／歌詞樹：**標題 anchor 跟欄位 anchor**（「詞」欄左對齊），另固定
  `ch`/`begin` 闊度、由 `word`/`end` 吸收剩餘闊度，視窗變闊唔會跳位。
- 圖示：`tools/make_icon.py` 用 PIL 生成 `assets/app.ico`（16/24/32/48/64/128/256）+ `app.png`；
  `App._set_window_icon()` 喺 Windows 走 ctypes `LoadImageW` + `WM_SETICON`
  （ICON_SMALL 32px／ICON_BIG 256px），失敗每 200ms 重試最多 15 次；
  `run()` 先 `SetCurrentProcessExplicitAppUserModelID` 令工作列用我哋嘅圖示。

### 影響
- `ui/theme.py`（重寫：PALETTES / set_palette / apply(name) / ON_ACCENT / SEARCH_HIT /
  BRAND_FONT_PX）、`ui/app.py`（圖示、`apply_theme`、`_restyle_tree`、`Brand.TLabel`）、
  `ui/pages/settings_page.py`（主題下拉 + 即時套用）、`ui/settings.py`（theme 已可選）、
  `ui/pages/editor.py`／`ui/widgets/{lyric_tree,timeline,preview,style_preview,markdown_view}.py`
  （`restyle()`、標題 anchor、`_theme_token`）、`ui/pages/help.py`（`_style_widgets` + `restyle`）、
  `ui/pages/home.py`（`restyle`）、`tools/make_icon.py`（新）、`assets/app.ico|png`（新）。

### 驗證
`_probe` 實機截圖三套主題 × 四頁（`_smoke/t2_*.bmp`）：ttk 與 Canvas 一致變色、無白色殘留；
深色主題下 Treeview 標題列不再是淺灰；標題列圖示為藍底白色咪高風（`ImageGrab` 截圖確認）；
逐字微調「詞」標題與詞語同一左邊界。`tests/test_editor_core.py` 26 checks PASS。
