## ADR-001 · `-l yue` 內部重映射為 `language_hints=['zh']`

**狀態**：✅ 已接受（2026-10-29）

**背景**
原規格書假設 `-l yue` 可以指定粵語識別。實測發現呢個假設唔單止錯，而且**反效果最嚴重**。

**決策**
`--language yue` **唔會**把 `yue` 傳畀百煉。程式內部統一重映射為 `language_hints=['zh']`，並喺 log 明確印出：
```
[warn] 已將 --language=yue 重映射為 language_hints=['zh']（見 ADR-001：yue 會觸發粵語→普通話轉寫）
```
其餘語言碼（`zh` / `en` / `ja` …）原值直傳。

**理由（實測）**
同一段粵語音源（ground truth：`我哋今晚一齊去食飯啦，你唔好唔記得帶埋個銀包。`）：

| `language_hints` | 輸出 | 粵語口語字 | 粒度 |
|---|---|---|---|
| 唔傳（auto） | `我们今晚一起去吃饭啦，你不要不记得带个钱包。` | ❌ 全蒸發 | 詞級 |
| **`['zh']`** | **`我哋今晚一齐去食饭啦，你唔好唔记得带埋个银包。`** | ✅ **全保留** | ✅ **18/21 字級** |
| **`['yue']`** | `我们今晚一起去吃饭啦，你不要不记得带上个钱包。` | ❌ **全蒸發** | 詞級 |

`yue` 喺呢個 API 嘅實際語義係「**識別粵語，但輸出規範普通話書面語**」，等同於要求模型做方言轉寫。
另外：官方 `language_hints` 語言碼清單亦**根本冇 `yue`**（只有 `zh en ja ko vi th id ms tl hi ar fr de es pt ru it nl sv da fi no el pl cs hu ro bg hr sk`）。

**被駁回的選項**
- **粵語自動改用 `fun-asr`**（官方唯一明文支援粵語）— 實測 fun-asr 確實正確輸出粵語（19/21 字級），但冇 `usage` 字段、`confidence` 尺度唔同，要雙軌處理。列為後備 model，唔做自動切換：**自動切換會令 `--model` 參數失去決定性，對教學場景係災難**。
- **argparse 層面拒絕 `yue`** — 對香港用戶最唔友善，佢哋唔會理解點解「粵語唔畀揀粵語」。

**後果**
- 代價：`--language` 的語義唔再係「原值轉發」，code 必須有 mapping table。
- 好處：用戶打 `-l yue` 得到正確嘅粵語歌詞，而唔係一堆普通話。

## ADR-002 · 唔傳 `enable_words` 與 `enable_itn`

**狀態**：✅ 已接受（2026-10-29）

**背景**
原規格書要求「必須開啟 `enable_words=True`」同埋「`enable_itn=False` 避免數字被轉阿拉伯數字」。兩者**都唔存在於本 model**。

**決策**
提交轉寫任務時**只傳** `model` / `file_urls` / `language_hints`（視情況）。其餘參數一律不傳。

**理由（實測）**
- 官方文件中 `enable_words` **只屬於 `qwen3-asr-flash-filetrans`**。本 model（`Qwen-Audio-3.x-ASR-Flash-Filetrans`）嘅時間戳係「**永久開啟、不可關閉**」，而 word-level **本來就自帶**。
- `enable_itn` 只存在於 `qwen3-asr-flash` 的 **OpenAI 兼容模式** `asr_options`。
- 實測：傳 `enable_words=True` / `enable_itn=False` **冇報錯亦冇可觀測差異**（both 200 OK，`words[]` 照樣有）。
- 唔傳嘅好處係**減少對未文件化參數的依賴**：呢啲參數今日被靜默忽略，聽日可能變成 `400 InvalidParameter`。

**後果**
- 數字歌詞點樣呈現由模型決定，我哋控制唔到（原規格書想解決嘅問題仍然存在，但**無解**，唔係我哋唔做）。
- code 更簡單、更抗 API 變動。

## ADR-003 · 本地音頻上傳走 `Files.upload → Files.get()` 預簽名 URL

**狀態**：✅ 已接受（2026-10-29）

**背景**
Filetrans 模型唔收本地路徑，必須先上傳。原規格書建議用 `oss://` + `X-DashScope-OssResourceResolve` header。

**決策**
主路線：
```python
up   = dashscope.Files.upload(file_path=wav, purpose="assistants")
fid  = up.output["uploaded_files"][0]["file_id"]
url  = dashscope.Files.get(file_id=fid).output["url"]   # 預簽名 https URL
if url.startswith("http://"):
    url = url.replace("http://", "https://", 1)
```
後備路線（`Files.get()` 失敗時）：`OssUtils.upload()` + `Transcription.async_call(..., headers={"X-DashScope-OssResourceResolve": "enable"})`。

**理由（實測）**
四種做法全部試過：

| 做法 | 結果 |
|---|---|
| `file://C:\...` 直塞 `file_urls` | ❌ `DECODE_ERROR` |
| 裸絕對路徑 | ❌ `REQUEST_INVALID_FILE_URL_VALUE` |
| `oss://...`（**冇** header） | ❌ `REQUEST_INVALID_FILE_URL_VALUE`（13.8s 後 FAILED） |
| `oss://...` + `OssResourceResolve` header | ✅ SUCCEEDED |
| **`Files.get()` 預簽名 https URL** | ✅ **SUCCEEDED（唔使額外 header）** |

⚠️ **陷阱**：`dashscope.Files.upload()` 返 200 但淨係畀一個 `file_id`，**唔係**可以直接餵畀 ASR 嘅 URL；必須再 `Files.get()` 拎 `url` 字段。
⚠️ 預簽名 URL 有 `Expires` 參數（實測約 7 日有效），必須「上傳即提交」，唔好 cache。

**後果**
- 主路線唔依賴任何未公開嘅 header，SDK 升級更穩。
- 需要兩次 API call（upload + get）而非一次。

## ADR-004 · 永久禁用 `paraformer-v2`（假時間軸）

**狀態**：✅ 已接受（2026-10-29）

**背景**
為咗搵「粒度最幼」嘅 model，測咗成個 model 清單。`paraformer-v2` 表面數據**最好**，實際上係最差嘅選擇。呢條決定特別記低，因為**下一個人好大機會會再揀佢**。

**決策**
唔准用 `paraformer-v2`（或任何 paraformer 變體）黎產生卡拉OK 時間軸。code 層面加 assertion log。

**理由（實測）**
粵語測試音源（21 個有效字）：

| 指標 | `paraformer-v2` | (`qwen-audio-3.1 + zh` 對照) |
|---|---|---|
| WordSlot 數 | **21（看似完美 100%）** | 18（86%） |
| 每個 duration | `244, 245, 245, 245, 244, 245, …` | `120, 240, 280, 320, 200, 120, 200, 280, …` |
| **duration 唯一值數量** | **2** | **7** |
| word 間 gap | **全部 0** | 有非零值 |
| 起始時間 | **0 ms**（實際語音 280 ms 先開始） | 280 ms |
| `confidence` 字段 | **冇** | 有 |

→ 係**均勻線性插值**，唔係聲學對齊。仲衰嘅係佢**冇句子內部停頓**：實測 ground truth 兩句之間有明顯停頓，paraformer 當冇到。

**後果**
用佢做出嚟嘅卡拉OK 會係**機械等速掃過**，完全唔跟歌手節奏，而且因為冇 gap，字幕永遠唔會喺停頓位停低。

## ADR-005 · ASS 時間戳統一格式為 `H:MM:SS.cc`，並集中於單一 helper

**狀態**：✅ 已接受（2026-10-29）

**背景**
開發期間踩過一次：時間戳寫成 `M:SS:cc`（如 `0:00:28`），ffmpeg 冇報錯退出，淨係喺 verbose log 印咗兩行 `Bad timestamp`，然後**輸出一條完全冇字幕、而且 md5 同輸入完全一樣嘅 mp4**。

**決策**
- 全專案只准有一個 `ms_to_ass_time()` helper，格式 `"{h:d}:{m:02d}:{s:02d}.{cs:02d}"`（例：`0:00:00.28`）。
- 分鐘與秒**必須兩位數**，毫秒位必須用小數點分隔。
- ms → cs 嘅換算（`max(1, round(ms/10))`）亦只准有一個 helper。

**理由**
1. ASS 規範硬性要求 `H:MM:SS.cc`。寫 `0:00:28` 時 libass 會解讀成「28 秒」，導致 event 時間錯位。
2. **失敗模式極度隱蔽**：ffmpeg exit code 0、輸出檔案存在、size 正常，淨係冇字幕。肉眼驗收先會發現，自動化測試唔 check frame content 就過咗。

**後果**
- 所有時間運算集中喺兩個 function，改算法淨係改一處。
- **要求**：任何改動呢兩個 helper 嘅 PR，必須附「抽 frame 目視驗證」嘅證據（对比 `_probe/burn test dir/frame_C_*.png`）。

## ADR-006 · ffmpeg 燒錄：切 cwd + 相對路徑 + `original_size`

**狀態**：✅ 已接受（2026-10-29）

**背景**
原規格書已預警 `ass=` filter 嘅路徑跳脫問題。實測確認存在，而且爆法好具體。

**決策**
1. **永遠唔好**把路徑直接寫入 `-vf ass=<path>`。改為：設 `subprocess.run(..., cwd=<ass 檔案所在目錄>)`，filter 只寫 `ass=<檔名>`；輸入影片用 `os.path.relpath()` 轉相對路徑。
2. ffmpeg 命令**必須**帶 `original_size=WxH`；同時 ASS 檔嘅 `PlayResX/PlayResY` 由 **ffprobe 讀取原片**填入，唔准寫死。

**理由（實測）**
```
$ ffmpeg -vf "ass=C:\Users\pslam\...\burn test dir\karaoke.ass"
[Parsed_ass_0] Unable to parse "original_size" option value
               "UserspslamDocumentsAgents_workspaceskaraoke_probeburn test dirkaraoke.ass"
               as image size
→ rc = 4294967274
```
Windows 路徑嘅 `C:` 冒號被 ffmpeg 當成 **filter option 分隔符**，路徑被切成兩段。目錄入面嘅**空格**進一步惡化。
切 cwd + 相對檔名 → 立即成功。

`original_size` 嘅必要性：libass 需要知道原片尺寸，先至可以用正確比例擺放字幕；唔加會喺輸出 canvas 與輸入尺寸不一致時走位。

**後果**
- `subprocess` call 必須帶 `cwd=`，而且 input path 要 `relpath` — 呢個約束要寫喺 function docstring。
- 需要先跑一次 `ffprobe` 拎解像度（多一次 subprocess call，可接受）。

## ADR-007 · 歌詞校正必有「字數鎖」，且思考模式必須 ON

**狀態**：⚠️ **已被 ADR-012 取代**（2026-10-29）——歌詞校正整體由 CLI 移除。
本 ADR 保留作歷史紀錄，其實測結論（思考模式係字數鎖必要條件）仍然有效，
若日後要重新引入校正功能，請先讀本 ADR 再讀 ADR-011 / ADR-012。

**背景**
用戶要求加入 LLM 歌詞校正（用百煉 `qwen3.8-27b`）。風險係：LLM 改寫歌詞後**字數改變**，會令所有 CharSlot 嘅時間軸失去對應關係。

**決策**
1. **字數鎖係鐵律**：校正後每行字數必須 `==` 校正前。**由程式驗證，唔係靠 prompt 保證**。
2. **驗證失敗 → 棄用校正結果，原地退回 ASR 原文**，並 warn log。（寧願歌詞有錯字，都唔可以令時間軸錯位。）
3. **思考模式必須保持 ON**。`enable_thinking=False` 喺本專案係**[禁用]**。
4. 預設 model = **`qwen3.8-flash`**；`qwen3.8-27b` 保留為 `--correction-model` 進階選項。
5. 以**批量**（每行 `N|原文（X字）`）發送，行號對齊輸出。

**理由（實測，同一份 6 行測試歌詞）**

| model | thinking | 用時 | 字數鎖 |
|---|---|---|---|
| `qwen3.8-27b` | ON | 134.6 s（22.4 s/行） | ✅ 6/6 |
| `qwen3.8-27b` | OFF | 2.9 s（0.5 s/行） | ❌ **5/6** |
| **`qwen3.8-flash`** | **ON** | **51.9 s（8.6 s/行）** | ✅ **6/6** |
| `qwen3.8-flash` | OFF | 2.5 s（0.4 s/行） | ❌ **5/6** |

→ **思考模式係守住字數鎖嘅必要條件**。關思考快 ~60 倍，但會數錯字數（實測把「其实我好想你知道我一直都在这里等你」改成少咗字）。

校正質素實測結果（正確）：
`我们→我哋` / `已经→已經` / `光竟→光景` / `不要说话→唔好講嘢` / `在这里→喺呢度` / `天塌下来→天塌落嚟`

**被駁回的選項**
- **唔鎖字數、校正後重新分配時間軸** — 本末倒置：重新分配就係重新引入估算誤差，抵消咗 ASR 時間軸嘅價值。
- **用 `fun-asr` 嘅 `confidence` 做門檻代替 LLM** — confidence 只能話你低信心，唔會話你應該改成咩字。

**後果**
- 一首 40 句嘅歌，校正階段約需 `40 × 8.6s ÷ 併發數`。**必須做並行分批**（ADR-007 後續：預設 batch=6 / workers=4），並顯示進度。
- 呢個係全 pipeline 最慢嘅一步，要有 `--no-correction` 開關畀用戶跳過。

## ADR-008 · 處理管線次序：OpenCC 押後到最後一步

**狀態**：✅ 已接受（2026-10-29）

**背景**
直覺做法係「ASR 一出就跑 OpenCC 轉繁體」。實測發現咁做會被後面嘅步驟破壞。

**決策**
固定次序，唔准調亂：
```
ASR → 字數鎖校正（LLM）→ 拆字（WordSlot→CharSlot）→ OpenCC s2hk → 斷句 → 生成 ASS
```
理由分層：
1. **校正必須喺拆字之前** — 字數鎖係以「行」為單位；拆完字再改就無從保證字數對應。
2. **OpenCC 必須喺 LLM 之後** — LLM 輸出**繁簡混雜**，實測：`我哋遊過當晚漆黑嘅海港`（前半繁、後半簡）。OpenCC 做最後一道**正規化閘門**，保證落地前全部係港式繁體。
3. **`config` 固定係 `s2hk`**，唔用 `s2twp`（差異：`裏vs裡`、`説vs說`、`着vs著`），亦**唔用 `t2hk`**（實測 `t2hk` 對本專案輸入反而輸出簡體，行為反直覺）。

**理由（額外）**
- OpenCC `s2hk` 喺 53 個測試詞上 **0 個長度變化**（如 `里面→裏面`、`干什么→幹什麼`），**唔會破壞字數鎖**，所以放最後安全。
- ⚠️ 但注意：字數鎖嘅驗證必須**喺 OpenCC 之前**用「同一個基準」做（LLM in vs LLM out），唔可以跨 OpenCC 比較。

**後果**
- OpenCC 只跑一次（對最終 CharSlot），效能最好。
- 若日後加新嘅文字變換步驟，必須插入呢條 chain 嘅正確位置並更新本 ADR。

## ADR-009 · 輸出規格固定：mp4 / libx264 crf18 medium / `-c:a copy`

**狀態**：✅ 已接受（2026-10-29）

**背景**
目標用戶係香港社福界同工（課堂環境、設備參差）。輸出規格要「一定播到」。

**決策**
- 輸出容器**一律 `.mp4`**，檔名 `<原檔名>_karaoke.mp4`（即使輸入係 `.mkv` / `.mov`）。
- 視頻：`-c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p`。
- 音頻：**`-c:a copy`**（原規格書要求保留原聲軌 + 加速）。**若失敗則降級** `-c:a aac -b:a 192k` 並 warn。
- 解析度、幀率**跟原片**（唔縮不放）。

**理由（實測）**
- `-vf ass=` **必然導致 video re-encode**，`-c:a copy` 只對音頻有效 — 所以「保持原片畫質」實際上係「以 crf18 接近無損重編」，要講清楚。
- crf 18 / preset medium 係「接近無損 + 可接受編碼時間」的平衡點，對 4-12 小時課程嘅示範 MV 長度（3-5 分鐘）綽綽有餘。
- 遇到 mkv 常見嘅非 mp4 相容音頻編碼（eg. 某些 PCM / Vorbis），`-c:a copy` 會失敗 → 必須有降級路徑。

**被駁回的選項**
- **保留原容器**（mkv 出 mkv）— 社福界設備參差，mkv 唔係部部播到。
- **NVENC 硬體加速** — 用戶機器唔一定有 N 卡，要寫 fallback，複雜度換唔到確定性收益。日後可加做 `--hwaccel` 可選 flag。

**後果**
- 實現上要根據 ffprobe 結果決定音頻 codec，唔可以無條件 copy。

## ADR-010 · 重依賴一律「懶安裝 + 友善提示」

**狀態**：✅ 已接受（2026-10-29）

**背景**
`--separate-vocals` 需要 AI 人聲分離（`audio-separator` / `demucs`），呢啲會拖入 `torch` / `onnxruntime`，體積以 GB 計。而本工具嘅用戶係課堂環境嘅社福界同工。

**決策**
- `audio-separator` **唔入** `requirements.txt`。
- 基礎 `requirements.txt` 只放：`dashscope`、`requests`、`python-dotenv`、`opencc-python-reimplemented`、`openai`。
- 用到 `--separate-vocals` 時先 `importlib.util.find_spec("audio_separator")` 檢查；冇裝就**印出具體安裝指令**並乾淨退出：
  ```
  [error] 未偵測到 audio-separator。請先執行：
          pip install audio-separator
      （人聲分離會額外安裝 onnxruntime，約需 500MB～2GB 磁碟空間）
      （唔用人聲分離可改用 --separate-vocals 以外嘅預設模式）
  ```
- 同理適用於未來任何重依賴。

**理由**
一般 `--separate-vocals` 係**可選強化**：背景音樂強烈時先用。基礎用戶（八成以上）裝唔到 GB 級依賴。
另外實測已知：`qwen-audio-3.1 + language_hints=['zh']` 喺**冇人聲分離**嘅情況下，對純人聲 TTS 嘅粵語識別已達 21/21 全中 —— 人聲分離並非常必需。

**被駁回的選項**
- **直接寫入 `requirements.txt`** — 對課堂環境係災難。
- **改成 `extras_require`（`pip install -e .[vocals]`）** — 標準做法，但要改成完整 package 結構（`pyproject.toml`），放棄「單一 `main.py` 拎去就用」嘅簡單交付，同課程教材嘅定位唔夾。

**後果**
- 「懶依賴」嘅錯誤訊息必須寫清楚安裝指令同磁碟空間，否則用戶會卡死。

## ADR-011 · 歌詞校正改為「保留原文語體」，禁止書面語⇄口語互相改寫

**狀態**：✅ 已接受並實作（2026-10-29，真實 MV 端到端實測後修訂 ADR-007）

**背景**
ADR-007 定落嘅校正 prompt 第 4 條係「輸出繁體中文，用香港粵語口語字（嘅、佢、唔、哋、咗、係、喺、諗、睇）」。
初版喺 edge-tts 朗讀語料上測試表現良好（`我们→我哋`、`光竟→光景`），但**嗰份測試語料全部係粵語口語**。真實 MV 一上場就出事。

**測試條件（首次真實歌唱場景）**
- 素材：林家謙《普渡眾生》（電影《破．地獄》主題曲）MV，1920×1080 / AV1 / 60fps / AAC / 180 秒
- Ground truth 歌詞：239 字（取自百度百科、Shazam、官方 MV 描述三方交叉驗證）
- ⚠️ **關鍵：呢首歌嘅原詞係標準書面語**（`輪迴塵間的人`、`徘徊來生的往生`），**唔係**粵語口語

**決策**
1. 校正 prompt 第 4 條改為：**只修正語音識別造成嘅同音／近音錯字；原文係書面語定口語，必須原樣保留**，
   並逐項列明禁止嘅轉換（`的↛嘅` `不↛唔` `這↛呢` `來↛嚟` `給↛畀` `了↛咗` `還↛仲`）。
2. ASR 片尾嘅**單字雜訊殘句直接丟棄**（實測吐出過 `"用。"`）。

**理由（實測，同一份 ASR 結果、同一 model、只換 prompt）**

| 策略 | 相似度 | 正確字數 | Δ vs 唔校正 | 用時 |
|---|---|---|---|---|
| 唔校正（基準） | 89.54% | 214/239 | — | — |
| V1 強制口語化（ADR-007 初版） | 80.75% | 193/239 | **−21 字** | 126 s |
| **V2 保留語體（本 ADR）** | **90.38%** | **216/239** | **+2 字** | 340 s |

→ LLM **無從判斷**一首歌係書面語定口語，強制改寫必然錯一半。
第二次完整重跑（ASR 每次結果略有唔同）V2 只改咗 3 處：修好 `循回→輪迴`，但整壞兩處 `迴→回`，**淨收益 −1 字**。

**同時落實嘅驗證結論**
- **ADR-001 喺真實歌唱場景成立** ✅：  `language_hints=['zh']` 對有伴奏、有唱腔嘅真 MV 出到 **89.7% 相似度**，
  而且原詞嘅書面語格式保留完整（`輪迴塵間的人`、`徘徊來生的往生` 全部踢中）。
  初版用 edge-tts 朗讀語料得出嘅結論冇被推翻。
- **`PrimaryColour` = 「唱過」嘅高亮色** 已經**目視雙重確認** ✅（抽 frame 實拍：6.0s 時前 5 字黃色、其後白色；100s 時約 15 字黃、6 字白）。
  名詞表 C 組嘅語義定義正確，唔需要調轉。

**Observed：ASR 與 LLM 兩者都係非確定性的**
兩次完整重跑同一段 MV：ASR 產生 13 句 vs 12 句、字數 239 vs 238、逗號位置亦有差異；
同一 prompt 嘅校正結果亦有明顯差異。**同一輸入可以出唔同質素嘅字幕**，呢點要寫落 README 風險章節。

**尚未定案（等使用者拍板）**
V2 雖然消滅咗災難模式，但**喺呢首書面語歌上淨收益只係 −1 ~ +2 字，卻要等多 2～7.5 分鐘**。
口語比重高或咬字含糊嘅歌可能更有價值，但**未實測**。
→ 待決：校正維持「預設開啟」定改為「`--correct` 手動開啟」。

## ADR-012 · timings.json 做 canonical；CLI 拆 generate / render / burn；移除 LLM 校正

**狀態**：✅ 已接受並實作（2026-10-29）

**背景**
smoke test 之後使用者進一步釐清產品定位，兩點根本變化：
1. **範圍收窄**：本工具只處理**粵語、國語、英語的書面語歌**。
2. **會加字幕編輯 UI**：讓使用者自己精準對齊每個詞的時間戳。
3. 既然有 UI 可以人手改錯字 → **LLM 歌詞校正變成負 ROI**（ADR-011 實測淨收益 −1 ~ +2 字，卻要等 2~7.5 分鐘）。

呢三點令原本「一條龍 ASR→ass→mp4」嘅單一命令變得唔合用。

**決策**

1. **`*_timings.json` 係 canonical interchange format**；`.ass` 降級為**由 json 渲染出嚟的衍生物**。
2. **CLI 拆三個 subcommand**：
   ```
   generate   影片 → ASR → timings.json + ass      （**預設唔出影片**）
   render     timings.json → ass                   （毋須重跑 ASR）
   burn       影片 + ass → mp4                     （淨係食 ass）
   ```
3. **`generate` 預設唔再出 mp4**，要影片請另外行 `burn`。
4. **徹底移除 LLM 歌詞校正**（code 清走，`openai` 亦移出 requirements.txt）。錯字交畀 UI 人手改。
5. **`burn` 淨係食 `.ass`**，永遠唔會隱含 render，避免靜默洗走人手 / UI 嘅改動。
6. **OpenCC 只喺偵測到中日韓字元時先跑**（使用者提出會做英語歌）。
7. **斷句改喺 WordGroup 邊界切**，唔再切穿一個詞。
8. **`burn` 由 `.ass` 自己讀 `PlayResX/PlayResY`**，令 burn 唔使依賴 timings.json 都行得通。

**timings.json schema（v1）**

```jsonc
{
  "schema_version": 1,
  "source": { "video": "...", "model": "...", "language_hints": ["zh"], ... },
  "style":  { "play_res_x": 1920, "font_name": "...", "primary_color": "#FFFF00", ... },
  "lines": [{
    "start_ms": 3950, "end_ms": 8890, "text": "輪迴塵間的人，揮之不能",
    "words": [{
      "text": "輪迴", "begin_ms": 3950, "end_ms": 4670,
      "estimated": true,                       // ← 詞內逐字邊界係按比例平分估出嚟
      "chars": [ { "text": "輪", "begin_ms": 3950, "end_ms": 4310 }, ... ]
    }]
  }]
}
```

- **兩層結構 `words[] → chars[]`**：保留 API 原本嘅詞邊界，UI 可以畀用戶拖成個詞、亦可展開逐字微調。
- **`estimated` flag 係本 schema 最重要嘅字段**：實測呢首 MV 有 **40% 嘅詞 / 57% 嘅字**嘅逐字時間軸係程式估出嚟。
  冇呢個 flag，UI 用家無從知道邊啲要人手校。
- `style` 內嵌 → render self-contained，改樣式唔使重跑 ASR。
- 每行嘅 `start_ms/end_ms` **存絕對值**，`render` 直接用、**唔重新推算**（避免 UI 改動同輸出對唔上）。

**理由（實測，2026-10-29 林家謙《普渡眾生》MV）**

| 項目 | 舊一條龍 | 新 generate |
|---|---|---|
| 執行時間 | 7m45s ~ 9m24s | **11 秒** |
| 產出 | ass + mp4 | **json + ass**（冇 mp4） |
| API 花費 | ASR + LLM 校正 | 淨係 ASR |

驗證結果：
- `render` 同一份 json 行兩次 → **byte-identical**（冇 round-trip 漂移）✅
- `render` 唔會改動輸入 json（除非加 `--sync-style`）✅
- `render --primary-color "#00FFFF" --font-size 64` → ASS `&H00FFFF00` / fontsize 64，覆寫生效 ✅
- `burn` 由 `.ass` 讀到 `PlayResX/Y = 1920x1080`，出 57.33MB mp4、保留 AAC 44.1kHz 立體聲原音軌 ✅
- 目視：7.0s 時前 8 字黃色（已唱）、後 3 字白色，底部居中 + 黑色描邊 ✅

**被駁回的選項**
- **`.ass` 繼續做 canonical** — UI 要自行處理 `\kf` 累加值嘅相對時間運算，而且 `estimated` 資訊喺 ass 入面**永久消失**。
- **`burn` 自動由 json render** — 會令「人手改過嘅 ass」被靜默覆寫，屬災難級 silent clobber。
- **保留 LLM 校正做 suggestions 清單** — 使用者最終決定：既然 UI 可以直接改錯字，範圍又淨係書面語歌，校正冇存在價值。
- **加 preview 功能（抽單格 / 短片）** — 使用者否決，直接 burn 全片。

**後果**
- `.ass` 檔案頭有註明「改時間請改 json 再 render」，但**冇技術上強制**；UI 要引導用戶唔好直接改 ass。
- `schema_version` 已加；日後加字段要 bump 版本並更新本 ADR。
- `timings.json` 若被人手改壞（例如顏色寫 `null`），`render` 有兜底預設值 + 清晰錯誤提示（實測撞過）。

## ADR-013 · 標點優先斷行 + 歌詞去標點（2026-10-29）

**決策**

1. **斷行改為「標點優先」**：全部句讀符號（`，。！？；：、…` ＋英文對照）都係斷行點；
   ASR `sentence` 邊界當「隱含句末標點」（防 ASR 漏標點）。
   `max_chars=18` 同 `gap>800ms` **降級做安全網**，淨喺「分句本身超長」時喺 WordGroup 邊界兜底。
2. **歌詞顯示剝走標點**（預設），統一規則：**行尾標點 → 剝走；行中標點 → 變半形空格 + `{\k<gap_cs>}` 停頓**。
   `--keep-punctuation` 可以還原 v1 行為（byte-identical 已實測）。
3. **短句定向合併**：雙條件（字數 ≤3 **且** 自身時長 <1500ms，`--min-clause-chars` / `--min-clause-ms`）
   先算「太短」；句末（hard）收尾 → **向後併**（黐返上一行尾）、句讀（soft）收尾 → **向前併**（帶住下一句）；
   合併會令行超 `max_chars` 就放棄、照出短行。
4. **資料結構**：`punctuation` 由 `CharSlot.text` 尾搬去獨立嘅 `WordGroup.punctuation` 字段，
   `CharSlot` 從此**永遠純字**；`WordGroup` 加 `sentence_end` flag；`LyricLine` 加 `break_reason`
   （`punctuation` / `sentence` / `max_chars` / `gap`）。
5. **timings.json bump `schema_version=2`**：`words[]` 加 `punctuation`、`lines[]` 加 `break_reason`、
   `lines[].text` 改為顯示用文字；v1 舊檔**自動相容**（讀入時將黐喺 text 尾嘅標點拆返出嚟，只 warn 唔 fail；
   英文句號 `.` 刻意唔剝，避免動到 `Mr.` 呢類縮寫）。

**理由（實測，2026-10-29 林家謙《普渡眾生》MV，23 行 / 169 詞 / 32 個標點）**

| 證據 | 數字 |
|---|---|
| 舊 `max_chars` 切法錯位 | 4 處（`…分叉的走`／`馬路，…`、`…偏偏起`／`了一次…`、`…世塵`／`傷感。`、跨 sentence 砌行 `…遺憾中，`／`普渡的眾生`），仲製造 2 字殘行 `不能。`／`傷感。` |
| 純按標點分句 | 32 個分句、**最長 13 字、最短 4 字**，全部 < 18 → 兜底完全唔使觸發 |
| ASR sentence 邊界 | 15 句入面 14 句本身以 `。`／`？` 收尾（同標點斷點高度重疊） |
| 標點唔影響時間軸 | `punctuation` 喺 ASR **冇獨立 begin/end**，剝唔剝都唔使改任何 `\kf` / `hold_ms` |
| v1 相容驗證（probe16） | 169 詞標點全數拆返出嚟、CharSlot 時間軸 **0 drift**；`--keep-punctuation` render 出嚟 Dialogue **byte-identical** |
| 新斷句驗證 | 32 行全部 ≤18 字、顯示文字 0 標點、4 個錯位全數修復、`break_reason` 全部 `punctuation`（兜底零觸發） |

**被駁回的選項**

- **`max_chars` 做主、標點只係建議** —— 實測標點分句天然就 fit（最長 13 字），而 `max_chars` 先至係錯位切法嘅元兇。
- **淨係句末符號（。！？）斷行** —— 會放棄好多好斷點，出 13 字以上長行。
- **短句一律向前合併** —— 句末短樂句（如 `好冇。`）會俾人拉咗入下一句，聽感割裂；分方向先至語義正確。
- **Stage 6 直接掉咗標點** —— timings.json 永久失去標點資訊，日後 UI 想還原／顯示都冇得返轉頭。
- **保持 v1 格式加冗餘字段** —— `text` 會有歧義（含唔含標點？），寫入讀取容易重複剝。

**後果**

- **ASR 標點擺錯位會照錯位斷行**（實測有 `揮之不能徘徊，` 呢類）—— 固有風險，algorithm 層減唔到；
  靠 `break_reason` 記錄 + 日後字幕編輯 UI 人手改（同 ADR-011/012 方向一致）。
- `WordGroup.text` 語義改變（唔再含標點）；`LyricLine.text` 係純字，**顯示一律行 `display_text()`**。
- 渲染時插空格 + `\k` 要將 `prev_end` 更新為下一詞 `begin_ms`，否則會重複插 `\k`、停頓雙倍（probe16 已驗證）。
- 短句合併後行中可能有多於一個空格（連鎖合併），屬預期行為。
- 驗證腳本：`_probe/probe16_punct_split.py`（25 項全 PASS）。

**修訂（2026-10-29 同日，實測《每當變幻時》後）**

1. **短句門檻放寬**：`min_clause_chars` 3 → **5**、`min_clause_ms` 1500 → **2500**——

3. **`_kind()` 標點優先過 `sentence_end`**：word 自帶標點先至決定 hard/soft，

4. 驗證：probe16 加 (c2)/(g1)/(g2) 三個 case，**28 項全 PASS**；

5. 已知殘留：ASR 喺 `逝去了的` 後面放 `。`（hard）→ 按規則向後併落
   `韶華去 四季暗中追隨` 尾，同樂句唔夾 —— 屬 R1 標點擺錯位固有風險。

## ADR-016 · 預覽／時間軸分界改「像素制」，波形高度改「目標值 + 夾高」（2026-11-02）

### 狀態
✅ 已採納（最終定案：sidebar 160px／左欄 386px（歌詞樹 5 欄 370px）／品牌兩行 15px／
預覽 +80px → 波形 192px、字塊 33px）

### 背景
1. **比例制**下 `_preview_ratio = 0.55` 只保證「大約」，任何視窗高度變化都會令 +100px 走位；
   用戶要求嘅係**實數**（預覽加、時間軸減），比例制做唔到。
2. **物理衝突**：1920×1009 視窗下右欄高 899px。時間軸畫布高 = 窗格 − 52px（標題＋zoombar）。
   「波形 128→192（+50%）＋字塊 22→33（+50%）」要
   `20(刻度)+192+4+33+16(概覽) = 265px` 畫布高 → 對應時間軸窗格 317px（= −80px）。
   所以 **預覽 +80 / 時間軸 −80** 先可以同時滿足「波形 +50% ＋ 字塊 +50%」；
   一開始試 +100 只做到波形 172px（+34%），差 20px 擠唔落。

### 決策
- `editor._preview_h` 改**像素制**：首次量度 = `int(右欄高 × 0.55) + PREVIEW_EXTRA_H(80)`，
  之後拖曳直接改像素；夾 `[120, 右欄高 − MIN_TIMELINE_H(200)]`（等價於舊有 30%–75% 保護）。
- `timeline.WAVE_H = 192` 係**目標值**，`_wave_h_for()` 夾成
  `min(192, 畫布高 − 刻度 − 概覽 − 4 − 一條 LANE_H)`：「先保證有一行字幕塊，剩落嘅全畀波形」。
  317px 窗格下剛好食到 192px（不再縮水）；若用戶日後拖矮時間軸，波形會自動讓位而唔會蓋住字塊。
- 字塊 `LANE_H 22→33`、`BLOCK_GAP 6` → 方塊高 18→27（+50%）。
- 字塊 lane 下限由 2 改 1：時間軸變矮之後強行留 2 行只會浪費；行與行本身唔重疊，
  first-fit 實際上永遠用第 1 行（同改動前觀感一致）。
- 圖例由獨立一行搬上 `_tl_box` 的 LabelFrame 標題，回收 ~20px 垂直空間畀波形。
- sidebar 總寬 200 → **160px**（`SIDEBAR_MIN_W` 160→140，仍可拖曳）。
- 品牌方塊 `Karaoke AI Subtitler` **分兩行**（`Karaoke` / `AI Subtitler`），11pt（≈15px @96dpi）；
  一行要 146px，160px 欄減 padx/內距只剩 134px，一定爆格。窗口標題同步改 `Karaoke AI Subtitler`。
- 左欄 260 → **386px**：歌詞樹 5 欄總寬鎖 **370px**（32+174+66+66+32），
  加 scrollbar 8 + LabelFrame 邊框/內距 8 = 386，五欄一欄都唔裁。
  逐字微調「詞」欄 64→140。

### 影響

  `ui/pages/editor.py`（`LEFT_W`／`PREVIEW_EXTRA_H`／`MIN_TIMELINE_H`／`_clamp_preview_h`／圖例位置）、
  `ui/widgets/timeline.py`（`WAVE_H`/`LANE_H`/`BLOCK_GAP`/`MIN_WAVE_H`、`_wave_h_for`、`_lanes_y_top`）、

## ADR-017 · 導航字級要經 ttk style；顏色色塊改 grid + 雙重上色（2026-11-02）

### 狀態
✅ 已採納（用戶需求：sidebar 160→140px、導航按鈕字級 +2、色塊顏色要同選取一致）

### 背景
1. **ttk::button 冇 `-font` option**（唔似 tk.Button）：`ttkb.Button(..., font=...)` 直接
   拋 `_tkinter.TclError: unknown option "-font"`。字級一定要經 `ttk.Style().configure(style, font=...)`。
   但 `bootstyle="primary"/"secondary"` 每次切頁都會改寫 widget 嘅 `style`，
   想「只在導航按鈕加大字」就唔可以只設一次。
2. **色塊唔跟選取色**（用戶附截圖回報）：原本用 `pack` 排「色塊 + hex 輸入框」，
   視窗一窄，pack 會先壓細第一個子元件 → 色塊縮到睇唔到（或只剩一兩 px），
   而 hex 輸入框照樣顯示新色 → 用戶見到「色塊同揀嘅色唔一致」。
   另外舊 code 只寫 `canvas["bg"]`，而且只 catch `ValueError` ——
   Tk 對 `#0000F` 呢類 5 位 hex 會拋 `TclError`，令色塊靜靜停留在舊色。

### 決策
- 導航按鈕改自訂 style：`Nav.TButton`（未選中）／`NavActive.TButton`（當前頁），
  兩者 `font=(ui_font, 11)`（主題預設 9pt +2），顏色用專案色票
  （`BG_HOVER` / `ACCENT`），切頁時切 style 而唔再切 `bootstyle`。
- 色塊 cell 由 `pack` 改 `grid`（label 跨兩欄、色塊 column 0、輸入框 column 1），
  子元件唔會再被擠到消失。
- 新增 `_set_swatch(key, color)`：**Canvas 背景 + 填滿嘅 rectangle item** 雙重上色；
  `color=None`（輸入未合法）就保留舊色並把邊框轉紅，唔會出現「輸入新色、色塊舊色」。
- 新增 `_normalise_hex()`（regex `^#?[0-9a-fA-F]{6}$`）：接受冇 `#`、大小寫混寫；
  輸入框失焦／Enter 時寫返 `#RRGGBB`，所以文字同色塊一定對得上。
- sidebar 總寬 160 → **140px**（`SIDEBAR_MIN_W` 140→120）。

### 影響
- `ui/theme.py`（`SIDEBAR_W`）、`ui/app.py`（`_nav_styles`、`NAV_FONT_SIZE`、切頁改用 style）、
  `ui/pages/home.py`（`_HEX_RE`／`_normalise_hex`／`_set_swatch`／`_normalise_entry`／色塊 grid 化）。

### 驗證
`_probe` 實機截圖：sidebar 140、品牌兩行、4 顆導航 11pt 無裁切、當前頁藍底深字；
主頁色塊 #00FFFF / #FF8800 / #000000 與輸入完全一致；
`#1234`（未打完）→ 保留舊色 + 紅框；`FF8800`（冇 `#`）→ 認得並上色。
`tests/test_editor_core.py` 26 checks PASS。

## ADR-018 · UI 轉淺色主題；設定頁改 grid；說明頁書面語化（2026-11-02）

### 狀態
✅ 已採納（用戶需求：litera 配色不美觀 → 要白底黑字；設定頁字細又縮中間；說明頁字級不一致、內容要書面語、CLI 說明不足；undo/redo 要 hint；平移 slider 拆走）

### 背景
1. **原本 UI 全部寫死深色**：`bootstyle="dark"` 73 處 + `theme.py` 深色票（#16161d 等）+

- 全 UI `bootstyle="dark"` → `"light"`；`theme.py` 亦一併 configure `dark.*` variant，
  避免殘留舊樣式。
- **`apply_ttkbootstrap_theme()` 於 `_build_pages()` 之後再呼叫一次**（idempotent）：
  這樣 variant style 已存在，覆寫才生效（卡片邊框、輸入框底色）。
- 具名字型 `TkDefaultFont` 等統一 10pt（原本 9pt）→ 全 app 字級不再過細。
- 設定頁改 **grid 兩欄**（標籤 10 字位固定 / 輸入 `sticky="ew"` 拉滿 / 按鈕靠右），
  左右留白 48px；外觀一節改為固定淺色的唯讀說明（移除 darkly/superhero/litera 下拉，
  避免再出現「深淺混搭」的破版狀態）。
- 說明頁：「章節」標題與樹項皆 12pt（內容 base 12pt）；`docs/使用說明.md` 全文改書面語，

## ADR-022 · 版本護欄：打包／推送前檢查 VERSION 有無跟住 code 升（2026-11-02）

### 狀態
✅ 已採納

### 背景
ADR-021 定下「`VERSION` 係版本號唯一真源」，但真源係**人手改**的。同日實測撞板：
另一個對話改好快捷鍵並 commit（`3ea0fa1`），**冇升 VERSION**；若直接打包就會出
「zip 叫 1.0.0、內容已變、程式自報 1.0.0」——同事回報問題時，你問「跑邊版」他答
1.0.0，你分唔清係修之前定修之後。

### 決策
1. **邏輯獨立成 `tools/version_guard.py`**（只讀 git，唔改任何檔），兩處共用：
   - `tools/build_release.py`：打包前必跑
   - `tools/hooks/pre-push`：推送前跑（靠 `core.hooksPath=tools/hooks`）
2. **只用 git 事實判斷**：基線 = 最後一次改動 `VERSION` 的 commit；基線之後若有
   commit 改過**非文件**檔案 → 警告。
   **唔用** mtime／「隔幾耐」／commit 數 —— clone、換機、補 commit 都會誤報。
3. **預設只警告**：`--strict` 才 `exit 1`；hook 預設 `exit 0`（要硬擋自行改一行）。
   理由：docs-only 改動、hotfix 試跑唔應該被鎖死；真正漏升版時，人眼見到警告就會停手。
4. **忽略清單**：`docs/`、任何 `*.md`、`VERSION`、`.gitignore`、`.gitattributes`。
   `requirements.lock.txt` **不忽略** —— 它會改變同事端的安裝結果，屬交付內容變更。
5. **非 git 環境靜靜跳過**（同事手上的 zip 冇 `.git`），唔應該噴錯阻住流程。

### 踩到的坑（值得記）
- **`git diff --name-only` 會把非 ASCII 路徑輸出成 C 式轉義**（`"docs/\346\236..."`，
  連引號），令 `startswith("docs/")` 失效。本專案 `docs/` 全部中文檔名，冇處理就會
  誤報「改過程式碼」。修法：`git -c core.quotePath=false`，比對前再 `strip('"')` 保險。
  （由 `tests/test_version_guard.py` 第 6 個 case 抓到，唔係靠肉眼。）
- **hook 不能帶 CRLF**：本機 `core.autocrlf=true`，下次 checkout 會把
  `tools/hooks/pre-push` 轉成 CRLF，`sh` 會爆 `$'\r': command not found`。
  → `.gitattributes` 加 `tools/hooks/* text eol=lf`。

### 影響
新增 `tools/version_guard.py`、`tools/hooks/pre-push`、`tests/test_version_guard.py`；
修改 `tools/build_release.py`（匯入 + 打包前檢查 + `--strict`）、`.gitattributes`、`DEPLOY.md`；
本機 git 設定 `core.hooksPath=tools/hooks`（屬本地設定，唔入 repo）。

### 驗證
- `tests/test_version_guard.py`：**8 checks ALL PASS** —— 基線通過／未升版只警告／
  `--strict` 擋下／升版後通過／只改 md 唔算／只改 `docs/` 唔算／改 lock 算／非 git 跳過。
  每個 case 開獨立臨時 repo，唔污染本專案。
- 本專案實跑：`[version] OK：VERSION 1.0.1 對應最新 commit`。
- hook 實跑：`sh tools/hooks/pre-push` → rc=0；`git ls-files --eol` 確認 `i/lf w/lf`、
  索引 mode `100755`。
- **真實 push 已驗證（2026-11-02）**：首次推送 `origin/main` 到
  `github.com/hklamsir/karaoke` 時，git 輸出的第一行就係
  `[version] OK：VERSION 1.0.2 對應最新 commit` —— 證明 hook 經 `core.hooksPath`
  正常掛上並執行（原本標記「未實測」，現已補上實證）。
- 附帶學到（值得記）：**fine-grained PAT 的 `permissions` 欄位會誤導** ——
  `GET /repos/{owner}/{repo}` 回 `"push": true` 只代表**帳號**對該 repo 有權，
  唔代表 **token** 有 Contents 寫入權。public repo 更甚：匿名都讀得到，`GET` 成功
  完全唔能夠當作有權限。
  診斷法：`POST /repos/{owner}/{repo}/git/blobs` 建一個 dangling blob（唔會產生
  commit、唔改內容）——403 `Resource not accessible by personal access token`
  即證明 token 範圍不足；空 repo 會回 409（代表已過授權層，只係冇 HEAD 可依附）。

### 修訂（2026-11-03 · v1.0.3）：警告只列真正動過 code 的 commit

**症狀**：只改 `requirements-ui.txt` 一個註解，push 時警告卻寫「之後有 **9 個** commit
改過程式碼」，並列出 8 個純文件 commit（README、ADR）。

**成因**：判定用 `code_changes_since()`（已過濾 docs／`*.md`／`VERSION`），但列印時用的
是 `commits_since()`（基線後**全部** commit），兩者沒有共用同一層過濾。屬訊息層缺陷，
不會誤擋，但會讓使用者漸漸無視警告 —— 護欄一被無視就等於失效。

**修法**：新增 `commits_with_code_changes()`，以
`git log --format=%x01%h%x09%s --name-only <baseline>..HEAD` 一次取回每個 commit 的
改動檔案，逐個套用同一套 `_is_ignored()`，只有含非文件檔的 commit 才列出。
用 `%x01`（SOH）作分隔符 —— git 路徑不可能含此字元，比用空行切更可靠。
`check_version_bump()` 的計數與清單一律改用 filtered 結果。

**已知取捨**：合併 commit 在 `--name-only` 下不帶檔案清單，因此不會被列出；它帶入的
改動已由被合併的個別 commit 反映，實務上不影響判斷。

**驗證**：`tests/test_version_guard.py` 由 8 → **13 checks ALL PASS**，新增 5 條回歸
（混合 commit 只列 1 個、列出正確對象、計數用 filtered 數量、不列純文件 commit、
仍列出真正動 code 的 commit）。本專案實跑由「9 個」修正為「1 個」。

## ADR-024 · 錯誤改用例外階層（KaraokeError 家族）；CLI 退出碼不變（2026-11-03）

### 狀態
✅ 已採納（v1.0.4 之後；與 v1.0.5 一併出包）

### 背景
v1.0.4 之前，所有可預期錯誤都由管線函式直接 `sys.exit(N)`（共 17 處）。三個問題：

1. **與 CLI 綁死**：`main.py` 的函式同時是「可被 UI import 的 API 層」，但 `sys.exit`
   會直接結束進程；UI 只能靠 `except SystemExit` 接，拿到的是 `exc.code` 一個整數，
   完全唔知發生咩事。
2. **無法分辨**：收到 3 唔知係「抽音失敗」定「人聲標準化失敗」；收到 2 唔知係
   「缺 ffmpeg」定「缺 API key」。
3. **測試只能斷言 `SystemExit`**：對「錯誤類型」零保證 —— 重構時把 code 由 3 改成 4
   都唔會紅（審查報告 §2.9）。

### 決策
新增例外階層，每個 `code` 與舊 `sys.exit(N)` 逐一對應：

| 類別 | code | 觸發點 |
|---|---|---|
| `KaraokeError` | 1 | 基底；亦用於無法歸類者（`code=` 覆寫） |
| `UsageError` | 2 | 缺 API key、禁用 model、輸入／字幕／timings 不存在、壞色碼 |
| └ `ToolMissingError` | 2 | 缺 ffmpeg / ffprobe / audio-separator |
| `AudioExtractionError` | 3 | 抽音、人聲分離、人聲標準化失敗 |
| `AsrError` | 4 | 提交／輪詢／逾時／subtask 全失敗 |
| └ `NoSubtitlesError` | 4 | 冇 `transcripts`、斷句後零行 |
| `BurnError` | 5 | ffmpeg 燒錄失敗 |

三個取捨（都是刻意，唔係順手）：

1. **`UsageError` 是最初契約之外多加的一層**。code 2 有 6 個觸發點，全部屬「用戶改
   設定即可解決」；若用裸 `KaraokeError(code=2)`，callers 無法分辨「用法錯」與
   「未歸類錯誤」，等於白做一層階層。`ToolMissingError` 掛在它下面 —— 同屬 code 2，
   但訊息要教安裝方法，所以獨立成子類。
2. **`NoSubtitlesError` 繼承 `AsrError`，唔直掛基底**。兩者成因同屬「ASR 冇畀到可用
   內容」，呼叫方可以只 catch 父類一次過處理，減少分支。
3. **例外訊息只放短句**。詳細 stderr / JSON 仍然由 `LOGGER.error()` 輸出。訊息會
   直接顯示在 UI 對話框，塞 2500 字 stderr 會爆窗；`tests/test_error_taxonomy.py`
   有斷言鎖住「單行、≤120 字」。

轉換層：`main()` 加 `except KaraokeError → return exc.code`。因為每個拋出點仍然先
`LOGGER.error()`，**CLI 的輸出與 v1.0.4 之前逐字相同**，只是不再 `sys.exit`。
UI 兩個呼叫端（`home.py`、`editor.py`）保留 `except SystemExit` 作為第三方套件的
保險，但自家錯誤已改由 `except Exception` 分支顯示可讀訊息 ——
由「exit code 3，詳見 log」變成「ffmpeg 抽音失敗（rc=1），詳見 log」。

### 影響
- `Raises` 由 `SystemExit` 改為上述類別：`generate_timings()`、`burn_video()`、
  `burn_subtitles()`、`find_ffmpeg()`、`find_ffprobe()`、`extract_temp_audio()`、
  `separate_vocals()`、`submit_and_wait_transcription()`、`parse_asr_result()`、
  `resolve_api_key()`，以及 `cmd_burn` / `cmd_render` 的前置檢查。
- **CLI 退出碼完全不變**（2/3/4/5），CI 腳本與同事的 `.bat` 無需改動。
- **UI 錯誤訊息變短且具體**（行為改善，非破壞性變更）。
- `_probe/probe*.py` 若直接呼叫這些函式，失敗時會出 traceback 而唔再靜靜 exit ——
  屬本機開發腳本，可接受（未改）。

### 驗證
- `pytest tests -q` → **91 passed / 13 xfailed**（重構前：66 passed / 17 xfailed）
- 4 條契約測試由 `XFAIL` 轉 `XPASS`（strict 機制逼使拆標記，已拆）：
  `AudioExtractionError`、`ToolMissingError`、`NoSubtitlesError` ×2
- 新增 21 條測試鎖住：7 個 `code`、6 條繼承關係、「全部係 `Exception` 唔係
  `SystemExit`」、`code=` 覆寫、4 條 CLI 退出碼端到端、1 條訊息長度
- 實機 CLI（獨立進程，非 in-process）：`generate` / `burn` / `render` 缺檔 → exit 2；
  `render` 正常 → exit 0

## ADR-025 · 修復審查報告全部 P0/P1：取消、原子寫入、跨磁碟、UI 防呆、長片記憶體（2026-11-03）

### 背景

`docs/代碼審查報告.html` §11 列出 9 項 P0/P1。其中 3 項已於前一輪處理完（§2.2 測試基建、
§2.7 escape 跳脫、§2.9 `KaraokeError` 家族）。本 ADR 收剩下的 6 項，連同 §9.2 遺留的
兩個契約（9.2-1 全靜音、9.2-12 重複提交）。

6 項的共同點：**失敗時畫面冇反應**，用戶無從排查 —— 燒錄跨碟直接 traceback、
輪詢鏈默默疊加、Tk callback 內的 `ValueError` 只去 stderr、取消只能殺程式、
長片 OOM、中斷後半截 JSON。所以修法都圍繞「失敗要麼講清楚，要麼唔會發生」。

### 決策

#### 1. 取消機制（§2.3 P1 / 9.2-11）

- `TaskCancelled` **刻意唔繼承 `KaraokeError`**。若繼承，`main()` 的
  `except KaraokeError → return exc.code` 會把「用戶主動取消」變成非零退出碼，
  即「我唔想等」= 「程式出錯」。取消不是錯誤。
- `GenerateOptions.cancel_event` 用 `field(default_factory=threading.Event)`，
  不用 class-level `threading.Event()`。後者會令**所有** options 共用同一個
  Event：取消一次之後，之後每次 generate 一開波就即刻被取消（`test_cancel_event_is_per_instance`。
- 檢查點放在：ASR 輪詢**每一圈的最頂**（不是尾部 —— `fetch` 本身可能慢幾秒）、
  各階段之間（抽音／人聲分離／上傳／斷句）、以及**寫檔之前**（避免只寫出 ass
  冇 json 的半完成產出）。
- 燒錄由 `subprocess.run` 改為 `Popen` + poll 迴圈 + `terminate()`（5 秒唔死就 `kill()`）。
  `stderr` 導向**臨時檔**而唔係 `PIPE`：poll 期間冇人讀 pipe，寫滿 64KB 緩衝就會
  死鎖 —— 變成「取消都取消唔到」。
- 取消後刪除半截輸出 mp4。刪不到（被播放器鎖住）只記錄警告，**照拋
  `TaskCancelled`**，唔可以讓 `OSError` 蓋掉取消語義。
- UI 用**獨立**「✖ 取消」按鈕，唔用「已經 disabled 的開始按鈕」兼職。誤按代價太大
  （中止一個已經跑了幾分鐘的 ASR 任務），而且 disabled 按鈕本來就收不到點擊。
- `ThumbCache.cancelled` 由死代碼接線：換片時把上一條 `_thumbs_task` 設
  `True`。為此 `PreviewPane` 新增 `_thumbs_task`（`_thumbs` 只在完成後才賦值，
  捕捉不到「正在跑」那個）。

#### 2. 單飛閘（9.2-12）

`main.SingleFlight`：`Lock.acquire(blocking=False)` 保證原子性，取代
`home.py` 的 `_running` 布林旗標。布林旗標是 check-then-act，兩條 thread 同時
讀到 `False` 就會一齊過關（TOCTOU），而「重複提交」正是併發問題。

`__exit__` 無條件 `release()`；重複 `release()` 拋 `RuntimeError`（同
`threading.Lock` 一致）—— 靜默成功會令閘門在仍有任務時被放開，防護失效且無徵狀。
`locked` 屬性只供顯示，唔參與判斷（Lock 無法原子查詢狀態）。

#### 3. 原子寫入（§2.8 P1）

`main.atomic_write_bytes / text / json`：同目錄 `.tmp` → `os.replace`。
覆寫前留 `.bak`（沿用 UI 既有約定：覆寫後才發現有問題時仍有上一版可救）。

- `ui/models.atomic_write_json` 改為**委派**（延遲 `import main`）。以前 UI 有 `.bak`、
  CLI 完全冇，兩份實作已經開始分叉。
- 為何唔新開 `io_utils.py`：`build_release.py` 的 `TOP_FILES` 是白名單，新增根目錄
  模組若漏加，交付包會 `ModuleNotFoundError`（上一輪 `tests/fixtures/*.json`
  就是同類事故）。等到 PR-2 拆 `karaoke/` package 時再搬去 `karaoke/io.py`。
- 沒有循環 import：`main` 不 import `ui`；`ui.models` 是延遲 import，module 載入時
  唔會拉入 CLI。

#### 4. 跨磁碟區 `relpath`（§2.1 P0）

`_rel_or_abs()`：`os.path.relpath` 拋 `ValueError` 時退回 `os.path.abspath`。
只用在 `-i` 與**輸出檔參數**；`-vf ass=<檔名>` 仍然用「`cwd` + 純檔名」（ADR-006），
因為只有 filter 內容才怕 `C:` 的冒號。

`MV 放 D:/、字幕輸出 C:/` 是常見配置，以前直接 traceback —— 屬「特定但常見」。

#### 5. UI 兩個 P0（§2.4 / §2.5）

- `_ensure_polling()` 冪等：旗標 + 只在 `_poll_position` 內自我重排。**引擎消失時必須
  清旗標**，否則鏈條斷了之後永遠唔會再啟動（換片後游標不動，另一種 bug）。
- `_adv_int(key, default)` 取代 6 處裸 `int(...)`，並在 `_start_generate` 外層包
  `try/except → messagebox`。Tk callback 內的例外只會去 stderr，用戶見到的是
  「按了按鈕冇反應」。

#### 6. 長片記憶體（§2.6 P1）

`MAX_PCM_SECONDS = 1800`：超過就只串流掃 peaks（每段 5 秒 = 80000 samples = 1000 bins，
剛好整除 80 samples/bin，最後一段以外無 padding，串接後等同一次過處理），
`_pcm` 清空、`playback_degraded = True`。一小時：peaks 約 2.9 MB，而非 115 MB。

- 為何唔用 `pygame.mixer.music` 串流：要重寫 play / seek / loop / play_range 全部
  播放邏輯，而 >30 分鐘的 MV 屬少數。本 ADR 只解決記憶體，唔順手改播放架構。
- UI 必須明示「長片模式」（狀態行 + 按播放時的對話框），否則用戶會以為播放壞了。
- `load()` 開頭重設 `playback_degraded = False`：呢個是 instance 狀態，換片唔重設
  會「一次載過長片，以後全部冇聲」。

#### 7. 全靜音偵測（9.2-1）

`main.detect_silent_wav()` 用 stdlib `wave` 逐段讀樣本（4 秒一段，門檻 int16=32 ≈ −60 dBFS），
`generate_timings` 命中時 `LOGGER.warning`（**唔 raise** —— 全靜音 MV 可能係用戶
刻意測樣式；而 ASR 之後一定回空結果，硬 raise 只會擋死合理流程）。

- 為何唔放 `ui/audio.py` 的 peaks 層（報告字面建議）：`generate` 管線根本唔 import UI，
  警告掛在那裡等於 CLI 用戶永遠見唔到 —— 同 §2.3 的「死代碼」是同一種錯誤。
- `_output_get()` 順手統一 dashscope 回應讀法：提交路徑用屬性、輪詢路徑用 mapping，
  同一個欄位兩套寫法；真實回應是 DictMixin 兩種都通，但 fake 只給其中一種。

### 刻意唔做

## ADR-026 · 逐字時間改用時間碼 + 跨字均分／修補（2026-11-03）

### 問題（用戶實測第 39 句）

1. **AI 漏詞，程式唔識補**：ASR 只吐 word 級時間，`word_slot_to_group()`
   （`main.py:968`）只在**詞內部**按字數平分，`estimated=True` 就係呢個意思。
   一旦整段詞被漏掉（「那裡保證何時能突破」），呢 8 個字擠喺 3:41.995–3:42.958
   （每個 ~107ms），而 `respread_word()`（`models.py:266`）只作用於單一個 word
   內部 —— 跨詞的缺口永遠冇人填。用戶手動把「破」的結束時間改成 3:53.158
   之後，中間 7 個字仍然原封不動。
2. **存檔時 normalize 反咬**：N4（`models.py:301`）見到 `begin < last_end` 就夾
   返 `begin`，再 `end <= begin → end = begin + 1`，於是重疊字被壓成 1ms，
   睇落更似「程式冇反應」。
3. **純毫秒唔人性化**：面板直接顯示 `221995`，用戶要心算「呢個字喺曲中第幾分
   幾秒」；`editor.py` 明明已經有 `_fmt_ms()`，但只用喺狀態列。

### 決策

| 項目 | 決定 | 理由 |
|---|---|---|
| 時間格式 | `3:41.995`（m:ss.mmm；過 1 小時自動 `1:03:41.995`） | 最短、最易讀，左欄唔使加闊；`03:41.995` 多佔 10px 冇額外資訊 |
| 輸入 | `timefmt.parse_time()` 接受 4 種寫法 | 新格式好用，但**純整數仍然當毫秒** —— 舊用戶肌肉記憶唔可以斷 |
| 編輯行為 | 改一個字只改嗰個字，另設 `⊞ 均分` / `⊞ 全段` / `✚ 修補` | 自動重攤會覆蓋用戶先前逐字對好的結果；可控性 > 少撳一下 |
| 均分預設 | **保留首末字**，只攤中間 | 用戶的實際流程係「先用耳對好尾字，再攤中間」，錨點係人手量度出嚟的事實 |
| 修補判斷 | 最長字 > `max(6 × 中位數, 1500ms)` → 整行重攤 | 漏字的真實徵狀係「一堆 107ms 字 + 一個 10 秒字」，逐字判斷捉唔到（中間字個個都 > 1ms），只有睇分佈先捉得到 |

### 補記 2（2026-11-05）：箭頭要用 Canvas 畫，同埋「連動順延」

**（一）`▲` / `▼` 字元唔可靠**

- 用戶實測：「繪畫的箭咀不是 ▲▼ 的樣子」。U+25B2/25BC 喺 Windows 會 fallback
  去另一個字型，出到嚟係實心方塊或者大小走位，同 ttk 按鈕邊框又唔夾。
- 改法：`TimeSpinbox` 改用 **Canvas 畫兩個多邊形**（上／下各一，中間一條分隔線），
  闊度 `ARROW_W=15px`、高度跟 Entry 的 `winfo_reqheight()`，並支援 hover 高亮。

- Canvas 唔會跟 ttk style 自動變色 → `EditorPage.restyle()` 要叫 `spin.restyle()`。

**（二）改時間撞到鄰字，要唔要自動推開？**

用戶提問：「前一個字的結束時間超過下一個字的開始時間，是否要自動把後面所有字
順延？反過來把開始時間拉前，是否要把前面的字向前移？」

- **決定：做，但預設關，由面板「連動」開關控制，並記入 `settings.json`。**
- 為何唔預設開：**音軌係事實，字幕只係描述**。自動推開會默默改掉用戶已經用耳
  對好的鄰字（甚至整句），而連鎖推會令整句慢慢偏離音樂；錯咗又好難察覺（畫面
  只係數字變咗）。預設「只改嗰個字 + 提示重疊」最安全，要推就自己開。
- 為何仍然要做：漏字、插入字、整句改長度時，逐個字搬係体力活。開關一開就
  一次過推好，而且**一次 push = 一個 undo 步驟**（`SetCharTimingRipple`）。
- 對稱處理：尾邊超出 → `shift_range(i+1..last, +overlap)`；頭邊超前 → `shift_range(0..i-1, -overlap)`。
- 夾邊界：向前推最多推到 0。唔夠位就**夾住自己**（`begin = prev_end - 可移距離`），
  寧願拖唔到盡，都唔好出負時間或者靜靜留低重疊 —— 手感同「拖到牆就停」一致。
- 字距保持：`shift_range()` 整段平移，唔重新分配（重新分配係「均分」掣的工作）。
- 提示列會講返實際做咗乜：「其後順延 +50ms」／「其前前移 -110ms」／
  「⚠ 與鄰字重疊 50ms（開「連動」可自動推開）」。

**驗證**：`tests/test_time_spinbox.py` 加到 13 條（新增連動四條：關閉時鄰字不動、
向後順延、向前前移、推到 0 就停）。全套 **170 passed**。UI 探針量度：時間欄那一行
reqwidth 248px（比用兩個按鈕時少 106px），左欄可用 378px。

## ADR-027 · 雙行歌詞：奇數句固定上行、偶數句固定下行，每行隔兩句才換（2026-11-09）

**狀態**：✅ 已接受

**背景**

用戶要求做到《舊夢不須記》卡拉OK 原片的效果：畫面固定兩行，進入下一句 1 秒後，
「上一句」被「再下一句」取代。逐幀核對原片（1920×1080 / 25fps）確認：

| 時間 | 上行 | 下行 |
|---|---|---|
| 18s | 舊夢不須記（白＝已唱） | 逝去種種昨日經已死（藍＝未唱） |
| 24s | 從前人妙 隨夢境失掉（藍） | 逝去種種昨日經已死（唱緊） |
| 27s | 從前人妙 隨夢境失掉（前半白） | 莫憶風裡淚流怨別離（藍） |
| 33s | 舊事也不須記（藍） | 莫憶風裡淚流怨別離（白） |

即：**上行永遠放第 1、3、5… 句，下行永遠放第 2、4、6… 句**；每句喺「下一句開唱
+1000ms」時被同行的再下一句取代。

**決策**

- `StyleConfig` 加 `dual_line` / `switch_delay_ms`（預設 1000）/ `line_gap`（0 = `font_size × 1.45`）。
  三個欄位只喺 `dual_line=True` 時寫入 `timings.json`，**單行輸出維持 byte-identical**。
- 每句仍然只產生 **1 個 Dialogue**（唔拆兩個 event），用 `\an2` + `\pos(x, y)` 固定行位：
  `y_down = PlayResY - margin_v`、`y_up = y_down - line_gap`。
- 顯示窗口（`_dual_line_window`）：
  `start = 0`（前兩句）或 `lines[i-1].start_ms + delay`；
  `end = lines[i+1].start_ms + delay`（最後一句用 `line.end_ms`）。
- 預覽期（event 早過第一字）用前置 `{\k<gap>}` 佔住時間軸，令 `\kf` 準時啟動 ——
  同 C-5 停頓補償係同一招，只係由「字與字之間」擴展到「行首」。
- UI 預覽 `overlay.draw_dual_subtitle()` 用**同一條窗口規則**，否則編輯器所見非所得。

**為何唔拆兩個 event**

一句只喺一行出現，event 數同單行一樣（N）。傳統「上下兩行都顯示當前/下一句」的做
法要每句拆兩個 event（2N），先可以喺中途換字；呢個設計用唔著，libass 負擔最細。

**邊界**

- 句距 < `delay`：窗口會 `end <= start` → 把 `start` 移前到 `line.start_ms`，
  **寧願本句遲少少出，都唔好同一行兩個 event 疊字**。
- 最後一句冇「下一句」→ `end = line.end_ms`。
- 編輯器改斷句後，句子索引會整體位移 → 每次 `render` 即時按 `lines[]` 計，**唔可以寫死**。

**驗證**

`sample_v3.json`（12 句）雙行輸出時間窗與原片一致；1080p 黑底實燒 18/24/27/33 秒
截圖對比，兩行位置、逐字變色、換行時機全部對得上。

## ADR-028 · 上傳／燒錄顯示真實進度，唔再只有跑馬燈（2026-11-09）

**狀態**：✅ 已接受

**背景**

用戶回報「上傳到百煉雲／燒錄時均冇 progressbar，唔知幾時完成」。診斷出三個**獨立**
原因，任何一個都會造成「冇進度」：

1. 主頁「進度」框係右欄**最後一個** `pack()` 的 widget，右欄冇 scroll → Tk 空間不足
   時直接裁走（同 `burn_dialog.py` 踩過嘅坑一模一樣）。
2. `StageProgress` 對「有 message 的 active 階段」刻意設做 `indeterminate`（跑馬燈）。
3. 上傳同燒錄**根本冇進度資料源**。

**決策**

| 位置 | 做法 |
|---|---|
| 燒錄 | `ffmpeg -progress <tempfile> -nostats`，poll 迴圈每 0.2 秒讀 `out_time_us`，除以 ffprobe 總時長 |
| 上傳 | 自建 multipart POST（`requests`），file-like 分塊讀取、累加位元組回報百分比；失敗**自動 fallback** 去 `dashscope.Files.upload` |
| UI | `StageProgress.set_fraction(pct)`：餵過真百分比後保持 determinate，唔會被同階段的 `report()` 打回跑馬燈 |
| 佈局 | 主頁進度框改 `side="bottom"` **最先** pack，確保永遠可見 |

**理由**

- `-progress` 寫**臨時檔**而唔係 pipe：沿用 ADR-025 的教訓 —— poll 迴圈期間冇人讀
  pipe，ffmpeg 寫滿 64KB 緩衝就會死鎖，連取消都取消唔到。
- 自建上傳：`dashscope 2.0.3` 的 `Files.upload` 喺 `_upload_form()` 一次
  `content = f.read()` 讀完整個檔才交畀 transport，**中間冇任何回調點**；
  唔自己發請求就永遠拿唔到真進度。
- Fallback 必要：實測本機代理環境下，大 POST 到 `/api/v1/files` 會喺約 23% 被
  `ConnectionResetError(10054)` 斷線，但 SDK 路線（同樣 endpoint）成功 —— 所以
  自建失敗必須靜靜退回，唔可以令整個 generate 失敗。

**驗證**

- 60 秒黑底片燒錄：收到 17 次進度，2.2% → 100%，文字「燒錄中 0:29 / 1:00（48%）」。
- 真實 212 秒 MV 上傳：4% → 23%（代理斷線）→ 自動退回 SDK 並成功。
- `pytest -m "not slow"`：**170 passed**。

## ADR-029 · 整體時間平移 `shift_ms`，唔改 `timings.json` 原始時間（2026-11-09）

**狀態**：✅ 已接受

**背景**

用戶要求「用 480p timings 對 1080p 畫面做整體平移對齊」。實測後發現**兩版其實同步**：

| 錨點 | timings 第一字開始 | 1080p 實際（量紅色填充） | 差 |
|---|---|---|---|
| 第 1 句「舊夢不須記」 | 14.06s | 14.2–14.4s | +0.15s |
| 第 3 句「從前人妙」 | 25.63s | 25.6–25.7s | −0.03s |

差異只有 1–3 幀（25fps）。之前判成「差 1.6 秒」係**預覽方法的錯**：把 `-ss` 放喺
`-i` 前面時，ffmpeg 會把輸出 PTS 歸零，ass 由第一句重新播，看起來就像整條時間軸
提前了 —— 呢個陷阱要記住。

**決策**

仍然提供整體平移，但**只作用於 render 層**：

- `StyleConfig.shift_ms`（預設 0）；`_shift_lines()` 對所有 `start_ms` / `end_ms` /
  `chars[].begin_ms` / `end_ms` 統一加減，並 clamp 到 ≥ 0。
- 唔改 `timings.json` 的原始時間（canonical 不變）；只在非 0 時寫入 json 記住。
- CLI：`render --shift-ms -250`；UI：主頁樣式「整體平移」spinbox（±5000ms，步進 50）。

**理由**

換另一版剪輯的 MV（前奏長度唔同）時，用一個固定 offset 微調比逐句改快得多；
保留 canonical 令「換片再對」可以隨時歸零，亦唔會污染原始辨識結果。

**驗證**

`tests/test_dual_line.py` 加 3 條（平移、負值 clamp、json round-trip）；
全套 **180 passed**。27 秒實燒：新舊字幕逐字同步（見 `_probe/dual_out/ok_27.png`）。

**教訓**

用 ffmpeg 抽片做字幕預覽時，`-ss` 必須放喺 `-i` **之後**（output seek）或改用
`trim` filter；放前面會令 PTS 歸零，字幕由頭播，容易誤判成時間軸偏移。

## ADR-030 · 雙行對齊跟主頁設定；上下行可水平錯位；字型清單修復（2026-11-09）

**狀態**：✅ 已接受

**背景（用戶三個回報）**

1. 「已在對齊設定頂部置中，但字幕仍然燒錄在下方」
2. 「上方歌詞要偏左、下方歌詞要偏右」
3. 「主要可設定系統中的中文字型」

**根因（四個，其中兩個係舊 bug）**

| # | 問題 | 根因 |
|---|---|---|
| 1 | 對齊設定對雙行完全無效 | `build_karaoke_ass` 的 dual 分支硬編碼 `\an2\pos()`，**完全冇讀 `style.alignment`** |
| 2 | 冇水平錯位能力 | 兩行都用 `x = PlayResX / 2`，冇任何 offset 欄位 |
| 3 | 字型下拉永遠只有一個 | `tk_font_families_safe()` 呼叫 `tkfont._get_default_root()` —— 呢個函數**唔存在於 `tkinter.font`**（喺 `tkinter`），每次都 AttributeError 被 `except` 吞掉 → 回傳空 list → fallback 只剩 `_DEFAULT_FONT` |
| 4 | 揀了字型都「唔似」 | 實測本機**冇安裝 `Microsoft JhengHei` 本體、亦冇 `PMingLiU`**（只有 `Microsoft JhengHei UI`），libass 靜默 fallback |

**決策**

- **垂直**：dual 分支改用 `\an{alignment}`，並按 8 頂 / 5 中 / 2 底分段計 `y`：
  - 頂部：上行 `y = margin_v`、下行 `y = margin_v + line_gap`
  - 中部：中心 ± `line_gap / 2`
  - 底部：下行 `y = PlayResY - margin_v`、上行 `y = y_down - line_gap`
  - 其他 alignment 值一律 fallback 2（雙行只支援三分垂直位置）
- **水平**：新增 `up_offset_pct` / `down_offset_pct`（整數 %，畫面闊度）；
  `x = PlayResX/2 + PlayResX × pct / 100`。UI 提供「偏左(-10) / 居中(0) / 偏右(+10)」。
- **字型**：
  - 修 `tk_font_families_safe()` → `tkfont.families()`（唔傳 root），並過濾 `@` 開頭的垂直書寫重複項。
  - 清單按「常見中文字型關鍵字」分組，中文字型排前（實測 350 個字型，中文組約 20 個）。
  - 初始值同 `apply_style()` 都會對照系統清單：字型唔存在就自動改用優先序中第一個可用的
    （`Microsoft JhengHei → JhengHei UI → YaHei → PingFang → Noto CJK → PMingLiU…`），
    並寫 log，避免 libass 靜默 fallback。
- 預覽同步：`overlay.draw_dual_subtitle()` / `draw_subtitle()` / `style_preview` 全部套同一套
  垂直分段與水平 offset，否則「預覽底部、燒錄頂部」。

**理由**

對齊同位置係用戶可調的表現層設定，唔應該被 render 層硬編碼蓋過；而字型清單失效係
純 bug（私有函數用錯模組），必須修，否則「可設定字型」等於假功能。

**驗證**

- `tests/test_dual_line.py` 加 4 條（頂部 / 中部 / 水平錯位 / round-trip）；全套 **184 passed**。
- 1080p 黑底實燒（`alignment=8`、`margin_v=80`、`up=-10%`、`down=+10%`、字級 100）：
  上行「從前人渺 隨夢境失掉」偏左、下行「莫憶風裏淚流 怨別離」偏右，位置喺畫面頂部。

**注意**

`PMingLiU`（新細明體）在本機**未安裝**，原片那種明體效果要另外安裝字型或改用
`SimSun` / `FangSong`。UI 只會列出實際存在的字型，所以下拉見到嘅一定燒得出。

## ADR-031 · 歌詞提前顯示上限、倒數圓點、句尾停留新語義（2026-11-11）

**狀態**：✅ 已接受

**背景（用戶四個回報，取自《舊夢不須記》原片對照）**

1. 「在一段長時間無字幕區段，要像原片一樣不要呈現下一句，在歌詞開始時間前 3 秒才顯示」
2. 「無字幕區段進入歌詞前可加入倒數 3 個圓點（每 0.5 秒一點），好似正式 KTV 的效果」
3. 「用戶可以自訂字幕距離底部的 px」
4. 「可自訂預覽窗格的 resolution，使用戶可按輸出 video 的真實解析度預覽」

**根因**

| # | 問題 | 根因 |
|---|---|---|
| 1 | 30 秒間奏提早 30 秒見到下一句 | ADR-027 的雙行窗口 = `前一句 start + 1000ms`，**冇上限**；單行模式則完全冇提前顯示 |
| 2 | 冇倒數提示 | 功能未做 |
| 3 | 底部留白只有滑桿（0–400），打唔到準確 px | UI 缺數字輸入 |
| 4 | 預覽假設 1920×1080 並自動填滿窗格 | `_redraw_video()` 寫死 `h * 16 / 9` |

**決策**

- **窗口計算抽出單一真源**：新增 `main.compute_display_windows(starts, ends, *, lead_in_ms, dual_line, delay_ms)`。
  `main.build_karaoke_ass()` 同 `ui/widgets/overlay.py` 都呼叫它 —— 舊版 overlay 自己抄了一份
  `_dual_rows()`，係 ADR-027 講嘅「所見非所得」隱患，今次一次過消滅。
- **提前顯示上限** `lead_in_ms`（預設 3000）：
  - `lead_in_ms > 0`：`disp_start = max(0, start − lead, 同排上一句的 disp_end)`
  - `disp_end = end_ms + switch_delay_ms`，但**夾住 `starts[下一句]`**（唔可以拖到人哋開唱）
  - `lead_in_ms == 0`：完全走回 ADR-027 舊算法，輸出 **byte-identical**（回歸保障）
- **「換行延遲」語義升級**（用戶明確要求保留）：`lead_in_ms > 0` 時它 = **句尾停留**
  （最後一字後多留幾耐才清空）。長間奏自然全空，密句自然無縫。
- **倒數圓點** `compute_countdown_dots()`：3 點 × 0.5 秒，即開唱前 `−1.5 / −1.0 / −0.5 秒`
  逐個亮起，最後一點亮到開唱一刻；全部用**唱過色**（用戶指定，唔用漸變）。
  - 幾何：字級 `0.40×`、與歌詞行間距 `0.12×`、字距 `0.35×`（用 `\fsp` —— 半形空格在 CJK
    字型太窄，實測三點會黐成一嚿）
  - 位置：目標行**上方**；`\an8`（頂部對齊）上方冇位 → 改放行下方，永遠不出畫面
  - 只在「完整空白 lead-in」才出（`disp_start ≤ start − 1.5s`）；密句／上一句仲喺畫面時唔出
- **底部留白**：滑桿 + 精確 px 數字框（0–1000，0 = 自動），共用同一個 `IntVar` 雙向同步。
- **UI**：主頁新增「提前顯示 [3000] ms」「☑ 倒數圓點」；「換行延遲」保留，提示改為「句尾多留」。
- CLI 同步加 `--lead-in-ms` / `--countdown-dots` / `--no-countdown-dots`；
  `ui/clidoc.py` 支援 `BooleanOptionalAction` 的否定 flag（否則「複製等價指令」會靜靜漏掉 `--no-...`）。

**理由**

「下一句幾時出現」係觀感問題，唔應該由「上一句幾時開唱」間接決定；而 KTV 的倒數圓點
本質係「提示即將入歌」，屬輔助資訊，放喺歌詞上方就唔會同文字爭位。
窗口邏輯只留一份，係避免同類 bug 再出現的根本做法。

**驗證**

- `tests/test_lead_in.py` 新增 14 條契約；`tests/test_dual_line.py` 明確 pin `lead_in_ms=0`
  鎖住舊契約。全套 **208 passed**（含 slow：真實 ffmpeg 燒錄與大數據量）。
- 1280×720 合成片真實 libass 燒錄，逐幀目視（`_probe/lead_in/`）：
  - 3.4s：未唱的歌詞已出現（開唱 6.0s，提前 3.0s）
  - 5.4s：上方 2 粒綠點（第 1、2 點已亮）
  - 6.2s：圓點消失，第一個字開始掃綠
  - 9.2s（雙行）：上行已唱綠偏左、下行未唱白偏右，下行上方 2 粒點 —— 與原片觀感一致

**注意**

- **舊 `timings.json` 打開即變 3 秒提前顯示**（正是需求）。要回到舊觀感：主頁「提前顯示」設 0。
- 圓點顏色固定跟「唱過色」，換色盤會自動跟。

## ADR-032 · 預覽窗格可自訂解析度與縮放（2026-11-11）

**狀態**：✅ 已接受

**背景**

要求 ④：「可自訂預覽窗格的 resolution，使用戶可按輸出 video 的真實解析度預覽」。
舊 `_redraw_video()` 寫死 16:9 並填滿窗格，用戶無法知道「1080p 成品實際係幾大」。

**決策**

- 編輯器預覽工具列加兩個下拉：
  - **解析度**：跟原片（= `timings.json` 的 `PlayRes`，即輸出影片真實解析度）／1920×1080／
    1280×720／854×480／自訂（`160–7680 × 90–4320`）
  - **縮放**：適合視窗／50%／100%
- `scale = min(要求倍率, 適合視窗倍率)`；狀態列顯示**實際**比例（例如 `1920×1080 · 42%`），
  唔會靜靜畫到爆框。
- 記入 `settings.json`：`preview_res` / `preview_zoom` / `preview_res_custom`，跨 session 保留。
- 字幕疊圖**唔需要**按預覽解析度換算：ASS 本身會將 `PlayRes` 縮放到輸出尺寸，
  所以 `overlay._metrics()` 用「畫面高 ÷ `play_res_y`」在 720p 同 1080p 預覽下都正確。

**理由**

要判斷「字幕會唔會壓到 MV 內嵌字幕」、「底部留白夠唔夠」，必須知道成品像素尺度；
1:1 檢視係唯一可以驗證 px 設定的方法。

**注意**

- 縮圖快取只有 **160px 闊**（長片按需抽 640px），100% 縮放時**背景畫面會模糊**，
  但字幕文字係 tkinter 直繪，仍然清晰。要像素級確認請按「高清單幀」。
- 改解析度／縮放會清空 `_photo_cache`（舊尺寸的 PhotoImage 唔可以重用）。
