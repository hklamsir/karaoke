# 視訊串流播放可行性評估

> 日期：2026-10-30
> 狀態：**技術可行，但建議不在第一期做**（理由見 §6）
> 依據：本機實測（AV1 1920×1080 60fps MV《普渡眾生》），腳本見 `_probe/bench_stream.py`、`_probe/bench_tk.py`、`_probe/bench_seek.py`
> 相關：`docs/字幕編輯器計劃書.md` §6.7（影片預覽規格）

## 1 · 結論摘要

| 問題 | 答案 |
|---|---|
| **技術上做不做到？** | ✅ **做到。** ffmpeg 端有 **6.8–10.6 倍**實時餘裕，tkinter 端每幀 **9–20 ms**（即 50–109 fps 上限） |
| **做來有甚麼用？** | ⚠️ **有限。** 校時間軸真正需要的是「知道哪個 moment 對邊句歌詞」同「看字幕擺在邊」，2fps 縮圖 + 字幕疊圖**已經做到**；「看流暢片」用 VLC 得 |
| **成本多大？** | 🔴 **中至高。** 並非技術難，而是**雙時鐘同步 + 線程模型 + process 生命週期**三個複雜位 |
| **建議？** | 🎯 **第一期不做。** 保留「2fps 縮圖 + 字幕疊圖」（已寫入計劃書 §6.7）。若用戶 insists，做**第二期可選功能**，規格收窄到 **640×360 @ 15fps** |

## 3 · 實測數據

### 3.1 ffmpeg 端：產出速度（牆鐘 10 秒片段，**3 次實測範圍**）

| 設定 | 等效倍速（3 次範圍） | 判定 |
|---|---|---|
| 解碼 only（`-f null`） | **11.5 – 12.8×** | ✅ 極寬鬆 |
| **PNG 960×540 @30fps** | **5.5 – 6.8×** | ✅ 夠（最差情況都有 5 倍餘裕） |
| PNG 640×360 @30fps | 6.6 – 9.1× | ✅ 夠 |
| **PNG 640×360 @15fps** | **8.0 – 10.6×** | ✅ 最寬鬆 |
| MJPEG 960×540 @30fps | 8.0 – 8.7× | ✅（但需 Pillow 解 JPEG） |
| rawvideo rgb24 640×360 | 9.5 – 9.9× | ✅（但位元組量 198MB/10s） |
| PNG 1920×1080 @30fps（原尺寸） | 3.2 – 3.3× | ⚠️ 剛好，不建議 |

> **結論：ffmpeg 端完全並非瓶頸。** 就算原尺寸 PNG 都有 3 倍餘裕。
> ⚠️ **注意 run-to-run 變動 ±20%**（機器負載影響明顯）→ 規劃預算要**用最差值**。

### 3.2 tkinter 端：每幀成本（1000×600 Canvas，40 次平均）

| 路徑 | ms/幀 | fps 上限 |
|---|---|---|
| A. `PhotoImage(file=)` 960×540 | 16.94 | 59 |
| B. `PhotoImage(file=)` 640×360 | 8.32 | 120 |
| C. `PhotoImage(file=)` 480×270 | 5.97 | 168 |
| **D. base64 → `PhotoImage(data=)` 960×540** | **18.04** | **55** |
| **E. base64 → `PhotoImage(data=)` 640×360** | **10.10** | **99** |
| **F. base64 → `PhotoImage(data=)` 480×270** | **7.00** | **143** |

> `file=` 路徑（第 1–3 行）是「幀先落 disk 再讀」——只作對照。
> **串流正確做法是第 4–6 行**（`data=` 直接由記憶體餵入），因為無需 I/O。

**成本分解**（關鍵：知道錢花在邊）

| 組成 | ms/幀 | 佔比 |
|---|---|---|
| base64 編碼 | 0.26 – 0.50 | **~4%** |
| `Canvas.itemconfig` + `update_idletasks` | 1.11 | ~11% |
| **Tk 內部 PNG 解碼 + PhotoImage 建立** | **~6–18** | **~85%** ← 真成本 |
| pipe 讀取（另一 thread，未計） | ? | GIL 爭用風險 |

> ⚠️ **PNG 解碼是主要成本**，並非 base64、亦並非繪製。
> → 這解釋了為何 **640×360 @15fps 是最佳甜蜜點**：每幀 10.1 ms，佔 66.6 ms 預算的 **15%**。

### 3.3 Seek 延遲（重啟 pipe）

| 解碼方式 | 中位數 | 最大 | 備註 |
|---|---|---|---|
| **軟解 AV1（libdav1d）** | **252 ms** | **336 ms** | ✅ 完全可接受 |
| 硬解 d3d11va（seek 路徑） | — | — | ❌ 失敗：`scale` 濾鏡讀不到 GPU 記憶體，要補 `hwdownload` |
| 硬解 dxva2 | — | — | ❌ 反而慢到 0.4× 實時 |
| 硬解 nvdec (CUDA) | — | — | ❌ 失敗（無 NVIDIA 硬體） |

**硬解解碼速度對比**（10 秒片段，`-f null` 路徑）

| 方式 | 牆鐘 | 倍速 |
|---|---|---|
| 軟解 AV1 | 0.79 s | 12.7× |
| 硬解 d3d11va | 0.71 s | 14.1× |
| 硬解 dxva2 | 26.17 s | 0.4× ❌ |

> ✅ **好消息**：seek 只需 **252 ms**（並非想像中的 1–2 秒）→ **無需做 keyframe index**，簡單直接 kill + 重開 ffmpeg 就得。
> ⚠️ **壞消息**：硬解**不可靠**（d3d11va 要加 `hwdownload` 先通、dxva2 更慢、nvdec 沒有硬體）。
> 而且就算修好，硬解只快 **11%**（12.7× → 14.1×）——**遠不值那個複雜度**。
> → **結論：只做軟解。**

## 4 · 方案選項比較

| 方案 | 描述 | 新增依賴 | 新增程式碼 | 體驗 | 判定 |
|---|---|---|---|---|---|
| **A. ffmpeg image2pipe + PNG** | `-f image2pipe -vcodec png` → thread 讀 → queue → UI thread `after(16)` → `PhotoImage(data=b64)` | **零** | ~350–450 行 | 可用，seek 252ms | ✅ 主方案 |
| **B. A + MJPEG** | 同上但 `-vcodec mjpeg`，用 Pillow 解 | `Pillow` (~4MB) | A + ~40 行 | 更快（encode 5×），但多一個依賴 | 🔶 備選 |
| **C. OpenCV (`cv2`)** | `cv2.VideoCapture` + `imencode` | `opencv-python` (~60MB) | ~150 行 | 最少 code，但依賴重 | ❌ 不值 |
| **D. ffplay 獨立視窗** | UI 叫 `ffplay -ss <t> video` | **零** | ~30 行 | 獨立視窗，同主 UI 不同步 | 🔶 最低成本替代 |
| **E. 不做** | 用 2fps 縮圖 + 字幕疊圖 | 零 | 0 | 並非流暢，但夠校時間軸 | ✅ **建議第一期** |

### 4.1 方案 A 的預算核對（用**最差值**計）

**640×360 @ 15fps（建議規格）**

```
每幀預算（實時 15fps）       66.7 ms
├─ ffmpeg process            8.0× 實時 → 約 13% 一核（獨立 process）
├─ tkinter（PhotoImage+Canvas）10.1 ms → 15% 一核
├─ base64 + queue + 同步      ~1.5 ms →  2% 一核
└─ 合計約 30% 一核            ✅ 非常寬鬆
```

**960×540 @ 30fps（技術上跑得更動，但不值得）**

```
每幀預算（實時 30fps）       33.3 ms
├─ ffmpeg process            5.5× 實時 → 約 18% 一核
├─ tkinter                    18.0 ms → 54% 一核  ⚠️
└─ 合計約 75% 一核            ⚠️ 接近單核上限，GIL 爭用會使其變慢
```

> 🎯 **640×360 @15fps 是甜蜜點**：30% 單核，有大量餘裕應付 UI 其它部分。
> 960×540 @30fps 技術上跑得更動，但**不值得**——校字幕看不清 30fps 的分別，
> 但要用多 2.4 倍的 CPU 預算。

## 5 · 真正的工程難點（並非「技術可行性」，是「複雜度」）

| # | 難點 | 描述 | 對策 |
|---|---|---|---|
| **E1** | **雙時鐘同步** | 音訊用 `pygame.mixer.get_pos()`（pygame 自己開的 clock），視訊用 ffmpeg pipe 出的幆（另一 clock）。兩者必然 drift | **以音訊為 master clock**：每幀用 `audio_pos` 選擇最近的 video frame；video 慢就 hold 上一幀、video 快就 drop |
| **E2** | **線程模型** | tkinter **只在主執行緒安全**。decode 必須在獨立 thread，UI 必須在主執行緒 | decode thread → `queue.Queue(maxsize=4)` → 主執行緒 `after(16)` 抽幀。**queue 有上限**避免記憶體爆 |
| **E3** | **Process 生命週期** | seek = kill ffmpeg + 重開。關窗、切頁、換片時都要確保 process 收乾淨，否則 **ffmpeg 進程 leak** | 一個 `VideoStream` class 封裝 `start/seek/stop`，`stop()` 必須 `kill()` + `wait()`；`atexit` + 視窗關閉 handler 雙重保險 |
| **E4** | **記憶體** | 每幀一張 `PhotoImage`，**Python GC 不會自動回收 Tk image**（要 Tcl 層釋放） | 只保留「當前幀 + 上一幀」兩個 reference，舊的 `delete()` 掉 |
| **E5** | **閃爍** | tkinter Canvas **沒有 double buffering** | 用 `canvas.itemconfig(img_id, image=...)` 更新，**不要** `delete("all")` + 重建 |
| **E6** | **GIL 爭用** | pipe 讀取 thread 是 Python code，同 UI thread 爭 GIL | pipe 讀取用 `p.stdout.read(n)` 阻塞讀（釋放 GIL），base64 用 `base64.b64encode`（C 實作，釋放 GIL） |
| **E7** | **畫面 vs 字幕疊圖不一致** | 串流只解決「畫面」，**不解決**「字幕疊圖 vs 真實 ASS 不一致」 | 不變——疊圖仍然是 Canvas 自己畫，並非 libass |
| **E8** | **音訊同步粒度** | `pygame.mixer.get_pos()` 精度約 10–20 ms | 對卡拉OK 逐字對位（字級 40–100ms）**足夠**；不需要 sample-accurate |

## 6 · 風險登記

| ID | 風險 | 機率 | 影響 | 對策 |
|---|---|---|---|---|
| **S1** | **GIL 爭用令實際 fps 跌到 15–20**（預測值是 98 fps 上限，實際未必） | 中 | 中 | 用 640×360 @15fps（預算只佔 27% 一核） |
| **S2** | **ffmpeg 進程 leak**（切頁／關窗時） | 中 | 高（幾十個 ffmpeg 進程食記憶體） | `VideoStream.stop()` 集中管理 + `atexit` |
| **S3** | **音訊 drift 逐漸累積**（播 3 分鐘偏 200ms） | 中 | 中（字幕對不上） | 定期用 audio_pos 重同步（每 5 秒） |
| **S4** | **Codec 不支援**（HEVC 10bit / Dolby Vision / AV1 硬件 profile） | 低 | 中 | 已有降級路徑（縮圖抽不到 → 顯示錯誤） |
| **S5** | **4K 片 pipe 位元組爆** | 低 | 中 | 強制 scale ≤ 960 闊 |
| **S6** | **串流同字幕編輯同時跑 → 兩個重 CPU 進程爭資源** | **高** | 中 | **互斥模式**：播放時暫停 Canvas 重繪；或串流獨立分頁 |
| **S7** | **做得靚但沒有人用**（用戶用 VLC 看片，不會在字幕編輯器看片） | **高** | **高（沉沒成本）** | 🔴 **最關鍵的風險**——所以建議第一期不做 |

## 7 · 建議路線

### 第一期（現行計劃，維持不變）

```
2fps 縮圖 strip（快取）  +  字幕疊圖（Canvas）  +  當前字幕卡
```

- **成本**：~350 行（`thumbs.py` + `preview.py` + `overlay.py`），零新依賴
- **已足夠**：校時間軸真正需要的資訊（當前畫面 + 字幕位置 + 逐字 chip）全部有
- **風險**：低

### 第二期（可選，用戶明確要求先做）

在編輯器加「串流播放」**獨立模式**（並非預設開）：

| 規格 | 值 | 理由 |
|---|---|---|
| 分辨率 | **640×360** | tkinter 只佔 15% 一核 |
| 幀率 | **15 fps** | 對住字幕看不需要 30fps |
| 編碼 | **PNG**（不用 MJPEG） | 零新依賴；8 倍餘裕已經夠 |
| 同步 | **音訊做 master** | 每幀選擇最近 video frame |
| 播放控制 | ⏮ ▶ ⏭ ⏸ + 重播 3 秒 | 沿用現有工具列 |
| seek | kill + 重開 ffmpeg（`-ss`） | 實測 237 ms，無需做 index |
| 模式 | **同字幕編輯互斥**（播放時暫停拖曳） | 避免 S6 |

### 零成本替代方案（隨時可加，建議先做這個）

在編輯器工具列加一個「**外部播放器**」掣：

```python
subprocess.Popen([ffplay, "-ss", str(t), "-autoexit", video_path])
```

- **~30 行、零新依賴、零同步問題、零 GIL 風險**
- 並非嵌在 app 裡面，但 90% 的「我想查看片」需求都解決了
- **可以在第一期就加**，作為 S7 的對沖：如果用戶確實需要看片，有這個按鈕

## 9 · 順帶發現的阻塞項（已寫入計劃書）

> 🔴 **專案 `.venv` 沒有 tkinter**
>
> ```
> .venv/Scripts/python.exe          → ModuleNotFoundError: No module named 'tkinter'
> py -3                              → Python 3.13.15, Tk 8.6 ✅
> py -3 -m venv <新 venv>            → Tk 8.6 ✅
> ```
>
> 根因：`.venv` 是由一個**沒有裝 Tcl/Tk** 的 Python 3.13.14 建的
> （`C:\Users\pslam\AppData\Local\Programs\Python\Python313\tcl` 只有 `dde1.4` / `nmake` / `reg1.3`，**沒有 `tk8.6`**）。
>
> **對策**：UI 用**獨立 venv**：
>
> ```bash
> py -3 -m venv .venv-ui
> .venv-ui/Scripts/python.exe -m pip install -r requirements-ui.txt
> .venv-ui/Scripts/python.exe -m ui
> ```
>
> （CLI 的 `.venv` 可以保持不變，兩邊無需一致。）
